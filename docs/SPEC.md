# SubmIT - Product Specification

This is the shared SubmIT product specification. It defines behavior that both the backend and frontend must understand. Backend behavior and API boundaries live in `backend/SPEC.md`; frontend behavior lives in `frontend/SPEC.md`.

## 1. Product Purpose

SubmIT helps students propose, develop, and join group projects for the next school year. Teachers review ideas, give structured feedback, decide which projects may proceed, and indicate whether they are willing to supervise them. Students apply to accepted projects by submitting a ranked list of preferences. After the application deadline, the system forms project groups of three to five students, honoring feasible administrator pins and optimizing the remaining assignments to match student preferences.

## 2. People and Roles

- A `STUDENT` can create and own project ideas, collaborate on ideas owned by other students, develop an approved idea into full specifications, and apply to accepted projects.
- A `TEACHER` can create and own single-owner ideas, develop approved ideas into full specifications, review other users' ideas and full specifications, provide ratings and feedback, make approval and acceptance decisions, and record their supervision interest. Teachers cannot review their own ideas.
- An `ADMIN` can manage accounts, school-year application periods, supervisor assignments, rubric versions, and project allocation runs. Administrator-only accounts do not replace teacher decisions about project quality or acceptance.
- Any authenticated rubric reader (`STUDENT`, `TEACHER`, `ADMIN`, including `{TEACHER, ADMIN}`) can download the complete definition of any existing rubric version as reusable JSON or readable Markdown. Downloads contain rubric-definition data only, not publication metadata or assessment records; they do not add anonymous/public rubric access or grant permission to publish.

An account has exactly one of these role sets: `{STUDENT}`, `{TEACHER}`, `{ADMIN}`, or `{TEACHER, ADMIN}`. `STUDENT` is exclusive of both staff roles. A dual-role account receives the union of teacher and administrator permissions; it can make teacher decisions and perform administrator operations. An administrator-only account cannot perform teacher-only grading or decisions, and a teacher-only account cannot perform administrator-only operations. The application must retain at least one account whose roles include `ADMIN`. Registration always creates an immediately usable `{STUDENT}` account and ignores optional submitted roles.

Account roles are represented canonically as a `roles` list in API account data, including login/token user data and user-list results; the optional scalar `role` query parameter matches membership in the account's role set. JWTs carry the `roles` claim and grant each claimed authority. A role change updates account data and audit history but leaves already-issued token claims unchanged until expiry; the new role set takes effect on the next sign-in. No former singular-role JWT compatibility or migration/backfill of deployed user rows is required; the application has no deployed accounts, only its default administrator and testing accounts. Bootstrap-administrator and testing-profile provisioning use their corresponding singleton role sets.

The account language is `en` or `de`, defaults to `en` for new accounts, and is retained with the account for subsequent authenticated sessions. Only the account owner may change this preference; it does not alter roles, credentials, token validity, or authorization. The shared class catalogue contains a `No class / unassigned` class by default; newly registered students and accounts changed to `{STUDENT}` by an administrator receive it unless they already have an explicitly assigned class. Administrators may reassign that class like any other. Every student has exactly one class. Users must be authenticated to access application data. An idea's student or teacher author can edit its idea or specification only while it is a draft or has been returned for revision; existing withdrawn-idea rules also apply. Teachers and dual-role accounts can review other users' project submissions.

Each account has a required display name distinct from its unique login username. Registration requires a nonblank name; leading and trailing whitespace is trimmed, and the trimmed value must be at most 120 characters. A signed-in user may change their own name, and an account with `ADMIN` may change any account's name without changing its username, password, or roles. The authenticated workspace and administrator account list show account names while retaining usernames for identification.

The account language controls frontend-authored interface text and frontend-generated locale formatting. Anonymous visitors use the browser's primary language when it is German or English (including regional variants), and English otherwise. User-authored and backend-authored text, including API errors, remains unchanged.

## 3. Project Lifecycle

An idea follows these stages:

1. **Idea draft:** A student or teacher creates a concise proposal describing the project and its initial specifications.
2. **Idea submitted:** The proposal is sent for teacher review and can no longer be edited by its author until it is returned or approved.
3. **Needs revision:** A teacher returns the idea with feedback. Its author may revise and resubmit it.
4. **Idea approved:** A teacher authorizes the author to develop full project specifications. This is permission to elaborate the idea, not yet acceptance into the project application round.
5. **Specification submitted:** The author submits the developed specifications for review by another teacher.
6. **Accepted for applications:** A teacher accepts the fully specified project into the school-year project catalogue. Only accepted projects can appear in student applications.
7. **Not proceeding / withdrawn:** Teachers may decline an idea or full specification with an explanation; its author may withdraw their own proposal before project allocation.
8. **Applications closed / initial allocation processed:** At the configured deadline, applications close automatically and the system processes the initial student-to-project allocation synchronously. The visible period status becomes `ALLOCATED` after a successful run or remains/becomes `CLOSED` after a failed run; clients do not observe an intermediate `ALLOCATING` period status.
9. **Groups allocated / finalized:** The allocation run completes and an administrator reviews and finalizes the result.
10. **Formal project application:** Once a group is formed, its students submit the official project application for teacher review. The form records the project topic, each student's individual topic and planned result, the initial situation to change, scientific investigation concerns, the project objective, dated milestones, and an optional cooperation partner.
11. **Project in progress:** The teacher-supervised group carries out the approved project. Teachers independently select the project's routine and final criterion-assessment rubric versions. Routine individual assessments are new, blank observations against every applicable criterion; repeated observations append history. Final criterion assessment edits only current values for the exact final rubric and preserves revisions. Group assessments and metrics remain routine-phase inputs. Administrators may retain authorized read access but do not grade.
12. **Project completed and archived:** A teacher may assess final criteria before formal completion, but formal completion still requires the existing final-grade and artefact prerequisites. Teachers record or confirm students' overall final grades based on the selected final criterion version and routine group/metric inputs. Administrators may retain authorized read access but do not record or revise final grades. A publication-reviewed archive of the website, poster, and publishable source data is made publicly accessible without platform registration.

An idea may be approved for full specification by a teacher. Acceptance into the application catalogue requires a submitted full specification and an explicit teacher decision. Approval and acceptance are distinct decisions.

## 4. Project Ideas and Specifications

An initial idea includes:

- A short title and description of the proposed project.
- The problem, opportunity, or intended outcome.
- A few initial feature or scope points that make the idea assessable.
- The expected learning topics or skills involved, if known.
- The student or teacher submitter and the intended school year.

The full specification expands the idea with objectives, intended users, functional requirements or feature descriptions, expected deliverables, a proposed scope, and known dependencies or resources. It remains linked to the original idea and preserves the submitted revision history. While an application period is open, students may read the title, idea description, intended outcome, scope points, learning topics, and accepted specification for each project in that period's catalogue so they can make an informed ranking decision; they do not gain access to other students' private idea data or teacher review details outside that open catalogue.

Authors may provide each idea or full specification narrative using existing form fields, a Markdown import, or a PDF upload. These modes are mutually exclusive per save. Idea title, school year, and student collaborators always remain manual form inputs; a full specification leaves the idea's metadata unchanged. Markdown is parsed locally into the existing fields and remains editable; only the resulting JSON narrative is submitted. Markdown templates are available in English and German from the authenticated Templates/Vorlagen page. Their level-two headings are: idea `Description`/`Beschreibung`, `Intended outcome`/`Beabsichtigtes Ergebnis`, `Initial scope points`/`Erste Umfangspunkte`, and optional `Learning topics`/`Lernthemen`; specification `Objectives:`/`Ziele:`, `Intended users`/`Vorgesehene Nutzende`, `Requirements`/`Anforderungen`, `Deliverables`/`Ergebnisse`, `Proposed scope`/`Umfang`, and `Dependencies or resources`/`Abhängigkeiten oder Ressourcen`. Heading matching ignores case and surrounding whitespace. List sections contain one bullet per value; scalar sections preserve paragraph text. Missing, duplicate, unknown, or malformed required sections are rejected without partial form changes, and existing field limits still apply.

PDF narratives are non-empty, content-checked PDF documents no larger than 10 MiB. The PDF replaces narrative fields and is stored privately with the idea or specification; it is not exposed through public archive data or unrelated responses. Authors can replace a PDF only at the same lifecycle stages where the existing narrative can be edited. Submitted content is immutable during review, and specification review/revision history retains the exact PDF bytes previously reviewed. Teachers can preview submitted PDFs in an accessible modal. Idea owners, authorized reviewers, and students reading a project through its open application-period catalogue may retrieve the corresponding private PDF with non-cacheable `application/pdf` responses; public archive browsing and unrelated students cannot.

An idea may be authored by a student or a teacher. A teacher-authored idea has one teacher owner and no collaborators; teachers cannot be collaborators on ideas. A student-created idea may have up to four additional student collaborators (five owners total). Every owner of a student-created idea may read and edit it and its full specification under the existing lifecycle rules. Only the student creator may add or remove collaborators; a collaborator may leave, but the creator cannot be removed or leave. Owner changes do not alter submission content or lifecycle state. An accepted project may be joined by students through the application process; submitting an idea does not reserve a place in its eventual group.

For a submitted idea, teachers may approve specification work, request a revision, or decline it. A revision request or decline requires non-empty written feedback; ratings are optional, and any ratings supplied use the existing 1-to-5 scale. Decisions and feedback are retained in the authorized idea history, with only ratings actually recorded for each idea-review entry shown.

## 5. Formal Project Application

After allocation forms a group, the group collaborates on one formal project application. It is distinct from students' ranked project preferences and is submitted against the group's allocated project. The official form contains:

- **Topic:** one project topic, at most 200 characters.
- **Individual topic per student:** one topic for each group member, at most 200 characters per student.
- **Initial situation:** a description of the initial situation the project aims to change, at most 400 characters.
- **Investigation concerns:** the scientific investigation concerns for the individual topics, at most 2,400 characters total across all students.
- **Objective or goal:** the project's objective or goal, at most 400 characters.
- **Planned result of individual parts:** a planned result for each student's individual part, at most 2,400 characters total across all students.
- **Milestones:** a list of milestone text and a date for each milestone.
- **Cooperation partner:** optional information about a cooperation partner, if applicable.

All allocated group members, including students added by allocation to an original applying cohort, are associated with the application. The per-student topic, investigation concern, and planned result are linked to their respective students. Enforce character limits on the text values as specified, counting characters consistently on both client and server. A teacher reviews the complete form and may approve it, request revisions with feedback, or decline it with an explanation. The group may begin the approved project work after teacher approval. Submitted revisions and decisions remain in the project's history.

## 6. Project Progress, Grading, and Metrics

The initial grading rubric is based on the draft `docs/Entwurf Rubrikenbewertung.docx`. It is a working document and may change during the project. The platform must therefore represent rubric versions and criteria as data, not hard-code this draft as an unchangeable schema. Each rubric version records its source, version/effective period, criteria, category structure, rating scale, and any configured calculation rules. Each project independently selects a routine and final criterion-assessment rubric version; neither defaults to a globally active version. A phase transition is recorded, and changing a used phase requires a reason. Projects and grade entries retain the exact phase and rubric version to which they apply; rubric changes do not silently reinterpret existing assessments.

The current draft's grading roster covers these categories and criteria:

- **A. Technical realization:**
  - **Concept and architecture:** deriving functional/nonfunctional requirements from the problem; structuring the system/product and interfaces; selecting appropriate technologies, tools, methods, or materials; justifying key choices; considering technical, security, organizational, legal, and ethical constraints.
  - **Quality of realization:** implementing the concept correctly; using technologies and tools competently; meeting an appropriate technical quality level, including relevant robustness, error handling, security, performance, accessibility, and resource use; solving technical problems systematically; delivering a robust product fit for purpose.
  - **Technical process, workflow, and documentation:** organizing files and work states; using version control; documenting process, configuration, and decisions; documenting setup and reproducibility; managing versions, backups, and archives; providing documentation that enables continuation by others.
  - **Verification, testing, and quality assurance:** defining verifiable requirements and a test strategy; systematically checking the realization; selecting suitable test/inspection methods; recording and resolving defects; testing the final product under realistic conditions.
- **B. Project management:** planning and definition of work packages, milestones, responsibilities, dependencies, and dates; progress/risk monitoring and response; meeting commitments and communicating changes; goal-oriented communication and conflict resolution; structured organization of project records and work states.
- **C. Written work and technical documentation:** logical structure; sound, relevant subject-matter analysis; justified decisions and results; reflection on results, limitations, and alternatives; relevant sources and data; correct, consistent citation including applicable AI-content rules; formal completeness; clear distinction of own work from reused material; correct language, appropriate expression, consistent terminology, and clear explanation.
- **D. Presentation, discussion, and defense:** clear structure; accurate and understandable communication of problem, method, decisions, and results; suitable and professional use of media; appropriate technical language, largely independent delivery, and time management; answering technical/methodological questions; explaining decisions and reflecting on alternatives and limitations; distinguishing individual contributions.
- **Self-competence:** constructive contribution to topic/problem definition; independent handling of process steps; process documentation and meeting agreements and deadlines.
- **Professional-field competence:** clear professional-field relevance; selection of suitable methods; results-oriented use of those methods.

The draft generally presents criteria on a 5-to-1 scale with evidence/notes and category-level overall assessments. The platform must support these fields and scale while allowing the active rubric version to define or revise the precise criteria, scale labels, applicability, and whether a criterion is assessed individually, for the group, or both. The draft contains both individual and group-oriented criteria; the rubric configuration must make the assessment subject explicit.

An administrator publishes a new immutable rubric version when the school approves a change. A version has an effective date or school-year applicability. The rubric applicable to a project and its assessments is explicit; activating a newer version does not silently change existing projects, assessments, or grade calculations. Where a school applies a new version to an in-progress project, the transition is recorded and the platform retains which version governs each assessment.

Authenticated rubric readers browse all rubric versions, including inactive versions, on the dedicated `/rubrics` page and download an individual version as a reusable definition. Administrators may start a local draft, copy a selected version or load reusable UTF-8 JSON, edit that publication-request definition, and explicitly publish it as a new immutable version after choosing a unique version label. Invalid uploads leave the prior draft intact, and replacing an edited draft requires confirmation. JSON follows the existing publication-request structure and excludes internal publication/record metadata; Markdown presents the same configured definition for reading. Neither format contains assessments or identities, and browsing/downloading does not publish or mutate a rubric. `/grading` remains focused on project assessment and histories.

During project realization, only teachers can record or revise performance grades against the project's selected rubrics. A routine assessment shows all `STUDENT`/`BOTH` criteria in configured category order, starts blank for every student and assessment, validates all entered rows before writing, and saves only explicitly graded rows as append-only observations. Group assessments and metric observations use the routine selection. Final criterion assessment uses the independent final selection and hydrates only current final values for that student and exact rubric version; unassessed rows stay blank and routine grades never prefill them. Changed final values create reasoned, history-preserving revisions; unchanged rows are not written. Every entry records phase, rubric version, criterion, assessed student or group, grade, date, teacher, and evidence/comments. Administrators retain authorized read access but cannot record or revise grades.

Only teachers can record project-level metric observations over time where defined by the active rubric or school configuration. Each observation is associated with its metric definition/version, project, value, measurement time, and recording user where applicable. Administrators retain authorized read access but cannot record metrics. Because the rubric is liable to change, metric definitions, units, valid ranges, and applicability must be configurable/versioned rather than embedded as fixed assumptions.

Final criterion assessments may be entered before completion. Formal completion remains gated by the existing overall final-grade and archive prerequisites. Teachers record or confirm final grades for individual students and, where configured, the overall project grade using only final criterion values selected for the final phase plus routine group/metric inputs. Administrators retain authorized read access but cannot record or revise final grades. The rubric draft does not define all aggregation or weighting rules. Calculation rules must be explicitly configured and versioned before automatic calculation is used; when a rule's criterion identifier is ambiguous between final student and routine group inputs, reject that calculation rather than merge phases by identifier. Until then, the platform preserves all assessment inputs and allows only a teacher to record or confirm each final grade with a rationale identifying how the relevant phase-appropriate rubric grades and metrics were considered; it must not silently invent a formula. Final grades and their basis are visible to authorized users.

## 7. Completion and Project Archive

On completion, the project retains an organized archive containing:

- An accessible, browsable archive of the project's website as it existed at completion. Internal links and included assets should work within the archive where feasible, and the archive must be clearly distinguished from the live site.
- The final project poster.
- All source data produced, collected, or used for the project, with descriptive names and context sufficient to identify the data.

The completed project's public archive is read-only and accessible to anyone without an account. Its public contents include the website snapshot, poster, and source data only after they have been reviewed and approved for publication. Artefacts that contain student data, personal or sensitive information, credentials, private communications, unpublished grades, or other restricted material must not be published. Source data must be anonymized or redacted when needed before publication. The website snapshot must be checked for embedded student information and unsafe active content before release.

The archive must not expose student names or other identifying details, group membership, user accounts, applications, formal-application/review history, individual or group grades, rubric assessments, teacher feedback, private metric observations, uploader identities, or internal audit data. Public archive pages and downloads must not link to authenticated-only resources or leak private data through metadata, filenames, embedded files, or site assets.

Artefacts are associated with the project and retain internal metadata such as artefact type, title, description, upload time, uploader, and publication status. Publication approval is explicit and auditable; uploading an artefact does not make it public. The platform provides public browsing and retrieval only for approved artefacts belonging to completed projects, while authenticated project members and teachers may access other artefacts according to role and school policy. Upload, replacement, publication approval, unpublication, and removal follow lifecycle permissions and are auditable. Data access and presentation must follow applicable school privacy and retention rules.

## 8. Teacher Review

Teachers can record an overall decision and written feedback on an idea or full specification. Idea decisions include approve for full specification, request revision, or decline. Full-specification decisions include accept for applications, request revision, or decline.

For each review, teachers can provide a 1-to-5 rating (1 = low, 5 = high) and optional comments for:

- **Work size:** expected amount of work for a student group.
- **Curriculum relevance:** fit with teaching topics and learning objectives.
- **Technical complexity:** difficulty of the technical work.
- **Feasibility:** likelihood of completing the proposed scope in the available school year.
- **Learning value:** opportunity for students to develop useful knowledge and skills.
- **Resource needs:** expected equipment, software, access, or external support.
- **Risk and dependencies:** uncertainty, external dependencies, or delivery risks.

Ratings support discussion and comparison; they do not automatically accept or reject a project. Teachers can also provide an overall recommendation and explain their assessment.

For every reviewed project, each teacher can record one supervision preference: **wants to supervise**, **willing to supervise**, **not willing**, or **not available**. A teacher may add a note. This preference does not by itself assign a supervisor. An administrator may confirm any teacher as the project's supervisor, including after the project has been allocated; assigning a teacher who explicitly declined requires the administrator to acknowledge the refusal. Projects need not have a confirmed supervisor to be included in an application period.

## 9. Student Applications and Group Allocation

An administrator must provide a label when creating or updating an application period. A period has that label alongside its school year, opening time, closing deadline, and set of accepted projects from that school year. Period responses expose the label and school year separately; a legacy period without a stored label uses its school year as the response label without rewriting the stored record. Its effective opening state follows those configured timestamps rather than a stale stored status: before `opensAt` it is not open, and at or after `opensAt` and strictly before `closesAt` it is `OPEN`. At or after `closesAt`, application writes, applying-group changes, and early runs are closed. Student period reads, `projectTitles`, and catalogue details remain available through the exact `closesAt` instant, even after deadline processing changes the stored status, and are unavailable after it. Students apply individually or together using at least three distinct accepted projects ranked in preference order. The same project cannot appear twice in one ranking. All application and applying-group changes require the period to be open strictly before its deadline.

Every new period defaults to **All students**, and legacy periods without eligibility configuration retain that default. Before finalization, an administrator may set **Selected** eligibility to the union of selected current student accounts and students currently assigned to selected classes; duplicates count once and an empty selection admits nobody. Class membership is resolved when each early, initial, or replacement run snapshots its inputs. Period edits and class reassignment affect future runs only. Administrators alone can read or change eligibility configuration. Ineligible students cannot create or update individual preferences (`403`), but saved applications remain readable and may be used if eligibility is restored before a later run; eligibility changes never submit or restore an application. Existing withdrawal rules remain unchanged.

An applying group has one student creator/manager and 2–5 accepted students at submission; a creator-only formation draft is allowed. The creator invites through display-name-only student lookup and manages the shared ranking. Invitations do not reserve students or replace solo applications. Only the invitee accepts or declines; a student may accept only one group per period. Every accepted member, including the creator, explicitly approves the current roster/ranking revision. Acceptance is not approval. The creator submits only after unanimous current approval and explicit confirmation of atomic replacement of all accepted members' solo submissions. Each student then has exactly one effective application. Solo writes cannot independently change eligibility while a submitted shared application represents that student.

Actual roster/ranking changes invalidate all approvals and reopen shared submission as a noneligible draft. Pending/declined invitations alone do not. Accepted non-creators may leave; a creator must transfer to another accepted member before leaving, or explicitly dissolve. Transfer preserves the approved revision and one manager; dissolution releases everyone. Withdrawal, reopening, departure and dissolution never restore replaced solo submissions. Remaining members must renew approval and resubmit; released students must apply again. Period-row locking serializes membership uniqueness, final seats, consent, solo replacement, pins and allocation snapshots. Current student roles, deadline, revision and catalogue are rechecked server-side.

Changing a shared ranking or submitting it requires every accepted member to be eligible at that time; otherwise the action returns `409`. A submitted group that later becomes mixed-eligibility remains unchanged and is excluded whole from each run until all members are eligible again. It is never split, withdrawn, or rewritten by eligibility processing.

A submitted group is an indivisible allocation unit: every member goes to the same project or all remain explicitly unassigned. Allocation may combine units and solo applicants but never split units, duplicate students or form groups outside 3–5. A pair needs a filler and a five-person unit cannot receive additions. The objective maximizes assigned pinned students, then total assigned students, then assigned students on projects prioritized in that period's run snapshot, then per-student rank satisfaction around feasible pins; shared units contribute once per member, not once per application. Early, initial and replacement runs snapshot exact original rosters, rankings, revisions and priority project IDs. Finalization persists original cohorts and the complete final membership, including additions, for the separate Formal proposal. Legacy records remain readable without inventing origin from equal rankings or idea ownership.

Every eligible current student is an allocation candidate even without a submitted preference. Such a student may be assigned to any feasible catalogue project and contributes zero preference satisfaction. Each run snapshots the effective eligible IDs and preference-submission state used for assignments. Authorized staff can identify assignments made without preferences and submitted groups excluded for mixed eligibility. A student sees only whether their own assignment used preferences; legacy results without immutable preference state are labelled unavailable, never inferred from current applications.

Pinning any member of a submitted group constrains the entire unit. Same-project member pins deduplicate effective students toward capacity five; conflicting group targets or excess effective capacity are rejected atomically. Explicit pins remain separately removable: another member's pin continues constraining the unit until the last is removed. Draft/pending membership does not expand pins. An unranked shared target still requires administrator acknowledgement. Student results contain display-name-only cohort labels and identify the caller's cohort, distinguish individual allocation additions and separate multiple original cohorts; missing historical provenance is labelled unavailable. Invitations, approvals and provenance are private and never appear in anonymous archive metadata, links or downloads.

Eligibility also limits pin participation: a pin never adds an ineligible student to a run. Pin records remain stored and can constrain a later run if the student becomes eligible again. Eligibility and class changes never mutate prior snapshots or results.

Before the deadline, an administrator may start an early preliminary allocation run while the period is effectively `OPEN`. It snapshots applications at that moment, allows later application changes, leaves the period `OPEN` whether it succeeds or fails, and is visible only to teachers and administrators. Early runs never count as the initial run. At the deadline, the system automatically closes application changes and processes exactly one initial allocation synchronously for every due period not already finalized, regardless of its stored status or any early or replacement runs. A post-deadline period edit or replacement run cannot defer or suppress that initial run; competing scheduler, administrator, update, and finalization paths serialize the check and creation. A period cannot be finalized without its initial run, and already-finalized history is not backfilled. The period status becomes `ALLOCATED` after success and remains or becomes `CLOSED` after failure; the period does not expose an intermediate `ALLOCATING` state. An allocation-run record may be stored internally as `RUNNING` during synchronous processing, then becomes `COMPLETED` or `FAILED`; clients cannot observe that transient run status through the API. After the deadline, administrators may start replacement runs until finalization. Until the period is finalized, an administrator may pin any student to any accepted project in the period catalogue, independently of whether the student submitted an application or ranked that project. The student ranking is never changed. A pinned student sees any resulting assignment through the ordinary student period projection, even without an application; no pin metadata is exposed. A pin to an unranked project, or to a project for a student without an application, requires explicit administrator acknowledgement. No project may have more than five effectively pinned students, deduplicating submitted-unit member pins; catalogue updates cannot remove a pinned project. Pins can be created, replaced, or removed until finalization and apply to every subsequently started run, including early runs.

Each student is assigned to at most one project. A pinned student is assigned to the pinned project and is not moved by a run whenever that project can form a valid group; otherwise the pin-specific unassigned outcome applies. Pinned students count toward group size. The exact objective order is: maximize assigned pinned students; maximize total assigned students; maximize assigned students whose project is a priority in this period's run snapshot; then maximize ranked preference satisfaction using the existing scoring and deterministic tie-breaking. Priority projects are equal within their tier. If no projects are prioritized, established allocation outcomes and deterministic behavior remain unchanged. Priorities cannot reduce the number assigned, override a feasible pin, split a submitted applying unit, or relax the group-size limit. Every allocated group contains at least three and at most five students. If a pinned project cannot form a group of at least three even with other students, the run completes without creating a smaller group; its pinned students are unassigned with an explanation naming the pin.

Administrators may designate any subset of a period's accepted project catalogue as priorities, independently for each period. The designation is binary, has no project-wide setting or ordering, and remains editable until finalization, including after the application deadline while replacement runs are permitted. Removing a project from a period catalogue removes its priority atomically; adding it back does not restore that designation. Actual priority-set changes are audited with the administrator, period, and previous/resulting project-ID sets; an unchanged replacement creates no event. Each early, automatic initial, and replacement run snapshots the priority IDs used and later configuration changes cannot alter that run's inputs, result, or metadata. Staff run history/detail includes the saved IDs (empty for pre-feature runs); student period/application responses and public archive surfaces do not expose priority data.

The allocation must never violate group-size limits or assign a student to multiple projects. If the constraints make a complete allocation impossible, affected students or projects remain explicitly unassigned; the system reports why and allows a teacher or administrator to review the result. It must not silently create groups smaller than three or larger than five. A run records its eligible applications, projects, pins, period-priority IDs, early/initial classification, result, and completion status as an immutable snapshot. Later application, pin, or priority-setting changes do not change earlier runs. Students never see early-run results: before the deadline, their period projection is based only on completed runs created at or after the deadline; after the deadline it uses the most recent such completed run, unless the result has been finalized. An authorized administrator can trigger early runs while the period is open and replacement runs after the deadline; finalized results are not silently overwritten, and early runs cannot be finalized.

## 10. Shared Invariants

- Only ideas approved by a teacher may proceed to full specifications.
- Only projects with submitted full specifications and an explicit teacher acceptance may be offered to students.
- Teacher ratings and supervision preferences are separate from approval, acceptance, and confirmed supervision.
- Applications include at least three distinct ranked projects and are editable only before the deadline.
- Application-period eligibility defaults to all students; administrators may select students and/or classes until finalization. Selected classes are resolved to current members at each run snapshot, and each run retains its own eligible IDs.
- Every eligible student may be allocated, including students without submitted preferences; the exact objective is assigned pinned students, total assignments, period-priority assignments, then satisfaction of available rankings, and no-preference assignments contribute zero satisfaction.
- A submitted shared application participates only when all members are eligible. Ineligible students, including pinned students, are excluded without altering saved applications, pins, or prior run snapshots.
- Preference-submission status is visible only to authorized staff and to a student for their own assignment. Historical snapshots without that evidence remain unavailable rather than inferred.
- A student is allocated to no more than one project per school-year allocation; submitted shared units are indivisible, and pins fix the entire unit without changing its ranked application.
- Allocated groups contain three to five students, inclusive; pins count toward these limits and an infeasible pinned project is reported unassigned, never as a smaller group.
- A group's formal project application contains the official fields and character limits, including per-student topics, investigation concerns, planned results, dated milestones, and an optional cooperation partner, and requires teacher approval before project work proceeds.
- Ongoing grades are tied to a versioned rubric criterion, assessment subject, teacher, and time and retain their history.
- Final student and project grades preserve their underlying rubric assessments and metric inputs and use only explicitly defined, versioned grading rules.
- Completed projects retain a browsable website archive, poster, and source data with access control and audit history.
- The approved archive of a completed project is anonymously and publicly readable; private student information, grades, reviews, and unapproved artefacts are never exposed through public routes or files.
- Allocation decisions are reproducible from the recorded application-unit, roster/revision and pin snapshots; later membership, ranking or pin changes do not alter earlier runs or original cohorts.
- Important submissions, reviews, decisions, application changes, and allocation actions are auditable.
- Collection views are paginated. Public URLs, role names, enum values, pagination metadata, and error shapes are stable behavior.

## 11. Student Classes and Elective Subjects

Administrators maintain shared class and elective-subject catalogues by adding and renaming entries. The class catalogue includes a default `No class / unassigned` entry. Newly registered students and accounts changed to `STUDENT` by an administrator receive this class unless a class is already explicitly assigned; administrators may reassign it like any other class. Every student has exactly one class and zero to four shared elective subjects; administrators assign or change these attributes. Assignments reference catalogue entries; names are resolved from the current catalogue. Unknown references, duplicate subjects, more than four subjects, and non-student targets are rejected without partial assignment changes.

Teachers and administrators may see the current class and elective-subject names beside student names in authenticated staff views, including ideas and reviews, application summaries, allocation results, administration, and grading. Students cannot manage catalogues or assignments and cannot see other students' assignments. Existing access to a student's own account is unchanged. Catalogue and assignment data are private to authenticated staff and never appear in public archive responses.
