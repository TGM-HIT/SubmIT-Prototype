# Dev-70. Promote reusable archived verification scripts into documented shared tooling

## Intent

Archived run evidence contains ad hoc verification programs in several languages. Some operations recur across runs but remain tied to historical paths, commits, expected counts or ticket policies. Audit those programs, identify genuinely reusable operations, and provide supported, tested commands under the root `scripts/` directory rather than making future runs copy historical evidence code.

## Source

Owner request on 2026-11-05: inspect archived runs' evidence scripts, promote those justified for regular cross-run use into `scripts`, document their usage, and standardize their language, with argued exceptions.

Bounded authoring inspection found examples in `harness/runs/archive/Dev-57-20261105-1929/evidence/suite-summary.py`, `prepare-contexts.py`, and `harness/runs/archive/Dev-57-20261105-1837/evidence/path-audit.py`, plus `harness/runs/archive/Feature-20-20261021-1024/evidence/openapi-comparison.mjs`. These are candidate families, not a preapproved promotion list. Their current code contains run-specific paths, policies or assumptions; they must not be copied unchanged into shared tooling.

## Scope and contract

- Inventory script candidates beneath every existing `harness/runs/archive/<run-id>/evidence/` at implementation start, including nested evidence directories and executable/shebang files without customary extensions. Record the archive inventory boundary/date and exact source paths, language, purpose, duplicate family and disposition in tracked `scripts/verification-inventory.md`. Count reviewed candidates and reconcile the totals by disposition. Do not claim an exhaustive script inventory from a short filename-extension list alone.
- Exclude copied application/source trees, build outputs, dependency caches, vendor packages, generated fixtures and disposable baseline/build contexts from promotion analysis. Document the concrete discovery/exclusion rules and classify candidate-like files in those excluded trees as copied inputs rather than independent reusable evidence tools. Discovery may enumerate paths, but must exclude the exact root `bugs-and-ideas.md` and protected local files before any content reads; do not follow symlinks out of scope. Limit content inspection to candidate source and minimum linked evidence needed to determine its purpose.
- Assess each candidate family for repeatable usefulness across different tickets, clear inputs/outputs, overlap with existing repository tools, dependency/runtime availability, safety, and policy coupling. Promote operations justified for repeated cross-run use; retain ticket-specific probes, hard-coded business assertions, one-off reproductions and generated fixtures as historical evidence. Give a concrete reason for every retained or consolidated family. More than one prior occurrence is useful evidence, not an arbitrary minimum: a single generally useful operation may qualify with a specific cross-run use case. Do not promote everything or reject everything solely on frequency.
- Implement promoted operations as a small Python 3 standard-library CLI at `scripts/verify.py`, with descriptive subcommands only for the selected operations and corresponding tests at `scripts/test_verify.py`. Python is the default common language because existing configuration checks already use it and the sampled report/provenance/path operations need no new dependency. Consolidate duplicate implementations rather than retaining parallel Python and JavaScript versions.
- A Node.js exception may live at `scripts/verify-node.mjs`, tested by `scripts/test-verify-node.mjs`, only for an audited operation that materially depends on existing Node/browser/JavaScript tooling and cannot reasonably use the Python default without adding dependencies or losing verified behavior. Record the exact operation, reason, existing dependencies and invocation in the inventory and usage guide. Do not add a Node file merely as a generic future hook. Non-Python/non-Node source candidates must either be ported when promoted or retained with a reason; no new language runtime or library is authorized. Existing Java fixtures, shell entrypoints and frontend preview tools are not subject to a repository-wide rewrite.
- Parameterize repository/run locations, pinned revisions, input/output paths and caller-supplied expectations. Do not freeze historical test counts, test names, ticket IDs, permissive path lists or environment-specific paths into shared policy. Preserve the selected operation's actual proving power: for example, an XML summary does not prove command settings or test execution provenance, and an exact-path checker must not silently replace a ticket's authorization policy. Integrate with existing supported tooling instead of introducing a competing browser runner, build runner or harness gate.
- Preserve historical evidence: copy/generalize selected logic into new tracked tooling, but do not move, edit, delete, reformat or relink archived scripts, logs, lessons or outcomes. Shared tooling must not require access to any ignored archive to run, import or test. Cite its archived sources as provenance in the inventory, not as runtime dependencies. Do not execute archived code merely to discover what it does.
- Supported commands must have `--help`, explicit required inputs, documented output shape, deterministic ordering where applicable, meaningful nonzero failures and actionable diagnostics. Reject missing/malformed inputs and unavailable prerequisites rather than silently skipping or emitting success-shaped defaults. Never execute caller strings through a shell, source private environment files, print secrets, mutate protected inputs or start/stop services implicitly.
- Input-copy/context operations, if promoted, must validate the complete requested input manifest before copying, reject traversal/symlink escapes and protected files before reading them, preserve required bytes/modes, and write only to an explicit isolated destination. Process-running operations, if justified, must document and bound their execution, cancellation, exit propagation and owned cleanup. Avoid broad deletion and unrelated process termination. Read-only operations stay read-only; outputs use explicitly selected generated/evidence locations and do not overwrite existing evidence without an explicit documented opt-in.
- Add `scripts/README.md` covering the common-language decision and exceptions, prerequisites, each command's arguments/examples, exit codes, output format, safety/side effects, test command and when not to use it. Add a short root `README.md` link to that guide. Examples use synthetic paths/data and do not contain real credentials. Update Makefile help and add `verification-tools-test`; include the dependency-free Python self-tests in existing `make check`, and the Node tests only if an exception is actually introduced. Do not make ordinary checks require a Docker daemon, browser or archived run data just to test these utilities.
- This is developer tooling, not a change to harness roles, dispatch, gates, ticket policy, application behavior, backend/frontend source, API, schema or specifications. [Bug-40](Bug-40.md) separately owns Compose lifecycle/pgAdmin tooling; inspect current shared-file changes and integrate without overwriting them or importing its feature scope. No ordering dependency is required.
- Implementation paths are limited to `scripts/verify.py`, `scripts/test_verify.py`, optional justified `scripts/verify-node.mjs` and `scripts/test-verify-node.mjs`, `scripts/README.md`, `scripts/verification-inventory.md`, `README.md`, and `Makefile`. **Scope-gate allowances:** temporarily allow the exact named `scripts/` files actually used and `README.md`; `Makefile` is already allowed. Do not broaden shared gate semantics or treat its existing broad permissions as ticket authorization. If the audit demonstrates a genuinely necessary additional implementation path, refine this ticket's exact path allowance before editing that path.

## Mechanical checks (the Evaluator re-runs)

Durable automated tests, using Python `unittest` and the existing Node test runner only for an approved exception:

- **Archive discovery and disposition accounting:** synthetic archive trees cover nested evidence scripts, extensionless shebang scripts, duplicate families, copied contexts/vendor/generated exclusions and out-of-scope symlinks. Verify no protected file content is opened and candidate/disposition counts reconcile. If discovery is a one-time audit rather than a shipped command, retain its reproducible invocation and outputs as evidence, and test the shipped filesystem selection primitives that it uses.
- **Promoted command success and negative cases:** each actual promoted subcommand has named tests for valid input, missing input, malformed input, applicable empty input and expected output/exit status. Select at least two synthetic configurations from distinct run-like directories with different paths and expectations, proving the command is not tied to its source ticket. Tests use independently constructed expected values, not the helper's own logic.
- **Semantic fidelity:** for each promoted family, add proving cases for its actual invariant. Examples: XML summaries must detect failed/skipped/nested or malformed reports and honor caller expectations rather than hard-coded 402 totals; structural comparisons must ignore mapping-key order but preserve array order and unapproved value changes; changed-path audits must inspect deletions and both sides of renames and keep policy explicit. Apply only the cases relevant to selected operations; document which named tests cover each promoted family.
- **Safety and failure reporting:** verify read-only inputs are unchanged, rejected paths/private inputs are not opened, existing outputs are protected, prerequisites fail explicitly, and diagnostic output contains no synthetic secret markers. Include representative allowed controls. For promoted copying/process functions, also test their specified traversal/symlink, destination, exit propagation and owned-cleanup boundaries.
- **Archive independence and portability:** run supported commands and tests using synthetic data with no archive path available, from a different working directory and paths containing spaces. Importing helpers does not execute commands, inspect the repository or create files. No tests require local `.env`, `docker.env`, workbook data, Docker, browser services or network access.
- **Inventory, language and documentation consistency:** verify every promoted inventory entry names a current supported command and its tests; every exception has a concrete language justification; examples and help agree. Reconcile all candidate dispositions, reviewed archive directories and excluded classes. Preserve before/after hashes of inspected historical source records and confirm no archive content changed. If the full audit unexpectedly identifies no suitable family, report that evidence for owner disposition before creating empty infrastructure or claiming implementation complete.

Standard checks:

- `python3 scripts/test_verify.py`; if the justified Node companion exists, `node --test scripts/test-verify-node.mjs`. Exercise each supported command's `--help` and at least one documented synthetic example.
- `make verification-tools-test` and the existing configuration check; verify `make check` includes the self-tests without adding external runtime prerequisites. Run Make in a verified private-file-free input context because the root Makefile automatically includes `.env`.
- From `backend/` in that context, `./gradlew test` and `./gradlew checkstyleMain`: Makefile changes must preserve the existing backend Make-target tests. Do not weaken existing tests or change application/test source if an unrelated problem appears.
- Format changed Markdown with the existing formatter and run `git diff --check`. No frontend application checks or OpenAPI generation are required unless separately authorized source changes alter that scope.

## One-time manual verification (in addition to automated tests)

- **Implementor-performed:** from the usage guide alone, select each promoted operation and run its documented example against two isolated synthetic run directories with no archived-run dependency. Retain the exact commands, outputs and exits under the current ignored run evidence directory, and check a representative deliberate failure as well as success. Do not execute historical scripts, use real credentials, or operate on live deployments to demonstrate reuse.
- **Implementor-performed:** independently reconcile the completed inventory against the implementation-start archive listing, inspect every promotion/retention rationale and language exception, and verify archive integrity against the pre-inspection hashes. No browser or human-only scenario is required. If a candidate cannot be inspected safely or needs an unavailable prerequisite, record that limitation and its effect on audit completeness rather than claiming the full review passed.

## Acceptance criteria (the Evaluator judges)

- All in-scope archived evidence script candidates are accounted for under reproducible discovery rules, with deduplicated purposes and reasoned promote/consolidate/retain dispositions; exclusions and unresolved inspection limitations are explicit.
- Genuinely reusable operations are available under root `scripts/`, documented and tested for different run inputs, without historical absolute paths, commits, counts or ticket-specific policies. Do not create unused empty infrastructure or claim a completed promotion if none has been justified.
- Python 3 is the common default for promoted helpers; any Node exception is narrowly necessary, tested and explicitly argued. No extra runtime/library or unrelated repository-wide language conversion is introduced.
- Supported commands have reliable observable outputs, explicit failures and the stated input/output/privacy boundaries. Tests establish each promoted invariant rather than treating a passing historical script as proof.
- Archived records remain unchanged and shared tooling has no runtime dependency on ignored evidence. Existing supported tools are reused rather than duplicated.
- Usage documentation and check integration match the implementation; all applicable named checks pass, limitations are reported truthfully, and only the authorized tooling/documentation paths change.
