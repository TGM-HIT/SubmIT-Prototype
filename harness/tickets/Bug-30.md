# Bug-30. Show meaningful audit events with timestamps, resources, and actors

## Intent

The administrator audit-history view reportedly labels every event "Recorded event", shows no useful timestamp, and displays "Resource - actor not supplied". Staff cannot tell what happened, when, to which resource, or who performed the action.

The current `AuditService` already records `action`, `occurredAt`, `entityType`, `entityId`, and `actorUsername`; user events also record `actorId`, while system events use `actorUsername: SYSTEM` without `actorId`. `AdminPage.vue` guesses several possible field names and displays generic fallbacks. Its existing timestamp test supplies hand-written frontend objects, so it does not establish that real HTTP responses contain usable audit fields. The reported failure needs verification across persistence, HTTP serialization, frontend service consumption, and rendering, not just replacement of placeholder text.

## Scope and contract

- Implement after [Bug-29](Bug-29.md), which owns the typed audit response and generated frontend audit-entry type. Reproduce the reported behavior against real audit responses after that work; fix any remaining audit-specific serialization, mapping, or rendering fault. Do not assume a TypeScript annotation fixes the runtime payload. This ticket supersedes Bug-29's presentation-preservation requirement only where readable action/resource labels and actor usernames/system attribution replace raw codes or the "not supplied" fallback.
- Make `/admin` -> **Audit history** display, for every valid returned entry:
  - A readable action-specific description, such as "Elective subject created" or "User role changed", rather than one generic event title. Inventory the action codes actually emitted by the backend, including dynamically constructed actions, and provide matching English and German catalog entries for all current codes.
  - The recorded `occurredAt` date and time, formatted with the existing locale-aware timestamp helper and reacting to the selected account language. Do not substitute request time, render a date without its time, or alter the stored instant.
  - A readable resource-type label and the recorded `entityId`, so two resources of the same type can be distinguished. Resource UUIDs are acceptable identifiers; resolving historical resource titles or adding per-row lookup requests is not required.
  - The recorded actor username for user events and a localized "System" label for `actorUsername: SYSTEM` events without `actorId`. Do not show "actor not supplied" merely because a valid system event has no actor UUID. Retain the recorded username rather than resolving it from a possibly renamed current account; `actorId` may remain secondary information.
- Use the generated audit-entry type and canonical response fields, not speculative `eventType`, `createdAt`, `timestamp`, `status`, or `id` fields. Preserve the existing audit JSON contract established by Bug-29; do not add invented historical facts or rewrite stored records to make the UI appear complete.
- Keep an explicit localized unknown-action/resource label that includes the original non-empty code when a future code is encountered. Unknown codes must not collapse to an indistinguishable "Recorded event" or produce missing-translation warnings. A genuinely unusable payload must surface a visible error through the existing error/retry pattern, not success-shaped rows made entirely of fallbacks.
- Preserve user-accessible pagination beyond the first 20 records. Refresh loads page zero; Retry repeats the failed page. After successful loading, show the requested records and correct page controls; empty and failed loads remain distinguishable. Retain keyboard focus on the initiating tab/Refresh/Retry control when it remains mounted, and use the existing pager's focus behavior. No new editor, mutation, cancel flow, or row-detail view is required.
- Keep both audit endpoints read-only and available only to authenticated teachers and administrators as specified in `backend/SPEC.md`; students and anonymous users must not gain audit access. Do not expose audit data in public archive responses or change which actions are audited. Keep existing user/catalogue administration behavior outside the audit presentation scope.
- Limit changes to audit-related backend response handling if needed, frontend service consumption, the audit view, localization, and directly related tests. No product specification, seed-data, dependency, global Jackson migration, or unrelated administration redesign is required. Existing code/test paths are within the scope gate; no additional scope-gate allowances are anticipated.
- If backend response annotations/models must change, regenerate and review the ignored `contracts/openapi.yaml` with `./gradlew generateOpenApi`, then regenerate and review tracked `frontend/src/api/schema.d.ts` with `npm run api:types`; commit the latter if changed. Never hand-edit either generated artifact.

## Acceptance criteria (the Evaluator judges)

- Real audited user and system operations yield usable fields through both HTTP audit endpoints and render as meaningful events, not uniform placeholder rows (`realUserAndSystemEventsHaveUsableHttpFields`, `renders real audit response fields`).
- Current actions/resource types have readable English and German labels; occurrence timestamps include date and time and follow the selected language; user/system attribution uses recorded data (`audit action/resource localization coverage`, `locale-aware audit occurrence times`).
- Future unknown codes remain identifiable, missing required data produces an explicit error, and a system event without an actor UUID remains valid (`unknown codes and malformed responses`).
- Later-page events, Refresh, Retry, empty/error states, and keyboard focus work as specified (`audit pagination refresh retry and focus`).
- Audit authorization, read-only history, public-archive privacy, and unrelated account/catalogue behavior are preserved against the post-Bug-29 baseline, holding the same callers, records, and requests constant while changing only audit presentation/response handling (`auditAccessRemainsRestricted`, public-archive privacy and existing administration regressions).
- Applicable project checks pass, generated artifacts are regenerated rather than hand-edited when necessary, no unrelated changes are introduced, and no check is claimed unless performed. The documented browser verification demonstrates readable events at desktop and mobile sizes in both languages.
