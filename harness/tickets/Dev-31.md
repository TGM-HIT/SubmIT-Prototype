# Dev-31. Build a reproducible full-lifecycle documentation run

## Intent

Provide German, screenshot-based Markdown guides explaining the complete project lifecycle for students, teachers, and administrators. Capture screenshots automatically from the real application using synthetic data, so the guides can be refreshed as the application changes. Structure documentation and capture configuration so further documentation languages can be added later without copying the lifecycle automation.

The user confirmed full-lifecycle coverage, German initially with support for future languages, and Markdown guides with screenshots stored in the repository.

## Scope and contract

### Deliverables and language boundary

- Add `docs/user-guide/README.md`, `docs/user-guide/de/README.md`, and German role guides `schueler.md`, `lehrkraefte.md`, and `administration.md` below that language directory. Link the entry point from the root README.
- Commit the Markdown guides and the automatically captured PNG screenshots they reference under `docs/user-guide/de/images/`. Keep temporary browser profiles, service logs, credentials, and run evidence ignored and outside that directory. Do not hand-create or mock screenshots.
- Write German headings, explanations, captions, and meaningful image alternative text. Refer to the application's actual visible control labels, with German explanations when those labels are English. Translating the application UI is not part of this ticket.
- Keep locale-specific prose, captions, synthetic example text, and image paths separate from shared lifecycle/capture logic. Use explicit language selection; initially support `de`. Document the steps for adding another language, including its guide files, text/configuration, and screenshots. No second translation, new localization library, application-wide i18n system, or generic documentation framework is required.
- Provide one documented command from `frontend/`, `npm run documentation:generate -- --language de`, that starts an isolated testing environment, executes the documented capture sequence across roles, refreshes the German screenshots, checks guide/image references, and shuts down its owned processes. Prerequisites are the existing Java/Gradle, Node, and Chrome/Chromium setup used by the preview tool. Read the testing password from the existing environment-based convention, not committed credentials.
- Use desktop screenshots at the existing preview tool's desktop dimensions and record those dimensions in the capture report. This ticket does not change responsive UI behavior or require a second mobile edition of the guides.

### Lifecycle coverage

Provide an overview connecting the three role guides, prerequisites for each chapter, navigation/control names, actions, expected visible results, and links to the next actor's step. The following matrix defines the required chapters and capture checkpoints; a chapter may use additional screenshots where needed for comprehensibility.

| Stage | Role guide and required explanation | Required screenshot checkpoint |
| --- | --- | --- |
| Account and setup | Students register/sign in and maintain their profile; administrators manage accounts, class/subject catalogues and student assignment. Use synthetic testing accounts for capture; do not publish passwords. | Student workspace and administrator account management |
| Idea development | Students create an idea and manage collaborators; teachers can author their own ideas but cannot review their own. Explain submitting, editing restrictions and withdrawal/decline alternatives without presenting them as the main success path. | Student idea draft and submitted idea |
| Idea review and revision | Another teacher reviews, requests revision with feedback, the author revises/resubmits, and the teacher approves specification work. Explain optional ratings and supervision interest separately from approval. | Teacher review and student's returned-for-revision state |
| Specification and acceptance | Author develops/submits the full specification; another teacher accepts it for applications. Distinguish approval to elaborate from acceptance into the catalogue. | Submitted specification and accepted project |
| Application period and preferences | Administrator configures school year, dates and accepted projects, and assigns a supervisor; students inspect the open catalogue and submit/update ranked preferences. Explain that ownership does not reserve a group place. | Administrator period setup and student ranked preferences |
| Deadline and allocation | Explain automatic closure/allocation at the deadline; administrator inspects pins, results, unassigned outcomes and finalizes a feasible result. Distinguish preliminary from finalized membership. | Administrator allocation result and student's finalized group |
| Formal application | Allocated students prepare the official group application with individual topics, concerns/results and milestones, submit it, and a teacher reviews/approves it. Explain revision/decline alternatives and that work is approved only after formal approval. | Student formal application and teacher approval |
| Project work and assessment | Administrator publishes a versioned rubric/metric configuration; teachers record individual/group assessments where configured, evidence, metric observations and history. Explain student visibility of their own individual grades and association with the original rubric version. | Administrator rubric configuration, teacher assessment/metrics and student's own grades |
| Final grades | Authorized teacher records/confirms final grades with rationale using assessments/metrics. Do not invent weights or a calculation formula; automatic calculation is described only if actually configured. | Teacher final-grade result |
| Completion and publication | Members upload synthetic website snapshot, poster and source data privately; authorized teacher performs publication review and completion according to existing permissions. Explain rejected/private content and unpublication/removal. | Authenticated artefact review and anonymous completed-project archive |

- Demonstrate one coherent primary project across idea, acceptance, preference applications, finalized allocation, formal application, assessment, completion and public archive. Maintain identifiers across role changes; do not splice unrelated fixtures into a purported continuous story. Supporting accepted projects and applicants may be synthetic prerequisites for valid rankings and a group of three to five.
- Show the main successful lifecycle plus the explicit idea-revision round. Other alternatives in the matrix require accurate explanatory text, not an exhaustive screenshot tour of every error or branch.
- Preserve all role, lifecycle, grading and publication rules in [the shared specification](../../docs/SPEC.md), [backend specification](../../backend/SPEC.md), and [frontend specification](../../frontend/SPEC.md). This is documentation/tooling work, not authorization, workflow, grade-calculation or UI redesign.
