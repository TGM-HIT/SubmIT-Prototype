# Dev-32. Separate generated-guide exclusions from a dedicated documentation audit

## Intent

[Dev-31](done/Dev-31.md) generates local Markdown guides and screenshots under `docs/user-guide/`, with the entire output tree ignored by Git. Keep these outputs outside the general Compliance checks, but provide a dedicated recurring check that verifies their completeness and correctness against approved requirements and actual application behavior. Generated prose is an audit subject, never a source of product policy.

Source: user requests to exclude Dev-31 output from the existing checks and to add a new Compliance check specifically for user-documentation completeness and correctness.

## Scope and contract

- Add a shared exclusion rule to `harness/roles/auditor.md` and make the Inspect/Commands guidance in all six definitions, `harness/checks/Compliance-01.md` through `Compliance-06.md`, consistent with it. For those six checks, exclude the exact repository-root subtree `docs/user-guide/`, recursively, including generated Markdown, images and any future locale output. Apply the exclusion before any content read, search, recursive discovery or link-target traversal; do not rely solely on the current Git-ignore state or whether a command normally lists tracked files. State the explicit, narrow Compliance-07 exception described below; do not create a contradictory blanket prohibition.
- During Compliance-01 through Compliance-06, do not inspect, search, validate, repair, format, stage or commit files in that generated subtree, or generate findings/follow-ups from their contents, age, links, images, missing chapters, orphan status or presence/absence. Do not run `make doc` merely for those checks. Compliance-07 may generate and inspect the output for its dedicated purpose, but must never hand-edit, stage or commit it.
- During Compliance-01 through Compliance-06, when an in-scope authored document links into `docs/user-guide/`, inspect the referring text normally, but skip generated-target existence, image and anchor validation. A generated target may legitimately be absent before generation; do not report that absence as a broken link. Do not open the target or traverse its outbound links. This exception applies only to targets inside the excluded subtree, not to the source document's other links.
- Keep authored sources in scope where relevant to each check: `frontend/scripts/documentation/` templates and locale configuration, reusable preview/generation tooling, `Makefile`, `.gitignore`, root README, developer guides and the three SPEC files. The root README's generation instructions and the tooling's output/ignore policy remain auditable. Do not broaden an individual check's purpose to require inspecting unrelated source files.
- The exclusion is path-specific: do not exclude all `docs/`, all ignored/generated files, similarly named directories such as `docs/user-guide-notes/`, or the tracked generated API types and regenerated OpenAPI contract inspected by Compliance-03. Preserve existing exclusions for run/lesson records and the human-maintained root backlog file, without reading or changing that file.
- Reports for Compliance-01 through Compliance-06 must identify `docs/user-guide/` as excluded, not as inspected or checked with no discrepancy. Record the exclusion and skipped incoming generated-target checks in `## Scope inspected`; retain each check's existing topic coverage and report format. Compliance-07 instead records the exact generated inventory and evidence actually inspected.
- Add `harness/checks/Compliance-07.md`, titled **User documentation completeness and correctness**, using [the check template](../templates/check.md) and the contract below. Register it in the Compliance ledger with no fabricated run date, result or run ID (use `—` for never-run cells). Suggested cadence: after user-facing lifecycle, role, UI or guide-generation changes; at least monthly. Keep the existing Dev-32 ledger title unchanged during this refinement; the implementing Orchestrator must add the new Compliance-07 row in its tracked closeout commit, while the Implementor supplies the definition. The Implementor must not edit or stage `harness/plan.md`.
- Scope-gate allowances: `harness/checks/Compliance-01.md`, `harness/checks/Compliance-02.md`, `harness/checks/Compliance-03.md`, `harness/checks/Compliance-05.md`, `harness/checks/Compliance-06.md`, and the new `harness/checks/Compliance-07.md`. These exact files require temporary allowances; Compliance-04 and the Auditor contract are already permitted. No broad `harness/checks/` allowance is authorized.
- This is a documentation/contract-only change. Dev-31 is completed; reference its actual root command and authored sources rather than implementing or altering its tooling. Do not change product/API behavior, add a linter/test framework, rewrite historical audit reports or amend completed tickets. Dev-31's generation-time validation remains required; Compliance-07 adds semantic review, not a replacement for those assertions.
- Comparison baseline: the check definitions and Auditor contract at HEAD immediately before implementation. Hold all authored audit inputs and topic requirements constant; vary only the presence or contents of the excluded output tree and incoming references to it.

### Compliance-07 definition requirements

- **Scope and authority:** inspect freshly generated `docs/user-guide/README.md`, each supported locale entry point and student/teacher/administrator role guide, referenced screenshots, authored locale/templates/scenario under `frontend/scripts/documentation/`, and the current capture report. Use `docs/SPEC.md`, backend/frontend SPEC files, developer guides, relevant source/tests and actual UI/capture evidence in the Auditor's existing source-of-truth order. The completed Dev-31 lifecycle matrix is a coverage checklist, not authority to override later approved specifications. Inspect only the minimal relevant implementation evidence.
- **Fresh generation and prerequisites:** from the repository root, run `make doc LANGUAGE=de` with `PREVIEW_PASSWORD` supplied through the documented environment convention, installed dependencies, Java/Gradle, Node and Chrome prerequisites, and no prestarted owned application services. For any later supported locale, enumerate supported locale configurations and run the same shared command per locale. Record actual commands, baseline SHA, locale, generation outcome, report path, checkpoint inventory and dimensions; retain sanitized reports/review notes under the ignored audit run evidence directory. Do not reuse old output as proof of a fresh successful run. Do not install dependencies automatically, expose credentials, stop unrelated sessions, or change generator error/cleanup behavior.
- **Completeness topics:** cover account/profile and administrator account/class/subject setup; idea creation/collaborators, review/revision and supervision interest; specification approval versus acceptance; periods/catalogue/ranked preferences; deadline processing, allocation and finalized groups; formal application/teacher approval; versioned rubrics, individual/group assessments and metrics; explicit final grades/rationale; private upload, publication review, completion and anonymous archive. For each stage identify the responsible role, prerequisites, navigation/controls, expected result, cross-role handoff, chapter and screenshot. Check the same-primary-project continuity and distinguish prepared supporting records from actual UI actions.
- **Correctness topics:** compare guide statements and screenshots with actual roles/permissions, current route/control labels and reachable setup, lifecycle transitions, pagination where used, own-grade visibility, rubric-version association and configured-only calculation rules. Inspect German prose, captions and alternative text for accurate meaning and usable screenshot framing; review each supported locale independently. Check internal/cross-guide links and anchors, valid nonempty PNGs and report dimensions. A successful generator exit or link validator alone does not establish semantic accuracy or complete lifecycle coverage.
- **Publication and privacy:** check anonymous archive instructions and visible/downloaded synthetic public content against approved-publication rules, and verify private/student/grade/feedback/uploader/audit information and credentials are absent from public content. Do not mistake authorized authenticated teacher/student screenshots in their respective guides for public archive leakage. Never use production data or claim private/public isolation from a screenshot alone; cite the generator's request/state/privacy assertions and relevant implementation evidence.
- **Failures and findings:** absent output before generation is normal. A failed generation, missing prerequisite, occupied service/session or unreachable UI state must record the exact command/stage/route/request/status available and stop with an honest `stopped` outcome; do not waive checks, fake screenshots or infer correctness from stale output. Record completed partial observations and every uninspected topic. After successful generation, missing chapters/images, misleading instructions or mismatched screenshots are findings. Never repair generated output directly: follow-ups target authored templates/configuration/scenario/tooling or the product defect evidenced against approved specs. Apply existing Bug/Dev/Feature classification, duplicate and decision-needed rules; unresolved product policy remains a decision, not an invented guide rule.
- **Reports:** retain the Auditor's standard headings and add a per-locale stage matrix with `Stage`, `Role`, `Guide/chapter`, `Screenshot/checkpoint`, `Requirement/source`, `Observed UI or implementation evidence`, and `Result`. Every topic must have evidence, a finding or an explicit not-inspected reason. List generation status, structural validation and semantic/presentation review separately; no broad "all correct" claim based only on command success. Generated output remains ignored and no generated files enter fix/follow-up commits.

## Mechanical checks (the Evaluator re-runs)

Named verification scenarios using existing file reads, searches and the repository tree; retain exact commands/assertions and observed results in the handoff/evaluation:

- **C1 — All-check scope agreement:** Inspect the Auditor contract and each of Compliance-01 through Compliance-06. Verify they consistently require the exact recursive output exclusion before reads/searches and do not reintroduce it through discovery, source-of-truth, link, format, health, orphan or report rules. Verify every existing audit topic remains covered for in-scope inputs.
- **C2 — Generated-target boundary:** For Compliance-01 through Compliance-06, check an authored link to an absent generated page and to an existing generated page/image with an anchor: both skip target existence/content/image/anchor validation without opening the output. Contrast with a missing non-generated link. Verify only Compliance-07 permits generation/inspection; the shared contract has no blanket prohibition contradicting that exception.
- **C3 — Authored-source and path boundary:** Verify `docs/SPEC.md`, the two technical SPEC files, development guides, root README, Dev-31's authored template/configuration/tooling paths and relevant Make/ignore definitions are not exempted when otherwise in scope. Verify a similarly prefixed path outside `docs/user-guide/` is not excluded. Verify Compliance-03 still regenerates/inspects `contracts/openapi.yaml` and checks tracked `frontend/src/api/schema.d.ts`; preserve the existing human-maintained-file exclusion without reading its contents.
- **C4 — Output-independent general reports:** For Compliance-01 through Compliance-06, compare revised reporting instructions with the pre-change baseline: generated output present, absent or containing stale/invalid text must yield the same authored-input audit scope, with an explicit exclusion/skipped-target note rather than output-derived findings or claims of inspected content. No documentation generation or content inspection of generated output is needed for this contract check.
- **C5 — Dedicated audit coverage and registration:** Compare the new check with the check-template headings and the Compliance-07 requirements above. Verify each lifecycle stage, role, correctness/privacy boundary, locale, structural/semantic review and report column has an explicit topic/evidence obligation. Verify the proposed ledger row uses the unique next check ID and empty never-run cells, and is registered by the Orchestrator at closeout, not staged by the Implementor.
- **C6 — Freshness, failure and findings contract:** Walk the check's instructions for successful fresh generation, absent initial output, missing password/browser, occupied ports, failed UI requests and generation failure with older output present. Verify only the fresh successful case permits a completeness/correctness conclusion; failed cases stop with exact diagnostics and uninspected topics. Verify generated defects lead to authored-source or evidenced product follow-ups, never edits/commits to generated files. Check configured-only grading, authenticated versus anonymous privacy and unresolved-policy handling explicitly.
- Run `git diff --check`. Before committing Markdown, run `make format-markdown FILES="..."` with exactly the Markdown files in that commit. No backend/frontend build, application tests, browser capture or full Compliance run is required to implement this documentation-only ticket; the future Compliance-07 run itself must perform the generation/review described above. No new automated test tooling is required; C1-C6 are explicit mechanical contract inspections, not runtime-test claims.

## One-time manual verification

- None beyond C1-C6 contract inspection. No UI or generated content changes are part of this implementation. Do not confuse verification of the new check definition with actually running Compliance-07; no successful audit may be claimed before execution.

## Acceptance criteria

1. Compliance-01 through Compliance-06 consistently exclude only the recursive `docs/user-guide/` subtree; the Auditor contract explicitly permits Compliance-07's dedicated generation/inspection without weakening other exclusions. Covered by C1/C2/C3.
2. Incoming links from authored documents do not cause generated outputs to be read or their absence/anchors/images to become audit findings; ordinary non-generated link checks remain intact. Covered by C2.
3. Authored documentation sources/tooling, specifications and existing API contract checks remain auditable under their existing purposes; existing unrelated exclusions are preserved. Covered by C1/C3.
4. General checks cannot derive findings from generated output; Compliance-07 may report its completeness/correctness defects but must target authored sources or evidenced product issues and never treat generated prose as policy or edit/commit generated files. Covered by C1/C4/C6.
5. Compliance-07 is defined and registered as never run, covers all specified lifecycle/role/locale, correctness, structural and privacy topics, requires fresh generation and evidence-based semantic review, and records explicit stopped/partial outcomes on failures without stale-output acceptance. Covered by C5/C6.
6. Only the named harness contracts/check definitions and the closeout Compliance ledger registration change; existing topics/report obligations remain intact, and all named checks pass. No application, generated-output or historical-record changes are included. Covered by C1/C3/C5/C6.
