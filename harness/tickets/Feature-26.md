# Feature-26. Browse teacher Formal proposals by project and period

## Intent

Teachers currently have to enter a project ID to open its Formal proposal. Give teachers a searchable, paginated list of proposals with human-readable project, group-member, and application-period context. Start with proposals for projects the teacher supervises, while allowing the teacher to search all proposals.

## Source

Owner clarification: teachers may see all Formal proposals. The initial list should show projects the teacher supervises; search/filtering should cover project name, student names, and application period.

## Scope and contract

- On `/formal-application`, replace project-ID lookup for users with the `TEACHER` role with a searchable list of existing Formal proposals. Show the project title, current display names of all allocated group members, application-period label and school year, and current proposal status. Keep proposal and project IDs only as internal API values; do not render them in labels, links, status text, or accessible names.
- Default the list to proposals for projects with a current confirmed supervisor assignment to the signed-in teacher. This uses the confirmed assignment, not a teacher's supervision preference. Provide an explicit way to clear this filter and see all proposals. Searching or filtering with the default enabled narrows the supervised-proposal set; when cleared, the same search can find any proposal.
- Provide one labeled text search that matches a case-insensitive substring in the project title, any group member's current display name, the associated application-period label, or school year. Trim surrounding whitespace; an empty or whitespace-only query means no text filter. Do not add unrelated search fields or invent additional filters.
- Add a paginated authenticated `GET /api/formal-applications` list endpoint for callers with the `TEACHER` role. It returns `200` with one summary per existing Formal proposal and supports optional `q`, `supervisedOnly`, `page`, and `size` query parameters. `q` is an optional string; trim surrounding whitespace, treat blank as no text filter, and perform a case-insensitive substring match against the project title, every group member's display name, the period label, and school year. `supervisedOnly` is an optional boolean defaulting to `true`; setting it to `false` includes proposals for every project, regardless of supervisor. Apply search and the supervisor filter before pagination. Use the existing pagination contract: zero-based `page` defaults to `0`; `size` defaults to `20` and is normalized to 1–100. Sort results deterministically. Missing/invalid authentication returns `401`; authenticated callers without the `TEACHER` role receive `403`.
- The summary response has exactly these required, non-null fields:

  | Field | Contract |
  | --- | --- |
  | `formalApplicationId` | UUID used internally for existing review actions; never displayed. |
  | `projectId` | UUID used internally to load the existing proposal; never displayed. |
  | `projectTitle` | Current human-readable project title; use `Unknown project` when the project record does not resolve. |
  | `studentNames` | Current display name of every allocated group member, in group order; use `Unknown student` when an account no longer resolves. |
  | `periodLabel` | Current associated application-period label; use the school year when a linked legacy period has no label, or `Unknown period` when no period resolves. |
  | `schoolYear` | School-year display value of the associated application period, or `Unknown school year` when no period resolves. |
  | `status` | Current status: `DRAFT`, `NEEDS_REVISION`, `SUBMITTED`, `APPROVED`, or `DECLINED`. |

  Resolve the period from the persisted allocated project-group context for the proposal; do not infer it from unrelated project or preference data. Do not include student IDs, rankings, applications, or unrelated allocation data, and do not render either UUID in the teacher UI.

- The endpoint returns the existing page envelope with `content`, `page`, `size`, `totalElements`, and `totalPages`. The `page` and `size` values in the envelope follow the normalized query values.
- Selecting a row loads that project's existing proposal and review history through the current GET endpoint, then presents the existing teacher review workflow with human-readable project and period context. Teachers can open proposals outside their supervision when the default filter is cleared. Preserve the current teacher authorization to read and review all proposals; do not add a supervisor-only access rule to the list, detail, or review APIs.
- Preserve the existing administrator project-ID lookup/review workflow and all student Formal proposal selection, roster, and authoring behavior. This ticket changes the teacher presentation and adds a teacher list API; it does not change proposal creation, review decisions, lifecycle rules, or backend authorization for existing operations.
- Add all new teacher-list labels, loading/empty/error/retry text, and filter controls to the parallel English and German frontend locale catalogs. Use accessible labels and keyboard-operable pagination, filters, and proposal selection; do not embed translated text in component logic.
- Coordinate with the open [Bug-31](./Bug-31.md), which also changes `FormalApplicationPage.vue` and its tests. Preserve its student-only roster and member-tab requirements; do not make the teacher list depend on the student-only roster API.
- Update `backend/SPEC.md` with the teacher list route, query contract, response fields, and unchanged all-proposal teacher access. Update all related Formal proposal and role passages in `frontend/SPEC.md` so teachers use the searchable list while administrators retain project-ID lookup and students retain their finalized eligible-project flow. Check the related Formal proposal, access, and role statements throughout both files for contradictions. `docs/SPEC.md` needs no change because the proposal lifecycle and review policy remain unchanged.
- Add an opt-in testing-profile preview fixture activated by `DADB_TESTING_FORMAL_PROPOSAL_SEARCH_PREVIEW=true make run-testing`. It must provide at least two valid existing proposals in distinct finalized periods, one supervised by `teacher01` and one supervised by another teacher, with distinct project titles and member display names. Keep this extension isolated from ordinary seed data and account counts; do not alter the existing standard Formal proposal fixture. Document the exact activation and seeded state in `backend/DEV-GUIDELINES.md`.
- No Makefile change or new dependency is required. Do not change generated API files by hand. `contracts/openapi.yaml` is ignored: regenerate and review it, but do not commit it. Regenerate tracked `frontend/src/api/schema.d.ts` with `npm run api:types` and include the type update for the new list endpoint.

## Acceptance criteria (the Evaluator judges)

- On `/formal-application`, a `TEACHER` sees a searchable, paginated list of existing proposals with project title, all group-member display names, application-period label/year, and status; no project, proposal, or student UUID is rendered. `FormalApplicationPage.test.ts` verifies the teacher view and summary content.
- The initial list contains only proposals for projects currently confirmed to the signed-in teacher. Clearing the supervised-only filter makes every existing proposal searchable and selectable, including proposals for projects supervised by another teacher. The public API tests compare the unfiltered result with every seeded proposal, and `FormalApplicationPage.test.ts` verifies both scopes; teachers remain authorized to read and review those other proposals using existing APIs.
- Search matches project title, any group member's display name, application-period label, and school year as case-insensitive substrings after trimming; blank search applies no text filter. Matching is performed across the complete proposal set before pagination. Named backend API and frontend component tests verify each field, blank input, and a result beyond the default page size.
- All new teacher-list content is localized in English and German with matching locale keys; `FormalApplicationPage.test.ts` and `i18n.test.ts` verify both.
- Selecting a result opens the existing proposal and review history, and the teacher can use existing review controls without a supervisor restriction. Loading/error/empty states are explicit; failed requests are not presented as empty results. The named frontend tests cover selection, retries, stale responses, and existing review behavior.
- After a successful review, the detail and matching list row show refreshed status while preserving search/filter/page state and keyboard focus. Cancelling the review confirmation makes no request or mutation; returning to the list restores focus as specified. `FormalApplicationPage.test.ts` covers each outcome.
- Students continue using the finalized eligible-project dropdown and group-roster tabs; administrator-only users retain project-ID lookup. Existing teacher GET/review permissions and all proposal lifecycle behavior remain unchanged. Role and API regression tests verify these constraints.
- The `DADB_TESTING_FORMAL_PROPOSAL_SEARCH_PREVIEW=true` fixture is testing-profile-only, contains the required supervised and non-supervised proposal examples, and leaves the ordinary Formal proposal fixture and 32-account baseline unchanged. The fixture tests and updated backend guide verify the opt-in path and its state.
- `backend/SPEC.md` and `frontend/SPEC.md` consistently describe the new teacher list, retained administrator lookup, unchanged student flow, and teachers' access to all proposals. OpenAPI and the generated frontend list-response types are regenerated and reviewed; standard backend/frontend checks pass.
