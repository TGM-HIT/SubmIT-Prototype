# Dev-55. Seed the draft grading rubric for testing

## Intent

Starting the application with `make run-testing` should provide an effective grading rubric based on `docs/Entwurf Rubrikenbewertung.docx` so the grading page and its existing rubric API can be exercised without first creating rubric data manually. The seeded version is a testing snapshot of that changeable draft, not a school-approved rubric.

## Source

Owner confirmation: provide the rubric through `make run-testing`. Owner refinement on 2026-10-27: "Use the `docs/Entwurf Rubrikenbewertung.docx` as rubric." This replaces the earlier synthetic criterion-content requirement, not the testing-profile boundary or prohibition on invented final-grade calculations. Source: [draft rubric](../../docs/Entwurf%20Rubrikenbewertung.docx), together with the versioned-data requirements in [shared specification](../../docs/SPEC.md) and [backend specification](../../backend/SPEC.md).

## Scope and contract

- Add a published testing snapshot of the draft to the existing `testing`-profile fixtures, clearly labeled with its source and draft/testing status. It must be effective on startup so `GET /api/grading-rubrics/active` succeeds and the rubric is present in `GET /api/grading-rubrics` when the full testing application is started with `make run-testing`. Do not add a Makefile target or change the existing startup commands.
- Use the document's actual German headings and descriptor content, not a small invented representative rubric. Cover A (Technische Realisierung: A1-A4), B (Projektmanagement), C (schriftliche Arbeit und fachliche Dokumentation: C1-C3), D (Präsentation, Diskussion und Verteidigung: D1-D2), and the additional Selbstkompetenz, Berufsfeldkompetenz, and Teamkompetenz tables. Preserve section/subsection membership and row order in a checked-in fixture-data representation supported by the existing model; do not make the Word document a runtime parsing dependency or introduce a new library.
- Reconcile the complete document into an explicit source-to-fixture inventory: numbered assessable descriptors, unnumbered legacy/proposed descriptors, editorial notes, and each section's `Gesamtkalkül`. Preserve assessable wording and normalize only document-layout whitespace. Where numbered replacements and unnumbered draft alternatives coexist, retain the alternatives and editorial context as draft descriptions/notes rather than silently dropping them, duplicating them as approved criteria, or resolving the author's open questions. Include the three additional competence tables as draft content, even though the document marks them as not yet covered. Do not import the sample candidate, supervisor, class, school year, or other completed cover-sheet fields as fixture identities or applicability policy.
- Build a valid rubric using the existing rubric structure and publication validation. Use the document's 5-to-1 assessment scale (numeric bounds 1-5, step 1), evidence/notes context, and section-level overall assessments. Represent `Gesamtkalkül` as a manual assessment in the existing model, not an inferred average. Assign stable identifiers and explicit student/group/both applicability; document any subject/stage mapping needed for the testing snapshot as fixture configuration, not a school-approved rule inferred from the draft. Retain individual and group assessment coverage. Keep the existing required metric definition clearly labeled as supplemental synthetic testing data, separate from the document-derived criteria: the draft does not define a quantitative metric. Leave aggregation rules empty. Do not invent scale meanings, mandatory-evidence rules, final-grade weights/formulas, or change grade-entry behavior.
- Make seeding safe and deterministic on repeated testing-profile startup: reuse the same fixture version without creating duplicates or mutating an immutable version; report a conflicting existing version explicitly rather than silently replacing it. Seed only in the testing profile; do not add accounts or rubric data to the default/production profile.
- Preserve the existing 32 testing-account invariant and all unrelated testing fixtures. Keep the existing make targets and API contract unchanged; no product/API SPEC or OpenAPI change is required.
- Update `backend/DEV-GUIDELINES.md` to describe the source document, draft snapshot/version, source-to-fixture mapping, explicit testing applicability, supplemental metric, and no-calculation boundary. Update `frontend/DEV-GUIDELINES.md` to distinguish the draft rubric available from ordinary testing startup from the separate rubric publication performed by the full-lifecycle documentation workflow; keep that workflow's deliberate API-publication coverage intact. The document remains unchanged and is not promoted to fixed schema or approved policy.

## Acceptance criteria (the Evaluator judges)

- On `make run-testing` startup, `GET /api/grading-rubrics/active` returns the effective, clearly labeled draft/testing snapshot sourced from the Word document, and `GET /api/grading-rubrics` includes that same immutable version. Draft rubric API fidelity verifies both endpoints and the complete source inventory.
- Repeating testing-profile fixture startup reuses the existing version without duplicates or mutation; a conflicting version fails visibly without overwriting it. The fixture integration test covers both cases.
- The rubric faithfully represents the document's sections and assessable descriptors, draft alternatives/context, 5-to-1 scale, evidence/notes, and manual overall assessments, with explicit testing applicability and individual/group coverage. Only the supplemental metric remains synthetic and is clearly distinguished from document content. Draft rubric API fidelity verifies these fields and the omission of sample personal data; no aggregation rule, invented final-grade calculation, approved policy, or runtime Word parser is introduced.
- Compared with the existing testing-profile fixture baseline enforced by `TestingAccountsConfigurationTest` and the five named idea/application-period fixture tests above, account and unrelated fixture data remain unchanged; only the draft/testing rubric and its publication audit event are added. All named baseline tests pass.
- A context without the `testing` profile has no rubric created by this fixture, as verified by the extended `TestingAccountsInactiveProfileTest`.
- The `/grading` browser check after `make run-testing` displays the seeded data at desktop and mobile viewports with both rubric requests successful. If a request fails, the manual check reports it rather than replacing or bypassing the fixture.
- `backend/DEV-GUIDELINES.md` and `frontend/DEV-GUIDELINES.md` describe the source-derived fixture and the distinction from the documentation workflow consistently; Documentation workflow preservation verifies the existing workflow continues to exercise rubric publication.
- Standard backend checks and Markdown formatting pass; API and product specifications remain unchanged.
