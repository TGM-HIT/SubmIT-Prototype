# Feature-28. Prioritize projects within an application period's allocation

## Intent

Administrators can configure an accepted project catalogue for each application period, but allocation currently optimizes assignments using student rankings and existing pins only. Let an administrator mark accepted projects as priorities for one specific period. The allocator should prefer assigning students to those projects even when a student ranked another project higher, without sacrificing a larger number of assignments or weakening existing pin and group-size rules.

## Scope and contract

- Priority is a binary, period-specific designation on projects in that period's accepted catalogue. The same project may be a priority in one period and not another. There is no global project-priority flag or ordering among priority projects.
- In the administrator Allocation view, list the selected period's accepted projects with their current priority state and controls to mark/unmark them. Keep loading, empty, error, retry, and save states. A failed save retains the administrator's draft selection. After a successful save, show the persisted selection and retain focus on the save control. Do not require a confirmation dialog for this reversible setting.
- Provide administrator-only `GET /api/application-periods/{periodId}/priority-projects` and `PUT /api/application-periods/{periodId}/priority-projects` operations. GET returns the current set of priority project IDs. PUT replaces the complete set atomically using a request containing `projectIds`, which may be empty; IDs must be unique and each must belong to the period's accepted catalogue. The response returns the saved set. Unknown periods return `404`; invalid, duplicate, or non-catalogue project IDs return `400`; changes to a finalized period return `409`; non-admin callers receive `403` and unauthenticated callers `401`. Annotate and test these conditions.
- Priority settings may be changed until the period is finalized, including after the deadline when replacement runs are still permitted. Removing a project from a period's catalogue also removes its priority designation atomically; adding that project back later does not restore priority. Periods with no designated priorities retain the existing allocation objective and deterministic behavior.
- Each new allocation run snapshots the priority project IDs used by the optimizer. Include `prioritizedProjectIds` in staff run responses, with an empty list for existing runs created before this feature. A later period-setting change affects only subsequently started runs; it must not alter an earlier run's saved input, result, or priority metadata. Priority data is available only through the administrator configuration operations and authenticated staff run history/detail; do not expose it through student period/application responses or public archive surfaces.
- Preserve the current optimization objective and exactness, changing only its ordering: first maximize the number of assigned pinned students as today; then maximize total assigned students; then maximize the number of assigned students whose assigned project is designated as a priority in that run's snapshot; then maximize ranked preference satisfaction using the existing scoring and deterministic tie-breaking. Thus, priority must not reduce the total number assigned, override a feasible pin, split a submitted applying unit, or relax the group-size limit. Priority projects are equal within their tier. When no project is designated, behavior and results remain as before.
- Priority affects early, automatic deadline, and replacement runs using the setting captured when each run starts. A period-specific priority change must not mutate any existing allocation run or result.
- Audit each actual priority-set change, recording the administrator, period, and previous and resulting project-ID sets. An idempotent PUT that leaves the set unchanged must not create a change event. Keep this staff-only audit data free of student information.
- Update `docs/SPEC.md`, `backend/SPEC.md`, and `frontend/SPEC.md` to describe the period-specific priority setting and objective order. Search each file for existing descriptions of allocation optimization, pins, period project catalogues, and allocation run snapshots; make the ordering and scope consistent without changing unrelated requirements. Declare each necessary SPEC change in the handoff. Do not edit developer guides unless implementation changes make a current instruction inaccurate.
- API changes require controller/request/response annotations, regenerated and reviewed `contracts/openapi.yaml`, and regenerated frontend API types. The contract must describe `projectIds` as required, unique, and allowed to be empty; describe the `prioritizedProjectIds` run-response field and its empty value for pre-feature runs. Never hand-edit generated files.
- Out of scope: project-wide priority, priority levels or ranking among priority projects, reducing the number of students assigned to favor priorities, manual student placement, changes to student rankings, pin semantics, eligibility, optimizer exactness, group-size limits, or allocation scheduling/lifecycle.

## Mechanical checks (the Evaluator re-runs)

Durable automated tests (join the build):

- Through public HTTP behavior, verify administrator GET/PUT persistence for distinct periods containing the same project, empty-set replacement, repeated idempotent PUT, and isolation when a project is prioritized in only one period.
- Verify `401`/`403` authorization, `404` for an unknown period, `400` for duplicate and non-catalogue IDs, and `409` for changes after finalization. Verify a catalogue update removes priorities for removed projects atomically and that adding the project back does not restore them.
- Verify audit events for actual changes include the admin actor, period resource, and before/after sets; verify an idempotent PUT emits no change event and no student information is recorded.
- Add independent optimizer regressions that prove the objective tiers: (1) existing pinned-student priority remains ahead of subsequent tiers; (2) total assigned count wins when prioritizing would leave more students unassigned; (3) with the same assigned count, a solution assigning more students to priority projects wins even when those students rank another feasible project higher; (4) preference score still wins when priority-assignment count is tied. Include feasible three-to-five groups and a shared applying unit to prove priorities neither split units nor relax group-size rules. Assert result counts, project membership, preference score/tier outcome, pin behavior, and determinism from ticket-owned expected values rather than the implementation's score helper.
- Verify an empty priority set produces the established no-priority result for existing deterministic optimizer fixtures.
- Through public allocation APIs, verify each newly started run stores and returns the exact prioritized project IDs used; after changing the period setting and starting another run, the earlier run snapshot/result/metadata remain unchanged and only the later run reflects the new set. Cover an early run and a post-deadline run when applicable.
- Frontend tests verify period-specific priority labels and controls, save success, draft retention and retry on failure, empty and loading states, role visibility, localized English/German copy, and display of the saved priority projects in staff run detail. Verify the ordinary student period response/page contains no priority metadata.

## Acceptance criteria (the Evaluator judges)

- An administrator can mark and unmark accepted projects as priority for a specific application period, with persisted configuration isolated from every other period. A project removed from a period loses that period's priority, and re-adding it does not restore the designation.
- Priority settings are mutable only before finalization. Endpoint authorization, validation and status behavior matches the documented `401`, `403`, `404`, `400`, and `409` conditions.
- The allocator uses this exact objective order: assigned pinned students, total assigned students, students assigned to period-priority projects, then existing ranked preference satisfaction and deterministic tie-breaking. Priority never reduces total assigned count or supersedes pin constraints.
- Submitted applying units remain indivisible, every group remains size three to five, eligibility and all existing allocation constraints remain unchanged, and no-priority fixtures retain their established outcomes and deterministic behavior.
- Every new run captures and returns its priority project IDs. Later changes affect only later runs; previous snapshots and results are unchanged. Existing pre-feature runs return an empty priority-ID list.
- Changes to priority settings create the specified staff-only audit event; identical-set PUTs do not create an event. Student-facing and public responses expose no priority metadata.
- The administrator view supports English and German, displays and saves period-specific settings, preserves drafts on failure, and displays the saved run priorities to staff. Existing allocation flows and run/finalization behavior outside the new priority tier remain unchanged.
- The three named SPEC files consistently describe period-specific project priorities and the objective order, without weakening existing requirements. Standard checks, generated API review, and manual verification pass; no generated artifacts are hand-edited and no unrelated files are changed.
