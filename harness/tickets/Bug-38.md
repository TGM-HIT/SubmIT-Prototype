# Bug-38. Document multipart upload size-limit responses accurately

## Intent

Multipart uploads are subject to a 10 MiB per-file limit and an 11 MiB aggregate request limit, including multipart framing and other parts. Either limit can cause rejection with HTTP 413 during multipart parsing, before application validation. The project-artefact OpenAPI operation omits this applicable 413, while three existing PDF-upload operations describe only the aggregate request limit and their 400 descriptions also claim that oversized files return 400. API consumers need accurate status triggers and response documentation without changing upload behavior.

## Scope and contract

### Affected operations and response changes

| Operation | Required 413 documentation | Required 400 documentation |
| --- | --- | --- |
| `POST /api/projects/{projectId}/artifacts` | Add the missing response; describe both limits below. | Preserve the existing project UUID / artefact metadata / content description and schema. |
| `POST /api/ideas/pdf` | Correct the existing response to describe both limits below. | Retain invalid metadata, empty/non-PDF file, and conflicting narrative inputs; remove the oversized-file cause. |
| `PUT /api/ideas/{id}/pdf` | Correct the existing response to describe both limits below. | Retain invalid metadata, empty/non-PDF file, and conflicting narrative inputs; remove the oversized-file cause. |
| `PUT /api/ideas/{id}/specification/pdf` | Correct the existing response to describe both limits below. | Retain empty/non-PDF file and conflicting narrative inputs; remove the oversized-file cause. |

- Each 413 description must identify **either** a file part exceeding `10 MiB (10,485,760 bytes)` **or** the entire multipart request body exceeding `11 MiB (11,534,336 bytes)`, including metadata, other parts, and multipart framing. These are strict exceedance limits, not rejection at equality. Do not describe the request ceiling as a PDF-only constraint or the sum of file contents alone. Preserve the existing PDF filename, signature, non-empty, and maximum-file-size requirements.
- Grounding: `backend/src/main/resources/application.properties` sets `spring.servlet.multipart.max-file-size=10MB` and `spring.servlet.multipart.max-request-size=11MB`; these binary-sized configuration values agree with the 10 MiB guards in `PdfFileValidator` and `ArtifactPayloadMapper`. Multipart parsing is shared by the four controller bindings above. The framework multipart size-exception/resolver path, not `ApiExceptionHandler`, supplies the 413; the latter does not handle `MaxUploadSizeExceededException`. Confirm the deployed path with real-server evidence in M2 before choosing its response representation.
- The PDF 400 causes are grounded in `PdfRequestValidator` (metadata and conflicting input checks), `PdfFileValidator` (empty/non-PDF validation), and `ApiExceptionHandler`'s `ApiException` mapping. The validators retain defensive over-size checks that can produce 400 when invoked with a synthetic multipart object or different parser configuration; do not remove or change those guards. The public contract here describes requests under the unchanged ordinary application configuration, where the parser intercepts over-limit uploads first.
- Keep all other responses unchanged: artefact upload retains `201,400,401,403,404,409`; idea PDF creation retains `201,400,401,403`; both PDF replacement operations retain `200,400,401,403,404,409`. Only the artefact operation gains a new status (`413`); the three PDF operations already declare it. Authorization, lifecycle, UUID binding, and domain failure behavior are not being redesigned.
