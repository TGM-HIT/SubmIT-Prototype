# Dev-54. Consolidate duplicate review request schemas

## Intent

The generated `IdeaReviewRequest` and `ReviewRequest` repeat the same JSON property shape and schema constraints, differing in their decision descriptions. This duplication makes frontend clients treat the same structural payload as different named contracts without providing a real type distinction. Use one generated request schema for that shared shape, not nominally distinct types, while preserving each endpoint's existing runtime behavior.

## Scope and contract

- Consolidate only the duplicate **OpenAPI/generated structural request schema** used by these three `POST` operations:

  | Route | Current schema | Resulting schema | Endpoint-specific decisions |
  | --- | --- | --- | --- |
  | `/api/ideas/{id}/reviews` | `IdeaReviewRequest` | `ReviewRequest` | `APPROVE_FOR_SPECIFICATION`, `REQUEST_REVISION`, `DECLINE` |
  | `/api/ideas/{id}/specification/reviews` | `ReviewRequest` | `ReviewRequest` | `ACCEPT_FOR_APPLICATIONS`, `REQUEST_REVISION`, `DECLINE` |
  | `/api/formal-applications/{id}/reviews` | `ReviewRequest` | `ReviewRequest` | `APPROVE`, `REQUEST_REVISION`, `DECLINE` |

  Each required `application/json` request body must reference the same canonical `#/components/schemas/ReviewRequest`. Remove the duplicate generated `IdeaReviewRequest` component rather than retaining an independently expanded copy or adding brands, discriminator fields, route tags in the body, casts, or hand-written frontend replacement models.

- Make the canonical backend schema definition the source for this shared generated shape. Keep the distinct runtime DTO bindings and their Jackson/Bean Validation behavior: `IdeaReviewRequest` is a bean with `NON_NULL` inclusion and rating setters using `Nulls.FAIL`; `ReviewRequest` is a record used for specification and formal reviews. They are **not** interchangeable runtime validators. Sharing the documentation schema does not authorize merging these DTOs, changing the controller-to-service payload conversion, or moving/changing service validation or authorization.
- Preserve the complete current generated property, requiredness, nullability, format, and constraint contract:
  - Exactly `decision`, `feedback`, `workSize`, `curriculumRelevance`, `technicalComplexity`, `feasibility`, `learningValue`, `resourceNeeds`, `riskAndDependencies`, and `recommendation`.
  - Required properties remain `decision` and `feedback`; all seven ratings and `recommendation` remain optional. No property gains a nullable type or an enum.
  - `decision` remains a string with `minLength: 1`. `feedback` remains a string with `maxLength: 5000` and the baseline emitted `minLength: 0`. `recommendation` remains a string with `maxLength: 2000` and `minLength: 0`. Each rating remains `integer`, `format: int32`, minimum 1, maximum 5.
  - Preserve the non-decision field descriptions. Replace the two decision descriptions with one accurate description identifying the three route-specific decision sets above; retain/document those sets at their respective operations. Do not describe the union as valid at every route. Preserve operation-specific rating semantics in the affected operation descriptions so a shared shape is not represented as shared runtime validation.
  - The emitted `feedback.minLength: 0` mismatch is owned by [Bug-28](Bug-28.md), not this ticket. Sequence this consolidation before that constraint correction; the coordinator must reconcile Bug-28's old schema-name inventory separately. Do not edit Bug-28 or fix its other fields here.
- Preserve exact methods, routes, path encoding, statuses, JSON request serialization, response bodies, validation/error messages, role/ownership checks, lifecycle transitions, review persistence, and audit effects. Comparison baseline is the captured revision above, using the same profile, fixtures, actor, lifecycle state, and literal JSON body; only schema identity/documentation and generated type references vary. In particular, retain these existing differences:

  | Rating input on an otherwise valid submitted resource | Idea review | Specification review | Formal review |
  | --- | --- | --- | --- |
  | All seven omitted | `201`; omitted ratings stay absent from the stored review payload | `400`; record serialization supplies nulls and `IdeaRules.ratings` rejects them | `201`; record serialization retains nulls |
  | A supplied rating is explicit JSON null, with the other six valid | `400`; Jackson rejects the supplied null | `400`; `IdeaRules.ratings` rejects null | `201`; optional null passes Bean Validation and is retained |
  | All seven are integers within 1–5 | `201` | `201` | `201` |
  | A supplied integer is 0 or 6, with the others valid | `400` | `400` | `400` |

  These are preservation examples, not a new or exhaustive status matrix. The three controller bindings establish `201`; `ApiDtos` establishes Bean Validation and Jackson constraints; `IdeaService`/`IdeaRules` and `FormalApplicationService` establish the different domain paths; `ApiExceptionHandler` maps validation/unreadable bodies and bad-request `ApiException`s to `400`. Do not “repair” these differences as part of deduplication.

- Runtime strings still reject missing/null/blank `decision` or `feedback`, enforce feedback/recommendation length limits, and keep existing whitespace handling: services trim for required-text/decision checks, without introducing new trimming of serialized or persisted text. Keep responses and their schema requiredness/nullability untouched, including the different `ReviewResponse` and `FormalReviewResponse`.
- Regenerate OpenAPI from backend annotations, then regenerate frontend types. `contracts/openapi.yaml` is ignored: regenerate and review it, do not hand-edit or commit it. `frontend/src/api/schema.d.ts` is tracked: regenerate and include its changes. Only generated request-type reference adjustments necessitated by removing `IdeaReviewRequest` may change `frontend/src/api/services.ts`, `frontend/src/api/services.typecheck.test.ts`, or `frontend/src/features/ideas/IdeasPage.vue`; add focused request tests in `frontend/src/api/services.test.ts`. Coordinate overlapping request-type work with Dev-44 rather than completing or rewriting its other service/pagination work.
- Exclude broad repository-wide deduplication, semantically different request contracts (including publication reviews), new dependencies/generation tooling, SPEC changes, UI behavior changes, response-model consolidation, rubric/allocation reconciliation, and Dev-44 ticket/run/ledger changes.
