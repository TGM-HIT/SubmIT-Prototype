# Dev-08. Add an opt-in minimal testing fixture mode without application periods

## Intent

`make run-testing` (Spring profile `testing`, in-memory H2) always seeds five application periods with their applications, allocation runs and groups: the original allocation preview period, the student04 (`ALLOCATED`) and student05 (`CLOSED`) assignment-state periods, and the two Dev-07 multi-group periods. They are all created from `TestingIdeasFixtureSeeder`, which seeds the allocation preview (`TestingAllocationPreviewSeeder.seed`, `seedStudentAssignmentStates`, `seedMultiGroupScenario`). The seeder also creates the ten accepted synthetic projects that form the period catalogues, with their supervision preferences. For manual testing of other workflows this data is noise in the Applications, Allocation and Overview views.

Developers need an opt-in way to start the testing profile without any application-period or allocation data, while keeping the testing accounts and the sample ideas and specifications. Default behavior must stay unchanged, so the existing fixture tests and the Dev-05/Dev-07 preview workflows keep working.

## Scope and contract

- Add an opt-in switch, read only when the `testing` profile is active, that selects a "minimal" testing fixture mode. The Implementor picks the mechanism that fits repository conventions. The existing precedent is configuration read from environment-style names (for example `DADB_BOOTSTRAPADMIN_USERNAME` in `BootstrapAdminConfiguration`) and documented in `.env.example`. Constraints:
  - The default (switch unset, empty or `false`) is the full fixture set exactly as today. Nothing changes for `make run-testing`, `make run-backend-testing`, `npm run preview` or any existing test unless the switch is explicitly enabled.
  - The switch has no effect and creates nothing when the `testing` profile is inactive. It must not add or change beans or behavior in the default profile.
  - The value `true` enables the mode. Document how other values are treated (for example anything other than `true` means the full set) and make the implementation match the documentation.
- **With the switch on**, the `testing` profile still seeds:
  - all testing accounts from `TestingAccountsConfiguration` (`student01`–`student15`, `teacher01`–`teacher05`, `admin01`, `admin02`, with the existing display names and the testing password);
  - the two sample ideas per student for `student01`–`student05` from `TestingIdeasFixtureSeeder` (one `IDEA_SUBMITTED`, and one with an approved idea review and a submitted specification, `SPECIFICATION_SUBMITTED`), unchanged in content.
- **With the switch on**, the `testing` profile creates none of the following (decision confirmed by the requester):
  - any of the five application periods and their student applications, allocation runs, finalizations and stored project groups;
  - the ten accepted synthetic projects of the allocation catalogues: the three "Supervisor-free preview project" ideas for `student01`–`student03` and the seven "multi-group preference option" ideas owned by `student06`–`student12`. No idea is in `ACCEPTED_FOR_APPLICATIONS` status as a result;
  - the `WANTS_TO_SUPERVISE` and `WILLING_TO_SUPERVISE` supervision preferences that `teacher01` and `teacher02` give those accepted projects;
  - the fixture marker records for the skipped scenarios (`testing_idea_fixture` records for the allocation preview period and the accepted projects, and `testing_multi_group_allocation_preview`). The per-student sample-idea markers are still created, so reruns stay idempotent.
- Not affected by the switch (unchanged in both modes): the formal-application fixture from `TestingFormalApplicationFixtureConfiguration` (project `03a00000-0000-4000-8000-000000000001`, group of `student01`–`student03`, submitted formal application). It is not one of the five application-period fixtures and does not depend on the accepted projects. This is an assumption; say in the handoff if the implementation shows otherwise.
- Add a Makefile target `run-testing-minimal` (listed by `make help`, in `.PHONY`) that starts the backend with the `testing` profile and the switch enabled, plus the frontend dev server, like `run-testing`. It must work without editing `.env`. Reuse the existing run targets where practical (for example a variable or a sibling backend target) rather than duplicating the frontend part. `make run-testing` itself stays on the full set. Document in `.env.example` (commented out, default off) how the switch is set through the environment, and its relation to `.env`, which the Makefile includes and exports: say what that means for `make run-testing`.
- Documentation: update `backend/DEV-GUIDELINES.md` ("Local workflow accounts" section) minimally with the switch name and its environment mapping, the default, the `make run-testing-minimal` target, what is skipped and what is kept as listed above, and the local/testing-only warning. Do not change the existing descriptions of the full set. Update `frontend/DEV-GUIDELINES.md` only if the preview tooling gains or changes usage text; no preview tool change is required, and the preview tool keeps the full set by default. After the change, check that the documented names, defaults and commands match the implemented behavior (see mechanical checks).
- No change to production code paths outside the testing-profile fixture classes and the new configuration read, to API shape, authentication, authorization, allocation, finalization or student-view logic, or to frontend behavior. No `SPEC.md` change is expected.
- Dependencies and ordering: Dev-06 and Dev-07 are done and are the baseline (`student01`–`student15` and the multi-group periods). Dev-09 (labels for the periods) is a sibling ticket and independent. It is authored in parallel and may touch the same seeders, so whichever lands second must rebase on the other and keep both behaviors. This ticket does not depend on Dev-09 and must not implement labels.

## Mechanical checks (the Evaluator re-runs)

Durable automated tests (join the build). Each fixture test class that sets the switch uses its own unique in-memory datasource URL, as the existing fixture tests do:

- **Switch off (default) = unchanged.** The existing `TestingIdeasFixtureTest` (profile `testing`, switch not set) passes unmodified, including `multiGroupPreviewHasFixedGroupsPreliminaryAndFinalStatesAndIsIdempotent`, `allocationPreviewContainsSubmittedApplicationsAndServiceGeneratedCompletedRun`, `assignmentPreviewAddsSyntheticUnassignedAndNoResultStudents`, and `exposesTwoValidWorkflowIdeasPerStudentToOwnersAndTeachers` (`teacher01` sees 20 ideas). Add a scenario with the switch explicitly set to `false` that proves the same full set (five periods, ten accepted projects) so an explicit `false` is not mistaken for on. `TestingFormalApplicationFixtureTest`, `TestingAccountsConfigurationTest` and `IdeaReviewControllerTest` also keep passing without edits unless they assert on data the switch changes (they should not run with the switch on).
- **Switch on = no periods, accounts and ideas present.** A new test class with the `testing` profile and the switch enabled (using the repository's property mechanism for tests, for example the `properties` attribute of `@SpringBootTest`) asserts that:
  - no `application_period`, `student_application`, `allocation_run` or allocation-created `project_group` records exist, other than the formal-application fixture group at project `03a00000-0000-4000-8000-000000000001`, and no `testing_multi_group_allocation_preview` or period-related `testing_idea_fixture` marker exists;
  - `GET /api/application-periods` returns no periods for `admin01` and for a student (for example `student04`), using the real login with the testing password;
  - all 22 testing accounts exist with their roles and display names, and can log in (representative check on one account per role is enough for login; the account count and usernames must be exact);
  - `student01`–`student05` each own exactly two ideas (`IDEA_SUBMITTED` and `SPECIFICATION_SUBMITTED`) with a review by `Olivia Chen` on the second, `teacher01` sees ten ideas in total, and no idea has status `ACCEPTED_FOR_APPLICATIONS`;
  - no `supervision_preference` records exist for the seeded ideas, and the ideas of `student06`–`student15` count is zero;
  - the formal-application fixture is still present and reachable as in `TestingFormalApplicationFixtureTest` (group of `student01`–`student03` and submitted application at the fixed project ID);
  - running the seeder again (`seeder.run(new DefaultApplicationArguments(new String[0]))`) creates no duplicates: the idea, period and marker counts are unchanged.
- **Inactive `testing` profile unaffected.** Extend `TestingAccountsInactiveProfileTest` (profile `default`, bootstrap admin) or add a sibling test that sets the switch to `true` and still asserts no testing beans (`seedTestingAccounts`, `seedTestingFormalApplicationFixture`, `testingIdeasFixtureSeeder`, `testingAllocationPreviewSeeder`), no ideas, no testing accounts, exactly one user (the bootstrap admin), and no period or allocation records. The existing inactive-profile assertions keep passing with the switch unset.
- **Documentation matches behavior.** One of the tests above (or a short, named test) reads the switch the way the documentation says: `true` enables it, unset/empty/`false` keeps the full set. The behavior for any other value is asserted if the documentation states one. Then the Implementor compares `backend/DEV-GUIDELINES.md`, `.env.example` and `make help` output with the implemented names and defaults, and reports the result.
- Search the test sources for assertions on the fixture counts affected only when the switch is on, and confirm none run with it on except the new class. No existing assertion should need to change, because the default is unchanged; if one does, the default behavior changed and the ticket is not met.

Standard project checks:

- Frontend checks are not required if no frontend file changes; say so explicitly. No OpenAPI generation or frontend API type generation applies (no endpoint, model or validation change).

## Acceptance criteria (the Evaluator judges)

- With the `testing` profile and the switch unset or `false`, the data set is exactly the current one: five periods, ten accepted projects, supervision preferences, the formal-application fixture and the sample ideas. All existing fixture tests pass unmodified.
- With the `testing` profile and the switch enabled, the backend seeds all 22 testing accounts and the two sample ideas for each of `student01`–`student05`, and no application period, application, allocation run, finalization, period project group, accepted-for-applications project, supervision preference or period-related fixture marker. The period list is empty for administrators and students.
- The formal-application fixture is unchanged in both modes.
- With the `testing` profile inactive, the switch has no effect: no testing accounts, ideas, periods or fixtures are created.
- Restarting the seeder with the switch on is idempotent.
- `make run-testing-minimal` exists, appears in `make help`, and starts the testing profile with the switch on. `make run-testing` and `make run-backend-testing` keep the full set. `.env.example` and `backend/DEV-GUIDELINES.md` document the switch, its default, what is skipped and kept, and the local/testing-only warning, and match the implemented behavior.
- No production, API, authorization or frontend behavior changes; no `SPEC.md`, OpenAPI or frontend type changes; the Dev-09 labels are not implemented here.
- Standard: the standard project checks pass; existing behavior outside the stated scope is unchanged; no unrelated cleanups; generated files (such as `contracts/openapi.yaml`) are not hand-edited or committed; no check is claimed that was not performed.
