# Dev-59. Load TGM workbook preferences in a dedicated testing profile

## Intent

Provide `make run-testing-tgm` to explore real previous-year student preferences and mutually declared applying groups from the owner's local workbook in a disposable testing environment. Create the students, their classes, accepted projects and valid applications in one new application period, without changing ordinary testing fixtures or relaxing production application rules.

Owner-provided [Projekte_2026_27.xlsx](../../../docs/Projekte_2026_27.xlsx): use only sheets `4aHIT`, `4bHIT`, `4cHIT`, `4dHIT`; each is a class. Column A is the student's full display name, D/E/F are ordered project choices, and G–K are declared group members. The owner confirmed both clarifications:

- Create every student account, but import an application only for three valid, distinct preferences; report skipped applications by sheet/row, without inventing preferences or weakening validation.

There were no whitespace-stripped username collisions, and the longest resulting username was 22 characters. ## Scope and contract

### Startup, isolation and source handling

- **REQ-001 — Dedicated startup.** Add a root `make run-testing-tgm` target using the existing shared testing-stack lifecycle to start backend and frontend. Activate a dedicated `testing-tgm` Spring profile together with the existing `testing` support profile. Retain the standard synthetic teacher and admin accounts, their existing testing login behavior, and the draft rubric. Replace the standard synthetic student accounts and their ordinary student-owned sample ideas/projects with the students, classes, and project data imported from the workbook; do not seed the default `student01`–`student25` accounts or their minimal-mode sample ideas in this profile. Import only workbook-derived projects and related TGM application data, with exactly one TGM period. Use the existing minimal-fixture mechanism rather than deleting existing seed code. Keep `make run-testing`, `make run-testing-minimal`, direct ordinary testing startup and production behavior unchanged.
- **REQ-002 — Explicit isolation.** Only the dedicated mode imports TGM data. The target must deterministically select its profile/minimal-fixture state even when `.env` contains conflicting ordinary fixture flags. Disable incompatible optional allocation-pin, applying-group, eligible-project and Formal proposal search preview switches for this target, without changing their behavior in other targets. Direct activation of the dedicated profile must also suppress ordinary synthetic student accounts, their student-owned sample ideas, and ordinary project/allocation fixtures; do not depend solely on Make setting a flag. Preserve the standard synthetic teacher/admin accounts and draft rubric when the profile is activated directly. A configuration that cannot meet these requirements must fail explicitly before claiming readiness.
- **REQ-003 — Read the workbook locally.** Read the actual root `docs/Projekte_2026_27.xlsx` at startup, resolving it correctly when Gradle runs from `backend/`. Do not require a separate manual conversion, download, external service, or new dependency. Use the existing JDK ZIP/XML facilities for this bounded XLSX import; support workbook relationship-based sheet resolution, shared/inline strings and sparse cell coordinates, rather than assuming physical cell positions or sheet-file order. Disable XML external entities/DTDs. Read only the four named sheets and the requested columns; C and other sheets/columns are not project or student sources.
- Before writes, validate required sheet/header structure, student identities, username collisions, project mapping and structural workbook readability. Missing/unreadable/malformed workbook, missing required sheet, ambiguous identities, account conflicts or unsupported structure must fail startup with a clear path/sheet/row diagnostic and no partially imported TGM data. Do not silently use synthetic data, an embedded snapshot, cached stale data or guessed cell values. Application-quality exceptions confirmed by the owner are reported/skipped, not treated as structural workbook failures. Formula values in required data must not be evaluated or fabricated; an unsupported formula must receive an explicit diagnostic.
- The runtime workbook remains local and untracked; the application must not serve it or expose a new upload/import endpoint. Treat its names as private school data: no external transmission, public archive publication, plaintext credential/token logging or broad row dumps. Store only normal private authenticated account/application records. Parser tests use invented data, not a committed extract of actual students.

### Mapping and application rules

- **REQ-004 — Student accounts/classes.** For every genuine nonblank student-name row in A after the header, create a `{STUDENT}` account regardless of preference validity; skip blank and numeric summary rows, not students with blank D–F. In this profile the student accounts are the workbook-derived students, not the standard synthetic `student01`–`student25` accounts; the five standard synthetic teacher accounts and two standard synthetic admin accounts remain available with their existing usernames, roles and testing login behavior. Preserve the trimmed full display name and assign the class named exactly by its sheet. Login is the column-A name with all whitespace characters removed, preserving remaining spelling, case, punctuation and diacritics; do not transliterate or invent suffixes. Use the repository's existing testing-only default password, hashed by the existing password encoder. No real credentials are imported. Reject an ambiguous duplicate identity or conflicting login rather than merging students or overwriting another account. Reuse an existing account only when persistent fixture provenance proves it is this same imported student. No elective-subject inference or extra teacher roles.
- **REQ-005 — Projects and specification.** Create one distinct project for each exact trimmed, nonblank project title appearing in D/E/F across genuine student rows, including titles on rows whose applications are skipped. Deduplicate identical trimmed titles across classes; do not fuzzy-match, merge similarly spelled titles or infer additional projects from C/G–K. Create complete invented idea and full-specification text explicitly marked as local TGM testing content, retaining the source project title. Follow the existing idea/specification model, with the full specification accepted and project status `ACCEPTED_FOR_APPLICATIONS`; make the project usable in the application catalogue through normal services. Use existing synthetic staff as fixture authors/reviewers where necessary, preserving self-review restrictions. Do not assert real teacher authorship, supervision or historical project content. Here “proposal” means the pre-application full specification, not a post-allocation Formal proposal.
- **REQ-006 — Period.** Create exactly one TGM period labelled **Diplomarbeiten 2026/27**, school year `2026/2027`, containing every imported project. Restrict its eligibility to the four imported classes so ordinary synthetic students do not become allocation candidates. On fresh import, open it one minute before import time and close it seven days later, allowing immediate editing/allocation experiments; document that these are relative testing dates, not historical dates. Leave it `OPEN`: do not pre-run/finalize allocation, create finalized project groups, approve Formal proposals, seed grades or publish archives. Existing administrative early-run/deadline workflows remain available.
- **REQ-007 — Individual choices.** Resolve D, E, F in that order after trimming cell-edge whitespace. A valid application has three nonblank, pairwise distinct imported project IDs. Import it as submitted, using existing eligibility/time/validation rules. Blank/repeated/invalid choices produce no effective application for that student unless covered by a valid shared application under REQ-008; do not pad, duplicate, sort, guess, substitute projects or change the minimum-choice requirement. Report sheet/row and reason for each skipped ranking without names or raw cell contents.
- **REQ-008 — Shared choices.** Interpret nonblank G–K as a roster of 2–5 distinct students, including the declaring student. Resolve members across all four classes using their column-A display names, allowing only leading/trailing and repeated whitespace normalization; preserve case/spelling and do not fuzzy-match, reverse name order or infer aliases. Roster comparison is set-based (column order may differ); preference comparison is ordered. Every named member must resolve uniquely, declare exactly the same complete roster and have the same valid ordered D/E/F ranking. Only then create exactly one submitted applying group for that roster, with every member accepted and explicitly approved at its current revision in this testing simulation. Select creator and persisted member order deterministically from source sheet order (`4aHIT` through `4dHIT`) and row order; do not infer a real historical creator.
- Use the existing applying-group service lifecycle for invitation, acceptance, ranking, unanimous approval and confirmed submission; seeded consent is explicitly simulated local data, not a claim about actual student consent. Every member has exactly one effective shared application and no simultaneous eligible solo application. Keep applying groups separate from post-allocation project groups and Formal proposals.
- If a declaration has unknown/ambiguous names, duplicate members, excludes its own student, has invalid size, is nonreciprocal, overlaps inconsistently, or has differing/invalid member rankings, ignore that group declaration and report coordinates/reason. Do not silently choose another member's ranking. Import each member's valid individual application instead; retain no effective application for invalid individual rankings. A student may not participate in two submitted groups. Determine the full group plan before writing so row traversal cannot cause duplicate shared/solo submissions.
- **REQ-009 — Repeatability and failures.** Reinitializing the same dataset in the same database must not duplicate accounts, classes, projects, period, applications, groups or simulated lifecycle histories, reset passwords, reopen a period, extend its deadline, or overwrite subsequent user edits. Persist fixture ownership and workbook checksum only after successful import; retain stable mappings to source coordinates. Reuse a completed identical import without replaying writes. If the workbook changes against an already imported database, fail explicitly and instruct use of a fresh disposable database rather than merging or destroying user changes. Structural validation occurs before writes; import writes are transactional, and failures roll back TGM-created records without touching unrelated data. Clear temporary security context even on failure. Restarting a fresh in-memory H2 instance may of course recreate the dataset.
- **REQ-010 — Reconciliation and guidance.** Emit a bounded import summary of source checksum, per-class student counts, unique projects, valid/invalid rankings, imported groups, grouped students, effective solos and skipped declarations/applications. Counts must reconcile: every imported student has either one shared application, one solo application or no application; no double counting of shared members as solo submissions. Report skipped records by sheet/row and reason, never full roster/name lists or passwords. Update root `README.md` and `backend/DEV-GUIDELINES.md` with the exact command, prerequisite workbook path, isolated local/private use, default testing-password convention, login derivation/class mapping, relative period dates, skip/group rules, summary, repeatability and fresh-database guidance. Explicitly document that TGM mode retains the five standard synthetic teacher accounts, two standard synthetic admin accounts and draft rubric, but replaces the standard synthetic student accounts and their student-owned sample ideas/projects with workbook-derived data. Document unchanged ordinary full/minimal modes and that the workbook is not distributed with the application.
