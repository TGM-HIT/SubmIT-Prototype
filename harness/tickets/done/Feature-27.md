# Feature-27. Select Rubrics & progress projects by name and membership

## Intent

Teachers and students currently enter a project UUID in **Rubrics & progress** (`/grading`) before loading a project's grading record. Teachers should select projects as they do under **Formal proposal**; students should choose from the projects they belong to. Neither role should need to discover or type a project ID.

## Source

Owner request: "as a teacher und 'rubrics & progess': currently the project is selected by project id. Change it equivalent to the project selection under 'formal proposal'. As a student show a list of projects the student is in instead of the project id input box."

Inspected baseline: [GradingPage.vue](../../../frontend/src/features/grading/GradingPage.vue), [FormalApplicationPage.vue](../../../frontend/src/features/formal/FormalApplicationPage.vue), [API services](../../../frontend/src/api/services.ts), [Feature-26](Feature-26.md), and [Feature-22](Feature-22.md). All references are path-only.

## Scope and contract

### Selection requirements

- **REQ-001 — Teacher selection.** On `/grading`, replace the project-ID input/load controls for any account with `TEACHER` with the searchable, paginated project selection used by the teacher Formal proposal view. The comparison baseline is the existing `/formal-application` teacher list: hold the authenticated teacher, persisted proposals, supervisor assignments, query, filter and page size constant; change only the destination opened after selecting a result, from proposal details to that project's grading record. Reuse the existing teacher summary API, not the student-only roster API.
- **REQ-002 — Teacher browsing semantics.** Default to current confirmed supervision of the caller; allow clearing the supervised-only filter to browse every existing proposal. Preserve the baseline's trimmed, case-insensitive substring search across current project title, every allocated member's display name, period label and school year. Show those human-readable fields and localized proposal status. Apply filtering before pagination through the existing API; expose accessible previous/next controls and page/count information. The same retained query must work when the supervision filter changes. Selecting another teacher's project after clearing the filter is allowed.
- **REQ-003 — Student membership selection.** Replace the student project-ID input/load controls with a labeled project dropdown using the existing authenticated self-only eligible-project API. Load **every page**, including beyond the endpoint's default request size, before treating the list as complete. Include the caller's persisted finalized memberships across all periods, including a project with no Formal proposal or no recorded grades. Exclude preliminary-only allocations, unassigned projects and other students' groups. Options show current project title, period label and school year; no proposal is required to select a student project. Reuse existing endpoint membership and fallback semantics; do not infer membership from preferences or send a student-ID query parameter.
- **REQ-004 — Human-readable context and roles.** Teacher results, student options and the selected-project heading must not display project, proposal or period UUIDs in visible text or accessible names. IDs remain internal request/option values. Distinct periods must remain distinguishable even when titles repeat. `{ADMIN}`-only accounts retain their existing project-ID lookup, read-only grading and rubric-publication workflow; `{ADMIN, TEACHER}` accounts use the teacher selector and retain teacher grading controls. Do not request teacher summaries for student-only or admin-only accounts, or student eligibility/roster data for staff.

### Interaction, preservation and boundaries

- **REQ-005 — Selection lifecycle.** Initially show no project's grading data or project-specific mutation controls. A selection loads the current individual-grade, group-grade, metric and applicable final-grade reads for exactly that selected project. Student final-grade reads remain self-only. Clear or hide the previous project's histories, final grade, success messages and unsaved project-specific drafts when leaving it; never submit an old project's draft for a newly selected project. Show the selected human-readable context with its grading record, not proposal editing/review controls.
- **REQ-006 — Async and failure states.** Provide localized, accessible loading, empty, failed-load and retry states independently for selection lists and project records. An error is not an empty list. Retain the selected project after record-load failure and retry that project's reads. Disable conflicting selection, search/filter/page changes and project mutations while project loading or a mutation is pending; also ignore late responses after cancel, return, unmount or a superseding load. Do not display a partial mixed-project result or enable writes against a failed/unloaded selection. Preserve the existing explicit no-final-grade state for the specific final-grade `404` only; other read failures remain errors rather than success-shaped empty histories.
- **REQ-007 — Return, focus and refresh.** Provide a teacher return-to-list action and a student clear/change-selection path. Returning/clearing makes no mutation, hides the old record and discards its unsaved project-specific drafts. Preserve the teacher's committed search/filter/page state and restore focus to the selected result, or the list heading if it no longer exists; student clear returns focus to the dropdown. On successful selection, focus the selected-project heading. Successful existing grading/metric/final-grade mutations stay on the selected project, refresh its displayed record, retain browsing state, and leave focus on the initiating control or a stable success/record heading if that control disappears. Failed mutations retain the selected project's input for correction. Reselecting a project must load its current persisted record, not restore stale histories or another project's form values.
- **REQ-008 — Preserve grading and privacy policy.** This is project discovery/navigation, not a change to backend grading access, formal approval requirements, grade calculations, rubric versions, history, or mutation payloads. Students still see only their own individual grades and final grades, with no grading mutation controls. Teachers retain their existing authorized reads/writes; supervision filters discovery only, not authorization. Do not replace the separate student-ID fields in teacher assessment forms, redesign grade history/final-grade JSON rendering, add new grading pagination, or modify the Formal proposal lifecycle. Preserve the Formal proposal selector's own behavior if extracting a small shared helper/component.
- **REQ-009 — Localization and responsive access.** Add every new frontend-owned label, status, error, retry and accessible name to both English and German catalogs. Use native accessible controls or existing patterns, visible keyboard focus and clear labels. At desktop 1440x900 and mobile 390x844, selection, search/filter/pagination, selected context and errors must remain operable without page-level horizontal overflow or clipped action controls. User-authored names and backend error text are not translated.
- **REQ-010 — Related documentation and tooling.** Update the related selection, role, interaction and grading passages throughout [frontend/SPEC.md](../../../frontend/SPEC.md), with no contradictory project-ID instructions for teachers/students. Backend/shared product policy remains unchanged. Update the teacher and student `/grading` stages in [documentation scenario](../../../frontend/scripts/documentation/scenario.mjs) to select through the new controls instead of filling `#project-id`; preserve its authorized initial-final-grade preparation, rubric transitions, recorded assessments and privacy assertions. Review other grading-specific preview/documentation selectors and adapt only consumers actually broken by this change. Do not hand-edit ignored generated user guides.
