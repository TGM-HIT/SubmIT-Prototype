# Dev-61. Make rubric definitions self-contained JSON and downloadable

## Intent

Keep the draft grading rubric as editable versioned data rather than Java-defined assessment settings, and let authenticated users download any existing rubric version as a reusable JSON definition or readable Markdown document.

Dev-55 already stores the draft descriptors in `backend/src/main/resources/testing/grading-rubric-draft.json`. Its seeder still expands a fixture-only shared `assessmentScale` and injects `evidenceRequired: false` into every criterion. Complete that separation without changing the effective draft rubric or introducing a new rubric schema.

## Source

Owner request: save the Dev-55 draft as JSON rather than hard-coded backend content, and make existing rubrics downloadable as JSON and Markdown. Owner confirmed that JSON downloads should be reusable definitions for editing and publishing a new version, not database/API snapshots: exclude internal record IDs and publication metadata. Related ticket: [Dev-55](Dev-55.md).

## Scope and contract

### Self-contained draft definition

- Make `backend/src/main/resources/testing/grading-rubric-draft.json` a complete definition conforming to the existing `RubricDtos.PublishRubricRequest` structure. Store each criterion's scale and evidence requirement explicitly in the JSON; remove the fixture-only top-level `assessmentScale`. Keep all rubric-specific criterion content, applicability, scales, evidence settings, metric definitions, and configured rules in the resource, not Java constants or per-criterion mutations.
- Simplify `TestingDraftRubricSeeder` to read, validate, and seed that definition. Generic validation, testing-profile selection, immutable-version conflict detection, and system publication metadata remain backend responsibilities. Do not remove independent hard-coded test expectations: they verify source fidelity and are not runtime rubric definitions.
- Preserve the effective Dev-55 rubric: version `dev55-draft-testing-v1`, names, German wording, category/criterion IDs and order, descriptions/draft context, applicability, scale bounds/steps, optional scale labels, manual overall assessments, supplemental synthetic metric, empty aggregation rules, and effective period. Keep the existing testing-only boundary, repeat-startup reuse, explicit conflict failure, and default-profile absence. Do not modify the source DOCX, add an automatic grade formula, or replace historical assessment bindings.
- Compare the pre-change and resulting definition/API content as parsed structures: object-key order is irrelevant, array order is significant. For API snapshots only, omit top-level generated record `id`, `createdAt`, and `publishedAt` from cross-startup comparisons; do not normalize other values. Textual JSON identity is not required.

### JSON and Markdown downloads

- Add a rubric-version download section on the existing authenticated `/grading` page, separate from project selection and grade-entry controls. All existing rubric readers (`STUDENT`, `TEACHER`, `ADMIN`, including dual-role staff) can download both formats; publishing remains administrator-only. No anonymous/public-archive rubric download route is added.
- Reuse `GET /api/grading-rubrics` and `GET /api/grading-rubrics/{id}` with a typed frontend service method for the latter. Offer user-accessible pagination for version summaries, including previous/future-effective versions rather than only the active version. Label entries by human-readable name, version and applicability; retain internal record IDs only as request values. A page may be empty; failed loads must never masquerade as an empty collection.
- Generate both downloads in the frontend from the full definition returned for the requested version, not a list summary or whichever version is currently active. No new backend export endpoint or dependency is required. Downloading or browsing a historical rubric must not change the active rubric, selected project, grade form drafts, or an assessment's rubric binding.
- JSON must be a UTF-8 `.json` file with the publication-request shape: `version`, `name`, optional `schoolYear`, `effectiveFrom`, optional `effectiveTo`, `finalGradeScale`, `categories` with complete criteria, `metricDefinitions`, and `aggregationRules`. Preserve nested category, criterion, metric and rule IDs and rule-version numbers: those are definition identifiers, not database record IDs. Exclude top-level record `id`, `status`, `createdAt`, `publishedAt`, and `publishedBy`. Recursively omit null optional request properties, including absent descriptions, stages, bounds and scale labels; preserve false, zero, empty arrays and all non-null configured values. Do not invent missing values.
- The exported JSON must be acceptable to the existing publication validator after an administrator supplies a new unique version label. Do not silently rename versions, shift effective dates, publish on download, or make an existing version mutable. Document that publishing an unchanged existing version still produces the existing duplicate-version conflict.
- Markdown must be a UTF-8 `.md` document presenting the same definition in readable order: rubric name/version/applicability and final-grade scale; category headings/descriptions; every criterion's ID, name, description, subject, optional stage, evidence requirement and complete scale/labels; metric IDs/versions/descriptions/units/bounds; and configured aggregation methods, scopes, precision and criterion/metric weights. Show empty rules honestly without inferred formulas. Preserve authored content and draft labels; escape Markdown syntax where needed to prevent content from corrupting the document structure. Do not embed private assessment records, grades, teacher/student identities, publication/audit metadata, or raw HTML as application-rendered preview content.
- Give files safe, version-specific filenames and correct `application/json` or `text/markdown` media types. Localize download controls, status/error messages and Markdown structural labels in English and German; do not translate user-authored rubric content. Release temporary object URLs after download/unmount.
- Provide explicit list loading/empty/error/retry and per-download pending/success/error/retry states. Disable duplicate actions for a pending download, keep the page/version context visible, and ignore late list/detail results after page changes, logout or unmount. An old request must not download a different version or show its success against a newly browsed row. Successful downloads leave the user on the same rubric-list page with focus on the initiating control; failure preserves that context and announces the error; canceled browser saving must not mutate any server or form state.
- Keep the controls usable without page-level horizontal overflow or clipped actions at desktop 1440 × 900 and mobile 390 × 844, with semantic links/buttons, visible focus and keyboard-operable pagination/downloads.

### Documentation and boundaries

- Update `backend/DEV-GUIDELINES.md` to explain the self-contained fixture, generic seeder responsibilities, reusable JSON structure, and why JSON is used here: it matches the existing nested publication contract and keeps changeable rubric policy as data; JSON is not an immutable school-mandated format. Preserve the Dev-55 draft/source and no-invented-calculation caveats.
- Update the relevant rubric statements in `docs/SPEC.md` and `frontend/SPEC.md` for authenticated definition downloads, available versions and reusable-definition/privacy semantics. Inspect related rubric, role and privacy statements throughout each document so the result is consistent. Existing backend read/publication contracts remain unchanged; no backend API annotation or generated schema change is expected.
- Do not add a rubric import/file-upload UI, change grading or publication permissions, implement automatic calculation rules, alter the Dev-60 Templates feature, or expand testing fixtures outside what is needed to verify this ticket. No dependency on Dev-60 and no scope-gate allowance is required: all deliverables are in existing allowed source/resources, guides and SPEC paths.

## Acceptance criteria (the Evaluator judges)

- The draft resource is a complete JSON publication definition with criterion scales and evidence requirements stored explicitly; the runtime seeder does not inject rubric-specific criterion policy. The effective Dev-55 rubric and testing-only/idempotent/conflict behavior are preserved under **Self-contained JSON definition** and **Dev-55 preservation**.
- Every existing rubric version can be reached through user-accessible pagination and downloaded in both formats by the existing authenticated rubric-reader roles, including inactive versions beyond the first page. **Version browsing and exact selection** and **Roles and read-only isolation** verify this without expanding publication/grading permissions.
- JSON contains the complete reusable definition, excludes record/publication metadata, preserves nested definition identifiers, and is publishable after an explicit unique-version edit. It does not silently alter version or dates. **Complete JSON export** verifies the complete output and publication behavior.
- Markdown faithfully presents every part of the selected definition, including scales, metrics and configured rules, without inventing calculations or disclosing private records. **Complete Markdown export** verifies the complete readable output and escaping.
- Downloads retain the same list/project/form state and focus, have explicit pending/failure/retry feedback, ignore obsolete responses, and release browser resources. **Pending/error/focus/resource behavior** covers these outcomes.
- Both locales and named viewports remain readable and keyboard-operable; **Localization/layout** and the recorded manual walkthrough verify this.
- The named checks pass, documentation accurately distinguishes rubric data from generic backend logic, no unrelated cleanup is included, and no validation or walkthrough is claimed without evidence.
