# Dev-33. Remove deprecated API usage and prevent regressions

## Intent

Backend test compilation reports that `OpenApiContractTest.java` uses or overrides a deprecated API. Remove deprecated API usage from repository-owned frontend and backend code, including tests and developer tooling, and make the supported verification workflow detect its return. A passing suite with hidden deprecation diagnostics is not sufficient.

Source: user-reported compiler message, “OpenApiContractTest.java verwendet oder überschreibt eine veraltete API”, and the request not to use deprecated APIs in either module. Inspection found repeated Jackson `JsonNode.fields()` calls in that test; identify exact deprecated declarations with compiler/type evidence rather than assuming these are the only cause.

## Scope and contract

- Inventory deprecated API calls, constructors, inherited members/overrides and referenced types against the repository's actual Java 23 and locked frontend/backend dependency declarations. Cover backend production and test sources, frontend TypeScript/Vue production and test sources, frontend configuration and repository-owned JavaScript/Node preview/documentation tooling. Resolve overloads and aliases where relevant. Do not claim absence from a grep for `deprecated`, clean test output alone, or editor-only strike-through styling.
- Replace confirmed usage with supported non-deprecated alternatives available in the current dependencies. Preserve behavior, validation, authorization, serialization, iteration semantics, ordering where relied on, test setup and assertion strength. In particular, retain complete OpenAPI response/schema inventories, object/type guards, exact membership comparisons and baseline independence in `OpenApiContractTest`; do not remove coverage to remove a warning.
- Enable visible, detailed Java deprecation diagnostics for both `compileJava` and `compileTestJava`, including APIs marked for removal, and make deprecated usage fail the supported backend verification. Prefer compiler options scoped to deprecation/removal categories; do not make unrelated warning classes fatal merely to enforce this ticket. Run fresh compilation so an up-to-date task cannot conceal warnings.
- Add a repeatable frontend check using existing installed compiler/tooling capabilities that resolves references to deprecated declarations in owned TypeScript, Vue script and JavaScript/Node tooling. Include it in the documented frontend verification path and a normal existing verification command or root `make check`; it must not be an unmentioned optional script. TypeScript's `ignoreDeprecations` setting concerns compiler-option warnings and is not a substitute for detecting use of APIs tagged `@deprecated`. Use existing dependencies only; no new linter, plugin, browser stack or package upgrade.
- The frontend check must report actionable file/location and deprecated symbol information, and exit nonzero on findings or an inability to analyze an included source file. Correctly handle imported aliases and deprecated overloads without flagging non-deprecated overloads solely because another overload is deprecated. Use existing Vue/TypeScript facilities to analyze Vue script content; do not silently skip `.vue` files or `.mjs` tooling. If a current toolchain genuinely cannot analyze a required category, expose the exact limitation as a blocker rather than claiming complete coverage.
- Do not hide deprecations with `@SuppressWarnings`, `@ts-ignore`, `@ts-expect-error`, lint disables, warning filters, lowered compiler diagnostics, blanket exclusions or assertions that accept diagnostic failure. Do not modify `checkstyle.xml`. Exclude third-party dependencies, build/cache/browser-profile directories and ignored generated docs from owned-source scanning. Generated API types are not hand-editable: if they themselves introduce deprecated references, trace the generator/source cause and report a scope conflict rather than editing generated output.
- External dependency implementation warnings, Gradle/plugin deprecations and npm package-install advisory/deprecation messages are not proof of owned deprecated API calls. Record such diagnostics separately without suppressing them or performing unrelated dependency remediation. No dependency upgrades, product/API contract changes, fixture changes or source-wide modernization unrelated to verified deprecated use.
- Update `backend/DEV-GUIDELINES.md` and `frontend/DEV-GUIDELINES.md` minimally with the required deprecation checks, covered source categories and no-suppression policy. Add concise prevention guidance to `harness/roles/implementor.md` (use supported APIs and run the checks) and `harness/roles/evaluator.md` (independently verify diagnostics and reject suppression/coverage loss). Agent wrappers already delegate workflow to these contracts; do not duplicate those rules in `.github/agents/*.agent.md` descriptions or change tool permissions/model guidance.
- Scope-gate allowances: `backend/build.gradle` and `harness/roles/evaluator.md`. Other expected source/test/script/package/Makefile/development-guide and Implementor-contract paths are already allowed; do not add broad directory exemptions.
- Coordinate with open [Bug-21](Bug-21.md), which also touches `backend/build.gradle`, frontend package metadata and preview tooling. Neither ticket depends on the other's identity changes; preserve any already-landed changes and do not implement that ticket's rename scope here.
- Comparison baseline: HEAD immediately before implementation, with the same runtime/toolchain/dependency versions, inputs, stored records, API contracts and test scenarios. Vary only supported API substitutions and deprecation verification/guidance. Record the complete owned-source inventory and exact diagnostic commands before editing; leave historical tickets, run records and lessons unchanged. Do not inspect or edit the human-maintained root backlog file.

## Mechanical checks (the Evaluator re-runs)

Durable regression scenarios, integrated with existing test/verification commands:

- **P1 — Java production and test enforcement:** Freshly compile both source sets with detailed deprecation/removal diagnostics. In an isolated temporary fixture exercise the same configured verification path with a deprecated call in production and then test sources; both must fail with file/symbol evidence. Include an API marked for removal and a valid non-deprecated counterpart. Do not inject fixtures into the real application sources or leave them tracked. Normal owned backend sources must compile with zero deprecated-API findings.
- **P2 — Frontend resolved declarations:** Add tests for a direct deprecated call/type, aliased imported reference, deprecated inherited member and deprecated overload alongside a non-deprecated overload. Exercise TypeScript, Vue script and Node `.mjs` files through the check's public command/configuration path. Deprecated fixtures fail with precise diagnostics, supported equivalents pass, and an unreadable/unparseable in-scope file fails explicitly instead of disappearing from the inventory. Use isolated fixtures with local test declarations where appropriate; do not add production deprecated use for testing.
- **P3 — Scope and no suppression:** Verify all owned categories are included, including backend tests and preview/documentation scripts; third-party/build/ignored generated output is excluded without excluding normal owned sources. Assert checker failure propagates through the documented standard verification entry point. Inspect the scoped diff for suppressions, relaxed warnings or lost test assertions; none is permitted.
- **P4 — Behavior and contract preservation:** Run all existing backend tests, especially the complete `OpenApiContractTest`, and frontend application/preview/documentation-tooling tests. If deprecated JSON iteration APIs are replaced, retain or add focused cases for empty objects, multiple entries, nested schemas and order-sensitive comparisons where used. Compare complete freshly generated OpenAPI before/after, normalizing only random server URLs; regenerate frontend API types and verify byte-identical output. No authorized contract change is intended.
- **P5 — Guidance and agent ownership:** Compare documented commands and coverage with actual build/script wiring and P1-P3 outcomes. Verify Implementor/Evaluator contracts consistently require supported APIs and non-suppressed verification, while agent wrappers still delegate rather than restating workflow. Check every API identified in the initial inventory is replaced or explicitly reported as an unresolved blocker; no silent carve-outs.

Standard checks:

- From `backend/`: fresh `./gradlew compileJava compileTestJava --rerun-tasks` with the implemented deprecation/removal enforcement, `./gradlew test`, `./gradlew checkstyleMain`, and `./gradlew generateOpenApi`.
- From `frontend/`: the newly documented integrated deprecation check, `npm run preview:test`, `npm run typecheck`, `npm test`, `npm run build`, and `npm run api:types` after regeneration.
- Run the root verification entry point if modified to wire enforcement. Retain compiler/checker stdout, stderr and exit codes under the ignored run evidence directory; distinguish freshly executed checks from up-to-date tasks and third-party warnings.
- Format exactly the changed Markdown files before each commit and run `git diff --check`. No new dependencies or manual generated-file edits.

## One-time manual verification (in addition to automated tests)

- None. Compiler/declaration diagnostics, isolated negative fixtures and the existing public HTTP/frontend/tooling suites establish acceptance. No screenshot or human-only UI assessment is needed.

## Acceptance criteria (the Evaluator judges)

1. The reported test-compilation warning is resolved at its actual cause, and owned backend production/tests and frontend production/tests/configuration/tooling have no verified deprecated API usage under the current supported toolchain. Covered by P1/P2/P3/P5.
2. Standard verification rejects reintroduced deprecated usage in both modules with actionable diagnostics, including Java tests/removal warnings and declaration-resolved frontend aliases/overloads/Vue/Node cases. Analysis failures are explicit. Covered by P1/P2/P3.
3. Warnings are not hidden, source categories are not silently omitted, and dependency implementation or install warnings are distinguished from owned API usage without unrelated upgrades. Covered by P1/P2/P3/P5.
4. Existing behavior, test assertion strength, complete generated API contract and tracked frontend API types remain unchanged; no unrelated modernization, product policy or dependencies change. Covered by P4 and standard checks.
5. Minimal developer and owning-role guidance prevents recurrence without duplicating rules in agent descriptions; all applicable checks pass and no incomplete analysis is reported as success. Covered by P3/P5 and standard checks.
