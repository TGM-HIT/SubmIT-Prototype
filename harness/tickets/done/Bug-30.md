# Bug-30. Show meaningful audit events with timestamps, resources, and actors

## Intent

The original report described uniform "Recorded event" headings, missing timestamps, and "Resource - actor not supplied". Bug-29 has since established typed responses and verified real timestamps and identifiers in the administrator audit view. The remaining problem is meaningful presentation: staff should see what happened, the affected resource's name, and the actor's name and role, rather than having to interpret action codes and UUIDs.

The post-Bug-29 `AuditService` records `action`, `occurredAt`, `entityType`, `entityId`, and `actorUsername`; user events also record `actorId`, while system events use `actorUsername: SYSTEM` without `actorId`. The typed view renders these canonical fields. Existing records do not contain historical resource names, actor display names, or roles; resolving current data cannot establish those historical facts.

Owner feedback in `Bug-29-20261024-2031/human-acceptance.md` asked: "show the real data" instead of the elective-subject UUID, and "show the real user and role" instead of the actor UUID. The continuation log `Bug-29-20261024-2102/run.log` records the owner's instruction: "Yes, keep it in Bug-30 and finish evaluating Bug-29." On 2026-10-24, the owner accepted the recommendation: "event-time snapshots for new events, with explicitly labelled current-data lookups for older events where possible", replying "Yes, follow your recommendation." These are Bug-30 requirements; Bug-29 remains closed.

## Scope and contract

- Build on completed [Bug-29](Bug-29.md). Preserve its canonical fields and typed pagination, but extend audit recording, response enrichment, and presentation as specified below. This ticket deliberately supersedes its exact audit-property-set baseline by adding documented context fields; it does not reopen Bug-29 or change the group-member contract.
- Make `/admin` -> **Audit history** display, for every valid returned entry:
  - A readable action-specific description, such as "Elective subject created" or "User role changed", rather than one generic event title. Inventory the action codes actually emitted by the backend, including dynamically constructed actions, and provide matching English and German catalog entries for all current codes.
  - The recorded `occurredAt` date and time, formatted with the existing locale-aware timestamp helper and reacting to the selected account language. Do not substitute request time, render a date without its time, or alter the stored instant.
  - A readable resource-type label and actual resource name/title or meaningful domain description. UUIDs may remain secondary identifying information, but are not sufficient primary presentation when a label is available. For records without their own name (such as a review, grade, application, or allocation run), use its actual related project/period/rubric context and event kind, not an invented title or arbitrary unrelated record.
  - The actor's display name, recorded username, and localized role for user events. Show a localized "System" label for system events, without inventing a human role or treating the intentionally absent actor UUID as missing attribution.
- For new events, persist immutable event-time snapshots of the actor's display name and role and the resource label alongside the existing audit facts. Inventory every audit producer, including dynamic actions and the real scheduler path. Capture context in the audited operation's transaction; deletion/removal events must capture the label before the resource disappears. Labels for rename/change events describe the resulting resource state, except removals use the last available state. Never derive the actor's historical role from an account after a role-changing operation has already mutated it. Later account/resource renames, role changes, or deletion must not change an existing snapshot.
- For pre-existing events without snapshots, resolve current actor/resource data where it still exists, with an explicit localized "Current data; historical value unavailable" indication for each independently resolved context. Do not write these lookups back as historical snapshots. Where a referenced record is absent, unsupported, or has no resolvable label, show localized "Historical details unavailable", retaining recorded username and secondary identifiers as applicable. Do not invent past roles/names, substitute the viewer as actor, or hide the whole event because enrichment is unavailable.
- Extend `AuditEntryResponse` on both audit routes with optional non-null `actorDisplayName` (string), `actorRole` (existing role enum), and `resourceLabel` (string), plus required non-null `actorDetailsSource` (`EVENT_TIME`, `CURRENT`, `UNAVAILABLE`, `SYSTEM`) and `resourceLabelSource` (`EVENT_TIME`, `CURRENT`, `UNAVAILABLE`). Emit display name/role together for resolved user contexts, omitting both for unavailable/system contexts; omit `resourceLabel` when unavailable. System entries retain `actorUsername: SYSTEM` and omit `actorId`. Preserve the five existing required fields and optional non-null `actorId` with their values/UUID/date-time representations unchanged. Describe snapshot/current/unavailable semantics and property requiredness in backend annotations. Do not introduce an audit ID or guessed `eventType`, `createdAt`, `timestamp`, or `status` fields.
- Resolve context server-side within existing layering and access boundaries, without browser per-row lookup requests, unbounded collection reads, or N+1 queries. Enrich both audit routes consistently; do not require the teacher caller to access the administrator-only user catalogue. Resolve only safe identifying context, not grades, private feedback, credentials, or full resource payloads.
- Keep an explicit localized unknown-action/resource label that includes the original non-empty code when a future code is encountered. Unknown codes must not collapse to an indistinguishable "Recorded event" or produce missing-translation warnings. A genuinely unusable payload must surface a visible error through the existing error/retry pattern, not success-shaped rows made entirely of fallbacks.
- Preserve user-accessible pagination beyond the first 20 records. Refresh loads page zero; Retry repeats the failed page. After successful loading, show the requested records and correct page controls; empty and failed loads remain distinguishable. Retain keyboard focus on the initiating tab/Refresh/Retry control when it remains mounted, and use the existing pager's focus behavior. No new editor, mutation, cancel flow, or row-detail view is required.
- Keep both audit endpoints read-only and available only to authenticated teachers and administrators as specified in `backend/SPEC.md`; students and anonymous users must not gain audit access. Do not expose audit data in public archive responses or change which actions are audited. Keep existing user/catalogue administration behavior outside the audit presentation scope.
- Limit changes to audit recording/context resolution and the audited call sites needed to capture snapshots, response annotations/models, frontend service consumption, the audit view, localization, and directly related tests. Do not add new kinds of audited actions, rewrite legacy history, migrate global Jackson configuration, or redesign administration. No product specification, global seed-data, or dependency changes are required. Existing code/test paths are within the scope gate; no additional scope-gate allowances are anticipated.
- Regenerate and review the ignored `contracts/openapi.yaml` with `./gradlew generateOpenApi`, then regenerate and review tracked `frontend/src/api/schema.d.ts` with `npm run api:types`; commit the latter if changed. Never hand-edit either generated artifact.

## Acceptance criteria (the Evaluator judges)

- Real audited user and system operations yield usable fields through both HTTP audit endpoints and render meaningful actions, actual resource names/context, and actor names and roles rather than UUID-only descriptions (`realUserAndSystemEventsHaveUsableHttpFields`, `renders real audit response fields`).
- New context snapshots survive later renames, role changes and deletions; legacy context is explicitly current or unavailable without rewriting history or inventing historical facts (`eventTimeContextSurvivesLaterChanges`, `legacyContextIsCurrentOrExplicitlyUnavailable`).
- Both audit routes expose the documented typed context fields and omission semantics with bounded, privacy-preserving enrichment; existing canonical event fields and group-member schemas remain intact (updated `auditOperationsDocumentTypedEntries`, serialization scenarios, `contextEnrichmentIsBoundedAndPrivate`).
- Current actions/resource types, role labels, and provenance indicators have readable English and German labels; occurrence timestamps include date and time and follow the selected language; user-authored names remain unchanged (`audit action/resource localization coverage`, `renders real audit response fields`, `locale-aware audit occurrence times`).
- Future unknown codes remain identifiable, missing required data produces an explicit error, and a system event without an actor UUID remains valid (`unknown codes and malformed responses`).
- Later-page events, Refresh, Retry, empty/error states, and keyboard focus work as specified (`audit pagination refresh retry and focus`).
- Audit authorization, read-only history, public-archive privacy, and unrelated account/catalogue behavior are preserved against the post-Bug-29 baseline, holding the same callers, records, and requests constant while changing only audit presentation/response handling (`auditAccessRemainsRestricted`, public-archive privacy and existing administration regressions).
- Applicable project checks pass, generated artifacts are regenerated rather than hand-edited when necessary, no unrelated changes are introduced, and no check is claimed unless performed. The documented browser verification demonstrates readable events at desktop and mobile sizes in both languages.
