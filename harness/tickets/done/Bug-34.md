# Bug-34. Remove fixed allocation size ceilings without weakening optimization

## Intent

Starting an allocation after `make run-testing-tgm` fails with `Run error: at most 60 students are supported, got 113`. Support this school-year dataset and larger valid inputs without arbitrary student, application, or project count ceilings. Preserve the existing exact optimization and allocation rules rather than replacing the error with incomplete input, a heuristic result, or an impractically exhaustive traversal left unchanged behind larger constants.

## Source

Owner report, 2026-10-29: "Run error: at most 60 students are supported, got 113"; request: "Please make the allocation run unbounded (why is it limited?)".

Current-state references: `backend/src/main/java/ac/at/tgm/submit/allocation/AllocationLimits.java`, `AllocationOptimizer.java`, `AllocationService.java`, and `AllocationEngine.java` in the same package; completed [Dev-59](Dev-59.md).

The current exact optimizer opens subsets of viable projects, solves residual solo min-cost flow, and branches over indivisible shared units. Its documented exponential search is guarded by 60-student and 12-project constants. Project subset iteration also uses a fixed-width `long` bitmask. The service separately reads at most 61 application records and rejects a larger total before filtering submitted applications. These are implementation guards, not school policy or group-size rules.

The approved local TGM source contains 113 students, 33 projects, 7 submitted groups with 29 members, 58 submitted solos and 26 students without effective preferences. All eligible students, not just the 87 students with valid rankings, must remain candidates. Use the actual source only locally; no real student names, logins, rankings or rosters may enter tracked fixtures or retained evidence.

## Scope and contract

- **REQ-001 — No fixed count ceilings.** Remove fixed student/application/project count rejection throughout the optimizer and service input-loading paths. Do not merely raise 60 or 12, install another hidden configurable ceiling, truncate input, narrow eligibility, or bypass the limit only in the TGM profile. "Unbounded" means no application-imposed count ceiling for otherwise valid finite inputs, subject to available machine resources; it does not promise constant runtime or support for infinite data. Keep group sizes 3–5 and applying-unit rules unchanged.
- **REQ-002 — A suitable exact search.** Address the underlying enumeration strategy so the actual 113-student/33-project TGM run completes, rather than only removing its guard. Use plain Java and existing dependencies. Reuse existing flow/constraint logic where appropriate; do not require a particular new algorithm, external solver, service or library. Remove fixed-width subset assumptions, including the 63/64-project shift boundary. Preserve the exact existing objective priorities (including pin handling, assigned count, and ranked satisfaction), unit indivisibility, eligibility, no-preference zero satisfaction, deterministic output and result ordering. Do not silently downgrade optimality, discard candidates, or return a partial/incumbent result as completed. Preserve established deterministic tie-breaking for existing supported inputs; document any internal search change without inventing a new allocation policy.
- **REQ-003 — Complete inputs.** Load every relevant application, eligible student, pin, shared unit and catalogue project. For paginated traversal, use stable deterministic ordering and avoid skipping records as query membership changes. Filter effective submitted applications under existing rules; drafts/withdrawn rows must not trigger an obsolete total-record limit or become effective applications. Include every eligible account-only student once and every shared member once, without simultaneous solo eligibility. Reuse existing repository/service patterns; do not load a partial page and claim it represents the whole period.
- **REQ-004 — Preserve lifecycle and visibility.** Apply the fix consistently to administrator early runs, automatic deadline initial runs and post-deadline replacement runs. Preserve synchronous processing, immutable input/result snapshots, existing OPEN/ALLOCATED/CLOSED and finalization behavior, pin constraints, role/ownership checks, audit behavior and private projections. A genuine failure must retain the existing explicit FAILED/error behavior, not become a successful empty or approximate allocation. No new asynchronous job API, timeout policy, cancellation protocol, optimizer mode, or public response field is requested.
- **REQ-005 — Guidance and scope.** Update optimizer/limit comments and the allocation/testing guidance in `backend/DEV-GUIDELINES.md` to explain why the old guard existed, the new no-fixed-count behavior, and remaining computational/resource costs without promising unlimited performance. Change product specifications only if strictly necessary to align with these requirements, minimally and explicitly in the handoff; do not weaken optimization rules to make tests pass. No frontend source/UI redesign, workbook/importer edits, fixture count changes, new dependencies or namespace migration. Preserve the owner workbook bytes and its existing staging state; never include it in a commit.
- No public API shape change is expected. If backend API annotations, validation or models must change, regenerate/review OpenAPI and consumed frontend types using the normal commands; never hand-edit generated files. All expected deliverables are already within the scope gate's backend source/test, backend guidance and SPEC allowances; no temporary allowance is requested.
