# Feature-29. Move rubric browsing and authoring to a dedicated Rubrics page

## Intent

The grading page currently starts with the entire active rubric and administrator JSON-publication controls, with rubric-version downloads elsewhere on the same page. This pushes project grading below a large definition unrelated to the immediate assessment task. Add a dedicated **Rubrics** / **Rubriken** navigation entry for viewing, editing, uploading and downloading rubric definitions, and keep the grading page focused on project assessment.

## Source

Owner request: move the full rubric out of the top of the grading view into a new Rubrics/Rubriken menu. The owner confirmed that editing means editing a draft copied from an existing version or uploaded JSON, then publishing a new version without changing the original. All authenticated rubric readers retain browsing/download access; editing, uploading and publishing are administrator-only.

## Scope and contract

- **Navigation and separation.** Add authenticated `/rubrics` navigation labelled `Rubrics` in English and `Rubriken` in German, available to `STUDENT`, `TEACHER`, `ADMIN` and combined-role accounts. Set the correct page title and active navigation state and support direct navigation/reload through existing authentication guards. Move the full definition display, administrator publication editor and paginated version/download controls out of `/grading`; do not merely collapse the same full rubric at its top. Keep `/grading` as the existing route and retain its project selectors, assessments, histories, metrics and final-grade workflows. A compact applicable-rubric name/version and link to `/rubrics` is allowed; rubric-driven assessment controls still need their applicable definitions and must not be removed.
- **Read-only browser.** On `/rubrics`, show the active version context and a user-paginated list of all versions, including inactive versions, using the existing summary and exact-version detail APIs. View a selected version's complete configured definition: applicability, final-grade scale, categories, criteria, subjects, stages, evidence requirements, rating scales/labels, metric definitions and aggregation rules. Do not silently substitute the active version for a selected inactive one or invent calculation rules. Use readable version/name labels, not UUIDs. Detail loading, empty/no-active, not-found, failure and retry states must be explicit; absence of an active version must not prevent browsing existing versions or administrator authoring.
- **Local administrator draft.** Reuse the existing editable JSON-definition approach rather than require a new graphical rubric designer. An administrator may start a new draft or copy a selected version into an editable publication-request JSON draft. Clearly distinguish that draft from the saved immutable version. Copy the complete reusable definition, without publication/database envelope metadata; retain definition IDs, nested versions, effective dates, optional values and configured rules unless the administrator changes them. Require an explicit publication action and a unique version label under the existing backend validation; do not generate or silently change dates or activate a version merely by viewing, copying, editing or uploading.
- **JSON upload.** Add an administrator file-selection control that reads UTF-8 JSON locally into the draft; upload does not persist a file or publish a rubric. Accept the existing reusable JSON download/publication-request shape. Parse and validate the root/required shape before replacing a draft; malformed JSON or a clearly incompatible definition produces an actionable localized error and leaves the existing draft unchanged. Existing publication validation remains authoritative for domain constraints. Display and retain server validation/conflict errors with the editable draft so the administrator can correct and retry. Markdown remains a readable download format, not a required import format; DOCX/PDF import is out of scope.
- **Draft replacement and cancellation.** Starting a new draft, copying another version, or loading a valid file over an edited draft requires confirmation before discarding unsaved changes. Declining replacement or cancelling file selection leaves the draft unchanged and sends no mutation. Provide an explicit Cancel/discard action for the editor; cancellation clears only local draft/error state, preserves the selected saved version and returns focus to the draft-opening control or a stable authoring control if that trigger is gone. Opening an editor moves focus to it; completed file loading moves focus to the editable definition. Successful publication refreshes version pagination/active context from the API, selects and displays the newly published saved version, clears the submitted draft and moves focus to its detail heading. Do not assume a future-effective publication becomes active today.
- **Async isolation.** While publication is pending, disable duplicate submission and draft-replacement controls. Browsing another page/version must not overwrite an edited draft; require the discard decision before an action that would do so. Guard delayed list/detail/file-read/download/publish results across version/page changes, cancellation, navigation/unmount, logout and account/role changes. A result for an abandoned context must not replace the current definition/draft, expose a stale download, or show publication success. Losing `ADMIN` removes and clears administrator draft/file state. Keep appropriate focus and selection after failed requests and retries.
- **Downloads.** Move and reuse the existing JSON and localized Markdown export helpers, safe distinguishable filenames, complete per-version payloads, optional-property semantics, pending/error/retry feedback and browser-download handling. Downloads remain read-only, contain definitions only, and exclude internal publication metadata, assessments and identities. Preserve exports for every version, including later list pages and inactive versions, without modifying active context or a local draft.
- **Permissions and immutability.** Non-admin readers have no author/upload/publish controls; hiding controls does not replace existing backend authorization. Reuse `GET /api/grading-rubrics`, `/active`, `/{id}` and administrator `POST /api/grading-rubrics`. Published versions and past assessment associations remain immutable; this ticket adds no update/delete-version endpoint, server-persisted draft lifecycle, role, activation policy, or public rubric access.
- **Preservation baseline.** Use the implementation run's pre-change Git revision for comparative checks. Hold the selected project, actor roles, locale, rubric definitions/effective dates and saved assessment records constant; vary only the route/component owning rubric browsing/authoring and the new local draft/file interactions. Preserve existing grading authorization, project selection, criterion-driven forms, histories and version associations, and preserve complete JSON/Markdown definition output for equivalent selected versions.
- **Wire existing consumers.** Update affected application shell/router tests, rubric/grading component tests, the reusable rubric-pagination preview option, real-browser grading/rubric download regression and full-lifecycle documentation scenario to use `/rubrics` for rubric tasks and `/grading` for assessments. The existing `--seed-rubric-pagination-preview` option currently requires `/grading`; make it work for `/rubrics` and adjust its documented usage/tests without abandoning its existing fixture purpose. Keep documentation publication steps as UI actions on the new page, not direct API replacements. Update only directly affected instructions in `frontend/DEV-GUIDELINES.md`; keep generated user-guide output ignored and do not manually edit it.
- **Specifications and generated contracts.** Update `frontend/SPEC.md`, including the existing statement locating version downloads on `/grading`, and only necessary shared UI-workflow wording in `docs/SPEC.md`. Reconcile all related rubric-reader, administrator-publication, grading and immutability statements in those files without contradictions. Existing backend rubric contracts already support this workflow and must remain unchanged; no backend API or generated-schema change is required. If a necessary API change is discovered, report the unmet requirement rather than invent a new persistence/authorization contract.
- **Scope exclusions.** No new libraries or schema-generation tools; no in-place modification of published rubrics; no Markdown/DOCX/PDF import, automatic grade formulas, assessment migration, school-policy approval workflow, unrelated grading redesign, global fixture replacement, or changes to the draft rubric resource. Required deliverables are under the existing source/script/SPEC/developer-guide scope allowances; no temporary allowance is needed.

## Acceptance criteria (the Evaluator judges)

- **AC1 (T1, T7):** authenticated users reach a distinct `/rubrics` page through `Rubrics`/`Rubriken`; `/grading` no longer hosts the full rubric, publication editor or version/download browser and preserves its applicable assessment workflows.
- **AC2 (T2, T6):** all versions remain reachable through pagination and exact-version viewing/downloading, including inactive later-page versions; complete configured definitions and existing JSON/Markdown semantics are preserved.
- **AC3 (T1, T3, T4):** only administrators create/edit local drafts, load JSON and explicitly publish a new immutable version. Copied/uploaded content is editable without changing existing versions or past assessments; viewing, editing and uploading alone never publish or activate.
- **AC4 (T3, T4, T5):** cancellation and declined replacement preserve the specified saved/draft state; parse/read/server failures retain valid input and support correction/retry. Pending/stale operations and role/account changes follow the specified isolation, selection and focus behavior.
- **AC5 (T4, T7):** successful publication displays the newly saved version and refreshes current context without assuming it becomes active or changing historical assessment associations. Student/teacher/admin grading authorization and student privacy remain unchanged.
- **AC6 (T6, T8, manual checks):** actual browser download, navigation, keyboard, layout and documentation workflows work on the new page, in both languages and specified viewports, without weakened checks or generated-guide edits.
- **AC7:** the named SPEC/developer-guide statements consistently describe the new ownership and immutable draft-to-publication workflow; applicable checks pass, generated artifacts are not hand-edited, and no unrelated project behavior or harness/history is changed.
