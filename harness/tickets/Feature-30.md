# Feature-30. Grade all student criteria in separate routine and final assessment modes

## Intent

Selecting a student for assessment should show every gradable criterion, rather than a single criterion selector. Routine assessments made during project work start blank and save only entered grades. Final criterion assessment uses a separately selected rubric and loads stored final-assessment grades for editing. Routine observations must not be mistaken for final-assessment values.

## Source

Owner request: "Adapt the grading view: always show all critera (gradable) when selecting a student. Save only those that have been set."

Confirmed clarifications:

- Routine grading means repeated assessment during project work: blank grades on each new assessment, saving only populated rows.
- Final grading means editing each criterion's stored final-assessment grade, not merely editing the student's overall final grade.
- Each project has one independently selected routine rubric and one final rubric. Final entry loads only that project's saved final-assessment values under its final rubric; unassessed criteria stay blank. Do not initialize final rows from routine assessments.
- Production rollout uses a clean database with no existing assessments; no legacy-assessment migration is needed.
- Routine and final assessment are explicit teacher-selected modes. Final assessment may take place once work is finished but before formal project completion, respecting the existing requirement that final grading precede formal completion. No new project status is requested.

## Scope and contract

- **Dependencies and boundaries.** Implement after [Feature-29](Feature-29.md), which separates reusable rubric browsing/publication from `/grading`. This ticket changes student criterion entry and project-specific assessment configuration on `/grading`; it must not return the full read-only definition or publication editor to that page. It requires backend and frontend changes, not merely rendering many existing one-criterion forms. No changes to the accepted source ticket or ledger rows other than this ticket's normal lifecycle.
- **Independent project selections.** Persist independent `ROUTINE` and `FINAL` rubric-version selections per project. Teachers, including teacher/admin accounts, select published versions using human-readable name/version/applicability and all-page lookup or accessible pagination. Administrator-only accounts retain read-only grading; rubric publication remains administrator-only on `/rubrics`. Both selections start unselected on a clean project; explain the prerequisite and provide the selection controls before assessment entry. Neither selection silently defaults to the globally active rubric. A selected version must satisfy the existing effectiveness rules when newly bound; do not require two different version IDs, since independence does not mean they must differ. Changing one selection cannot change the other.
- **Binding and history.** Replace the existing single project-wide rubric binding assumption with phase-aware binding and recorded version transitions. Retain the existing explicit transition-reason requirement, maximum 2,000 characters, when changing a used phase to another version. Do not erase a used binding or reassign prior records to the new version. Historical assessments retain their phase, rubric ID/version, student, criterion, assessor and revision chain. An unused phase can remain unselected; a used phase cannot be cleared as a substitute for a transition. A same-selection save creates no new transition/audit event. Normal runtime history must remain intact even though no pre-rollout migration is required.
- **Student selection.** Replace the individual-assessment raw student-ID input with a labelled selector containing the selected project's actual allocated members, using their current display names and enough existing class/context information to distinguish them. Obtain members from an authorized grading read surface, not by guessing IDs, deriving membership from existing grades, or widening the student-only Formal roster endpoint. Empty, loading, failure and retry states must be explicit, and a member with no grade history must still be selectable. Preserve Feature-27's teacher project discovery and student self-only project selector.
- **All gradable rows.** For the selected student and mode, render all criteria permitting `STUDENT` or `BOTH` from the exact selected rubric version, grouped in configured category/criterion order. Exclude `GROUP`-only criteria from individual grade inputs. Include each row's readable identity, applicable description, configured scale/labels, evidence requirement and editable grade/evidence/comments; retain assessment date and explicit transition/revision reasons where required. No fixed criterion count, hard-coded 1–5 scale, hidden first-page-only rows, automatic grade, or inferred criterion mapping between rubrics. Render the entire set, with vertical scrolling allowed; provide a clear empty state if no criterion permits individual assessment.
- **Routine entry.** Opening a new routine assessment or successfully completing one starts with all grade values blank regardless of prior routine observations. A row is eligible to save only when a grade is explicitly chosen; do not coerce blank to zero or treat default dates as input. A wholly untouched row produces no request or record. Evidence/comments without a grade are incomplete input: show row validation and preserve it, rather than silently discarding it or inventing a grade. Validate all populated rows before sending any writes, including configured grade bounds/step, assessment date, text limits and required evidence. Saving valid selected rows appends new routine observations; it does not revise or overwrite older routine observations.
- **Final entry.** Load the current saved `FINAL` criterion values for this project, selected student and exact final rubric, including evidence/comments/date, using the full relevant history beyond the default page size. Show blank values for criteria without a final assessment. Routine assessments, another student's grades, superseded entries and entries from a different final rubric version cannot populate the editor. Save only newly populated or changed rows: create a final criterion assessment when none exists; use the existing history-preserving revision semantics for a changed saved row, requiring a nonblank reason within the existing 2,000-character limit. Maintain at most one current final row per project/student/rubric/criterion through initial creation, revision and fixture setup; concurrent creation/revision must not produce competing current rows. This restriction does not prohibit repeated routine observations. Unchanged rows create no revisions. Clearing a saved grade must produce explicit validation, not delete the record or persist a blank grade. A row without a saved grade may remain blank. Final mode is not a request to force completion of every criterion.
- **Save orchestration and failures.** Reuse per-row creation/revision services where appropriate; a new batch API is not required. Disable duplicate submission and project/student/mode/rubric replacement while writes are pending. Do not present an arbitrary sequence of writes as an atomic save. If using per-row requests, track each confirmed success and retain unresolved rows; report partial failure explicitly, refresh confirmed records and retry only unresolved rows, never replay known successful routine writes or final revisions. An ambiguous network outcome is not safe to retry blindly: reconcile against saved history before allowing retry, or report the unresolved outcome without claiming success. Conflicting revisions require refresh/reconciliation with preserved input, not silent last-write-wins. If an atomic batch is chosen instead, all-or-none behavior needs public-surface tests and annotations; do not mix the two guarantees.
- **End states and async isolation.** A fully successful routine save refreshes the selected student's history, clears submitted routine values for the next assessment and focuses an accessible save-result summary. A fully successful final save refreshes the editor from the saved final values/history and focuses its save-result summary. Failure retains unresolved input and focuses the summary/first invalid row with actionable feedback. Cancel discards only local changes after confirmation if dirty, restores blank routine inputs or saved final values and focuses the student selector; it sends no write. Switching student/project/mode/rubric with dirty input requires a discard decision; declining keeps the context and draft. Loading and failed reads must never display another context's editable grades. Ignore stale responses after reselection, unmount or account change; clear private drafts on logout/role loss. All interface strings are localized in English/German.
- **Connected grading surfaces.** Inventory and update `RubricBinding`, student creation/revision/history, group assessment, metrics, final-grade decisions/input snapshots, fixture creation and typed frontend clients so no consumer retains a hidden single-global-binding assumption. Existing group assessment and metric workflows remain routine-context workflows; this ticket does not add a final group-assessment grid or final metric-entry mode. The overall student/project final-grade controls remain distinct from final criterion assessment and use the project's final rubric. Maintain snapshot traceability to the actual phase/version of each considered input. Do not mix same-named criterion IDs from routine/final rubrics or automatically translate weights across definitions. Preserve existing explicitly configured rule evaluation and teacher-grade/rationale paths; if separately selected rubrics cannot satisfy a rule, show an actionable validation error rather than invent a cross-rubric calculation. Teachers can still consider routine observations through their documented rationale; no new final-grade formula or required weighting is authorized.
- **Lifecycle and permissions.** Retain Formal-proposal approval gates, allocated-membership checks, teacher-only grading mutations and student self-only individual read access. Both criterion modes are available explicitly to authorized teachers without requiring the project to already be marked complete. Keep formal completion's final-grade prerequisite and archive privacy unchanged. Do not turn routine/final mode selection into a new project lifecycle transition, grant administrator-only accounts grade mutations, or expose staff rosters/configuration mutations publicly.
- **API contract.** Add `GET /api/projects/{projectId}/assessment-rubrics` for authorized project grading readers and `PUT` on that route for teachers only, plus teacher/administrator-only `GET /api/projects/{projectId}/grading-members`. Do not widen the student-only Formal roster endpoint. Configuration responses include required nullable UUID `routineRubricId` and `finalRubricId`; PUT requires both keys with the same nullability and optional phase-specific transition reasons (nonblank when required, maximum 2,000 characters), so changing one selection must preserve the other explicitly. Member responses identify real allocated members with required UUID `studentId`, nonblank current `displayName` and available class context, never a global account list. Extend individual grade creation/history with a required non-null `assessmentType` enum `ROUTINE | FINAL`. Revisions inherit their original phase/version/student/criterion and cannot change them through request input. On `GET /api/projects/{projectId}/student-grades`, add optional `assessmentType` and UUID `rubricId` filters alongside existing `studentId`; omission means unfiltered history, not a phase default, and invalid supplied filters are rejected. Preserve existing individual creation/revision routes and self-only enforcement. Publish the final route/method/request inventory in the handoff and specifications; use typed DTOs and centralized client services instead of alternate UI-only state. Document required properties, nullability, UUID/enum formats and validation descriptions in both request/response. Keep each existing grade/date/evidence/comment/revision/transition constraint. A shared response used for group grades must report their routine context consistently, rather than ambiguously omit phase.
- **Contract generation and documentation.** Update backend annotations, regenerate/review ignored `contracts/openapi.yaml`, then regenerate and commit tracked `frontend/src/api/schema.d.ts`; never hand-edit generated files. Update all affected statements throughout `docs/SPEC.md`, `backend/SPEC.md` and `frontend/SPEC.md`: singular active/bound rubric assumptions, phase-specific assessment history, final criteria versus overall decisions, explicit selection and completion ordering must agree. Update directly affected backend/frontend developer-guide fixture/tooling descriptions. Keep the existing rubric publication/export definition reusable; project assessment phases are associations, not a reason to hard-code routine/final criteria into the draft rubric.
- **Clean rollout and fixtures.** No production data conversion, database deletion command, missing-phase-as-routine fallback, or legacy compatibility default is required. Update all assessment-producing test fixtures, testing seeders and documentation setup to write valid explicit phase/binding data, and verify tests asserting their inventories/current identities. Keep the ordinary draft rubric resource and 32 testing-account inventory intact. The optional grading-selection preview must still exercise its previous project selection/privacy cases, and must additionally provide separate routine/final rubric definitions with different scales/criteria, some saved final rows, an unassessed member/criterion and historical routine observations. Use synthetic testing-only definitions; do not treat them as school policy.
- **Preservation baseline.** Compare against the implementation run's pre-change revision (including completed Feature-29). Hold actor roles, allocated project membership, proposal approval, saved rubric content, grades and configured calculation inputs constant when checking unchanged non-target behavior; vary only phase-aware association and the new student criterion workflow. Preserve rubric immutability, read-only exports, project discovery, student privacy, revision history and unaffected group/metric/overall-grade operations. Required files are within existing source/script/SPEC/developer-guide scope; no new library or scope-gate allowance is required.

## Mechanical checks (the Evaluator re-runs)

Durable automated tests through public APIs/components and existing runners:

- **T1 — Independent bindings:** new project has two unselected phases; select distinct effective versions, reopen and verify persistence; also select the same version for both phases and prove separate histories. Test a rubric on a later lookup page. Changing one phase preserves the other. Test unused selection, same-value no-op/audit behavior, invalid/nonexistent/not-effective version, phase/rubric mismatch on assessment creation, used-phase clear rejection and recorded transition with required reason/length. Prior assessments remain on their exact phase/version.
- **T2 — Members and all criteria:** authorized staff member lookup returns all real members including one with no grades. Select by readable name/context, render the complete rubric in configured order, include `STUDENT`/`BOTH`, exclude `GROUP`-only inputs, and test heterogeneous scales, optional/mandatory evidence and no-individual-criteria state. Grade count must exceed 20 in at least one test. Test member/rubric/history read loading, empty, failure, retry and stale completion.
- **T3 — Routine saving:** historical grades never prefill a new routine grid. Save a subset and assert exact persisted rows/requests, untouched rows absent, optional zero preserved when valid, and fresh blank values after success. All-blank Save sends no writes and explains that nothing is selected. Evidence/comment-only row, out-of-range/off-step grade, future date, missing required evidence and text-length violations preserve input and cause no writes during prevalidation. A second routine assessment creates new history without superseding the first.
- **T4 — Final editing:** start with different routine and final rubrics sharing at least one criterion ID but different values; populate only exact final/student/version rows. Include relevant current entries after the default history page and superseded entries. New final row creates once; changed saved grade or evidence/comments produces a linked revision with reason; unchanged rows produce no writes; blank unsaved rows remain absent. Duplicate/concurrent final creation and competing revisions cannot leave multiple current final rows, while repeated routine creation remains allowed. Clearing a saved grade or omitting the revision reason is rejected without deleting history. Reload sees saved final values while routine mode is still blank.
- **T5 — Save recovery:** cover a middle-row failure after earlier confirmed writes (or atomic rollback if an atomic API is chosen), explicit success/failure counts, preserved unresolved input, retry without duplicating successful rows, ambiguous network completion reconciliation and stale revision conflict. Test duplicate-click and context-switch blocking while saving. No whole-form success notification on partial failure.
- **T6 — Context, cancel and roles:** test project/student/mode/version changes while dirty, accepted/declined discard, Cancel with no writes, focus and selected-context end states, stale reads/write feedback after navigation/unmount/logout, and role loss clearing drafts. - **T7 — Connected calculations and lifecycle:** routine group/metric writes do not replace the final binding; final criterion edits and overall decisions do not replace the routine binding. Exercise two different rubric definitions and same-version two-phase configuration; rule inputs cannot cross phase merely because IDs match. Retain configured-rule and manual-rationale behavior with exact input snapshots, actionable incompatible-rule failure, immutable prior decisions and approved-proposal gating. A teacher can perform final criterion assessment before formal completion, and completion still requires its existing final-grade/artifact prerequisites.

- **T9 — Contract:** public OpenAPI/schema tests assert complete required/nullable/property sets for changed request/response DTOs, phase enum, UUID selections/filters and inherited revision behavior. ## Acceptance criteria (the Evaluator judges)

- **AC1 (T1, T2):** each project has independent routine/final rubric selections; selecting a legitimate student displays all gradable individual criteria from the correct exact version, including students with no prior grades.
- **AC2 (T3):** routine entry is blank on each new assessment; only explicitly graded, valid rows are recorded as new observations, with no records for untouched rows or silent loss of incomplete input.
- **AC3 (T4):** final entry loads only stored final criterion values, supports new values and history-preserving revisions, leaves unassessed rows blank and creates no writes for unchanged rows. It never uses routine grades as initial final values.
- **AC4 (T5, T6):** save/cancel/retry and pending/stale operations have the specified visible data, draft and focus outcomes; partial/ambiguous writes cannot masquerade as success or be blindly duplicated.
- **AC5 (T6, T7):** teacher-only mutations, member validation, student self-only privacy, approval gates, completion ordering, routine group/metric workflows and overall final decisions remain coherent; two rubrics and overlapping criterion IDs do not merge phases or invent calculations.
- **AC6 (T8, T9):** all assessment-producing fixtures and consuming APIs/clients are phase-aware, generated contracts match validation/serialization and the documented clean-rollout design has no legacy migration/default dependency.
- **AC7 (manual checks, T2, T6, T8):** the documented preview and lifecycle workflows reach the new grading states in both languages and specified viewports, without bypassing selectors, removing assertions or editing generated guides.
- **AC8:** the three SPEC files and affected developer-guide descriptions consistently describe this workflow; required checks pass, Feature-29's page separation is preserved, and no unrelated cleanup or manually edited generated artifact is included.
