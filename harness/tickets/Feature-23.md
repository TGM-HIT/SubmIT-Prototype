# Feature-23. Select eligible students for application periods

## Intent

Application periods currently treat students with submitted preferences as the allocation pool. Administrators need to define which students may apply in each period, and allocation must include every eligible student even when they submitted no preferences. Staff and each affected student must be able to identify assignments made without preferences.

## Scope and contract

- Add administrator configuration to application-period creation and editing for the eligible cohort. The default is **All students** for new and existing periods, preserving current behavior. Administrators may instead select individual students, classes, or both. In selected mode, eligibility is the union of selected student IDs and students who currently belong to selected classes; overlaps count once. Class membership is evaluated when each allocation run snapshots its inputs, including early and replacement runs.
- Eligibility configuration may be changed until the period is finalized, including while applications are open or after an early run. Each run snapshots the resulting eligible student IDs and does not change if settings or class membership later change. Existing periods without stored eligibility configuration behave as **All students**; do not lose period, application, pin, or run data during migration/backfill.
- Extend the application-period request with optional `eligibilityMode` (`ALL_STUDENTS` or `SELECTED`, default `ALL_STUDENTS` for requests that omit it), `eligibleStudentIds` (UUID array), and `eligibleClassIds` (UUID array). The arrays default to empty. In `ALL_STUDENTS`, both arrays must be empty; in `SELECTED`, the eligible cohort is their deduplicated union, and empty arrays mean no students are eligible. Reject duplicate IDs, unknown IDs, and selected student IDs that do not identify current `STUDENT` accounts with `400`; malformed UUID values also return `400`. Do not impose an arbitrary array-size limit. Responses to `ADMIN` include the current mode and arrays (empty arrays for all-student mode); omit these three properties from responses to other roles to avoid exposing cohort membership. The response properties are optional and non-null when present. Document the enum, UUID formats, defaults, uniqueness and reference validation in backend annotations and generated OpenAPI.
- Keep the student and class selectors usable for every record beyond the default collection page: load all pages or provide accessible search/pagination. Use current display names and class names as labels, never UUIDs. The `All students` mode is explicit, and switching to selected mode allows choosing students/classes; switching back clears the selected cohort from the saved configuration. Show loading, empty, error, and retry states for lookup data; a lookup failure must not appear as an empty cohort.
- Eligibility governs who may apply and who can be allocated. An ineligible student's existing preference application remains stored and readable under current permissions, but does not enter a run; if the student becomes eligible again before allocation, the saved preferences can participate without being recreated. Ineligible students cannot create or update preferences while ineligible (`403`); existing withdrawal behavior remains available before the deadline. Eligibility never implicitly submits or restores an application.
- A submitted applying group's ranking is a preference application for every member. Creating or changing its ranking and submitting it require every accepted member to be eligible at that time; reject these group actions with `409` when the eligibility precondition is not met. If eligibility changes after submission, the whole group is excluded from a run until every member is eligible again; do not split, withdraw, or rewrite the stored group. Existing read, invitation, consent, leave, and withdrawal rules remain otherwise unchanged.
- Every eligible current student is an allocation candidate, whether or not they have preferences. Students without a submitted individual application are treated as having no preference ranking (zero preference-satisfaction contribution); allocation may assign them to any project in the period catalogue when feasible. Preserve the existing allocation objective: maximize assigned student count first, then rank satisfaction for students who have preferences, using existing tie-breaking behavior. Continue enforcing one project per student, feasible pins, immutable run snapshots, and group sizes of three to five; do not invent a final-grade or other scoring rule.
- Submitted applying groups remain indivisible. A group is eligible for a run only when every member is eligible at snapshot time; if any member is ineligible, exclude the entire submitted unit without splitting it. If all members become eligible again, the submitted unit may participate using its saved roster and ranking subject to existing lifecycle rules.
- Period eligibility applies to pins as well as applications: a pin does not make an ineligible student an allocation candidate. Retain existing pin records and behavior for eligible students; a previously saved pin can take effect in a later run if its student becomes eligible. Eligibility changes and class reassignment must not mutate prior run snapshots or results.
- Persist each new run's effective preference-submission state with its immutable assignment result. Authorized staff assignment entries expose optional, non-null `hadPreferences` (`true` for a saved individual or submitted shared ranking used by the run; `false` otherwise). The student period assignment projection exposes optional, non-null `assignedWithoutPreferences` for the caller only. Both fields are absent for legacy results where the immutable snapshot cannot establish the value; do not infer historical preference state from current applications. Show an explicit unavailable label for such legacy results. Do not expose other group members' preference-submission status to students, or expose rankings, class/cohort membership, optimizer internals, or pins through student results. Preserve current student and archive privacy boundaries.
- In the administrator application-period view, show and edit the cohort alongside existing dates, catalogue, status, and label. Non-admin period views do not show eligibility configuration. A successful create or update refreshes the visible period and saved configuration; focus moves to the updated period heading or row. Cancel makes no request, restores the saved configuration, and returns focus to the control that opened the editor. Preserve accessible keyboard operation and usable desktop/mobile layouts.
- In student application and group flows, clearly indicate when the current student is ineligible and prevent new preference submission or update; do not hide or erase a saved application. Preserve existing ability to read and withdraw that application. Do not permit a shared ranking change or submission unless every accepted member is eligible; return `409` for a group ranking or submission blocked by member eligibility. If a submitted group becomes mixed-eligibility because settings or class membership change, identify its exclusion in staff allocation results without splitting or rewriting the group.
- Update `docs/SPEC.md` (especially Student Applications and Group Allocation and Shared Invariants), `backend/SPEC.md` (application periods, applications, applying groups, allocation and student-class rules), and `frontend/SPEC.md` (period configuration, student application state and allocation results). Search all related eligibility, preference, class, pin, and allocation statements throughout each edited file; make them consistent and declare each changed SPEC in the handoff. Update developer guides only if their documented setup or behavior becomes inaccurate.
- Preserve the existing three-layer backend architecture and generated-contract workflow. Do not edit `contracts/openapi.yaml` by hand. Generate it from backend annotations, review the contract diff, and regenerate tracked frontend API types if affected.
- Out of scope: changing student class assignments or class catalogue management; changing preference minimums or ranking rules; splitting applying groups; changing existing pin authorization or finalization behavior; student access to another student's application; automatic translation; changes to grading or final-grade policy.

## Mechanical checks (the Evaluator re-runs)

Durable automated backend/API regression scenarios:

- **Default and persistence:** Public HTTP tests prove a newly created period that omits eligibility fields and a pre-existing period with no stored eligibility fields both behave as `ALL_STUDENTS`. Create, read, update and reload an administrator-selected cohort; include all-student mode, student-only mode, class-only mode, overlapping student/class membership counted once, and switching back to all students. Verify updates are rejected for finalized periods and do not partially change dates, catalogue, or eligibility when validation fails.
- **Eligibility input and authorization:** Verify malformed, duplicate, unknown class/student IDs and a selected account whose role is not `STUDENT` are rejected with the repository's documented validation status and no mutation. Only `ADMIN` may create/update eligibility; anonymous, student, and teacher requests receive their standard authentication/authorization outcomes. Verify all-student requests with nonempty ID arrays are rejected. Ensure non-admin application-period responses omit `eligibilityMode`, `eligibleStudentIds`, and `eligibleClassIds`, while administrator responses contain non-null values.
- **OpenAPI and generated types:** Assert both request and response schemas for the three eligibility properties, including enum values, request optionality/defaults, response optionality, UUID array item formats, non-null semantics when present, and validation descriptions. Assert the `hadPreferences` and `assignedWithoutPreferences` properties are optional and non-null when present on their respective response schemas. Run `generateOpenApi`, review the generated contract diff, and regenerate frontend types where consumed.
- **Application eligibility:** Through public APIs, an eligible student may create/update preferences and an ineligible student cannot create/update them. Exclusion retains the saved application and it remains readable and withdrawable before the deadline; restoring eligibility before a run makes the unchanged saved preferences eligible again. Verify another student's application remains inaccessible.
- **Run snapshots and class timing:** Verify a run includes every eligible student, including those without applications, and excludes ineligible students with saved individual preferences. Change selected classes/student assignments or eligibility after an early run and verify the earlier snapshot and result remain unchanged while a subsequent early/replacement/deadline run uses the new cohort. Include current class membership at run snapshot time and ensure role changes away from `STUDENT` do not introduce a non-student candidate.
- **Preference-free allocation:** With at least three eligible students without preferences and feasible catalogue capacity, verify they can form a valid assigned group on a catalogue project, contribute zero preference satisfaction, and do not reduce the assigned-student-first objective. Also cover fewer than three candidates (no undersized group), a mixed eligible/ineligible set, and pins: an ineligible pinned student is not assigned, while an eligible no-preference pinned student follows existing pin rules.
- **Applying-group indivisibility:** Verify ranking changes and submission are rejected while any accepted member is ineligible. Submit a valid group, then make one member ineligible before a run. Verify none of the group is allocated through that submitted unit, the saved group is not split or rewritten, and the result identifies the exclusion for staff. Restore eligibility for every member and verify the original unit can participate again. Include an otherwise eligible independent student to prove group exclusion does not exclude unrelated candidates.
- **Result visibility:** Staff run details identify each assigned student's preference-submission status and explain any mixed-eligibility unit exclusion. The affected student's own period projection identifies assignment without preferences. Legacy run results lacking immutable preference state omit the flag and render the unavailable label instead of inferring from current data. Verify students do not receive other group members' preference flags, rankings, eligibility IDs, pin data, optimizer internals, or class membership; anonymous archive responses remain unchanged.
- **Regression surface:** Update and run relevant public API tests in `ApplicationPeriodSupervisorTest`, `ApplyingGroupApiTest`, `AllocationEarlyRunApiTest`, `AllocationPinApiTest`, and `StudentPeriodAssignmentApiTest`, plus any new focused eligibility API tests. Preserve existing application validation, optimization, pin, early/deadline/replacement-run, group provenance, and privacy behavior for all-student periods.

Durable automated frontend regression scenarios:

- **Administrator configuration:** Test create and update in both eligibility modes, class/student union and deduplication labels, preserved all-student default, all-page lookup or accessible pagination beyond 20 students/classes, stale-value refresh, validation, lookup failure/retry, and that non-admins do not see controls or cohort data.
- **Interactive end states:** Verify successful create/update refreshes the period and focuses its heading/row; cancel sends no mutation, restores saved selections, and returns focus to its trigger. Verify keyboard operation and mobile layout without exposing UUID labels.
- **Student/group behavior:** An ineligible student sees a clear explanation, cannot submit or update preferences, retains access to read and withdraw a saved application, and can use it after becoming eligible again. A mixed-eligibility submitted group is not displayed as assigned or rewritten; preserve existing group editing and withdrawal behavior.
- **Allocation result labels and privacy:** Staff result rows clearly identify assigned students without preferences and mixed-group exclusion. Student result shows only the caller's own no-preference assignment indicator; verify other group members' status is absent from rendered text and API state available to the student.

## Acceptance criteria (the Evaluator judges)

- New and existing periods default to all students; an administrator may configure a selected cohort using individual students, classes, or both, with current class membership evaluated per run and overlapping membership counted once.
- Only eligible students participate in allocation. Saved individual preferences remain stored during exclusion and can participate again if eligibility is restored before a later run. Eligible students without preferences are allocation candidates and can be assigned to any feasible catalogue project without inventing a preference rank.
- Allocation still maximizes assigned student count before rank satisfaction, honors existing pins for eligible students, preserves immutable early/initial/replacement snapshots, and never violates one-assignment or 3–5 group-size rules.
- A submitted applying group is included only when all of its members are eligible at snapshot time. Mixed-eligibility groups are excluded whole, remain unchanged, and are never split; unrelated eligible candidates continue to be allocated.
- Staff can identify assigned students without preferences and mixed-group exclusions. Each student sees only whether their own assignment was made without preferences; preference status, class membership, eligibility configuration, pins, and optimizer internals for other students remain private.
- Administrators can create and edit eligibility configuration until finalization; other roles cannot configure it or see cohort membership. Forms provide accessible all/selected choices, complete lookups, clear loading/error/retry states, and the specified success/cancel focus behavior.
- Existing all-student application, group, pin, early/deadline/replacement allocation, result privacy, and archive behavior remain unchanged. The three named SPEC files are consistent with the implementation, generated API output is derived from annotations, and all standard project checks pass.
