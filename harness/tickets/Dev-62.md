# Dev-62. Establish atomic SPEC-to-test traceability

Refined from Compliance-02-20261101-1603 after Evaluator pass 4; implementation is limited to the scope below.

## Intent

The Compliance-02 report's earlier assertion that archive safety was the only uncovered requirement was unsupported. The replacement atomic inventory identifies many constraints for which this audit did not establish an exact asserting test. ## Mechanical checks (the Evaluator re-runs)

Durable automated tests (join the build):

- **M1 - Inventory integrity (`check-spec-test-traceability.mjs`):** validate the documented record schema, unique IDs, classification/status combinations, exact current source excerpts/ranges, coverage of substantive source passages by clause/disposition records, historical-row reconciliation, derived totals, and resolvable local finding/ticket links. For `covered` rows require existing test files, exact Java method or Vitest title locators, and setup/assertion excerpts that occur within the cited test rather than elsewhere in the file. Reject class-only/missing evidence and structurally combined clause records. Do not claim that syntax checks prove semantic atomization, complete normative extraction, or that a quoted assertion proves a requirement; those judgments remain the explicit M2 review.
- **M2 - Independent semantic reconciliation:** the Evaluator checks the complete three-file source-to-inventory mapping, the historical Finding-4 dispositions, and every `covered` row's actual setup/assertion sufficiency. Verify descriptive facts and scope exclusions do not inflate uncovered totals, substantive prohibitions remain included, and passing examples are not extrapolated into other roles, boundaries, concurrency, or UI states. Record this source-level review in the evaluation; no automated semantic oracle or passing-suite count substitutes for it.
- **M3 - Validator fixtures (`spec-test-traceability.smoke.mjs`):** using temporary isolated fixtures, prove a valid atomic record and allowed multiple-clause reuse of an exact test pass; duplicate IDs, structurally grouped IDs, missing source dispositions, absent test method/title, stale or moved source excerpts, missing/wrong-method assertion excerpts, invalid status combinations, and uncovered rows without a linked finding fail with actionable diagnostics and nonzero exit. Prove descriptive/scope-exclusion dispositions do not inflate normative counts while a genuine prohibition remains normative. Prove a correctly linked unresolved/delegated row passes without being counted covered. These fixtures test machine-checkable rules; semantic overclaims are judged in M2, not promised as automatic natural-language detection.
- **M4 - Gap regressions and honest findings:** each new passing regression names its clause ID and asserts the exact relevant boundary/failure/authorization or UI state through the existing public surface. For a demonstrated behavioral failure, verify the durable finding includes the expectation, controlled setup, actual result, reproducing command and evidence reference, and the inventory does not mark it covered; do not weaken the assertion or merge a failing/disabled test to obtain a green suite.
- **M5 - Artifact completion preconditions:** first search current tests, including `ArtifactServiceTest` and `ProjectWorkApprovalApiTest`. Require independent cases with an authorized teacher, active project, approved formal application, final grade present, and every other completion prerequisite met, omitting each required artefact type (`WEBSITE_ARCHIVE`, `POSTER`, `SOURCE_DATA`) in turn. Assert completion rejection and unchanged project state, and retain an all-types-present allowed control. Existing both-missing/final-grade-missing assertions alone are insufficient; if new coverage is needed, exercise `POST /api/projects/{projectId}/complete`. If behavior fails, use M4's finding disposition.
- **M6 - Historical rubric-version preservation:** first search current tests, including `GradingServiceTest.otherRubricVersionRequiresExplicitTransition` and current grading HTTP tests. Identify an assessment created under version A; perform the supported publish/selection transition to B with an authorized actor and query assessment history through the public API. Assert that same assessment's identity, A association, grade, criterion and recorded evidence remain intact, while a permitted new B write uses B. Transition/new-write assertions alone are insufficient. If behavior fails, use M4's finding disposition.
- **M7 - Preservation and tooling integration:** verify `npm test` runs both the new fixture tests/validator and existing Vitest suite, and documented commands match the package scripts. Compare the implementation diff against its entry revision: the three SPEC files, production backend/frontend runtime files, generated artifacts, archived evidence, and unrelated ticket/ledger content are unchanged. Validator fixture roots contain an excluded-path sentinel and prove bounded discovery does not open/traverse it; use synthetic paths, not the actual excluded content.

- **AC1 (M1, M2):** every current normative SPEC clause has an atomic record, with exact method/setup/assertion evidence or a linked durable non-covered disposition. Descriptive statements and scope exclusions have reasoned dispositions without inflating normative totals; substantive prohibitions and preconditions remain included. - **AC2 (M1, M2, M4):** every historical Finding-4 row is reconciled against current text/tests, distinguishing overlooked assertions, new passing tests, unresolved test gaps, demonstrated failures, delegated work, and obsolete/reclassified clauses. Each is backed by an exact passing assertion or a durable reproduced-failure finding, not merely the original insufficient test.

API, metric, architecture, transaction and frontend obligations are separately traceable without extrapolating unrelated behavior.
- **AC5 (M1, M3, M7):** the validator rejects the specified structurally invalid fixtures, accepts valid classified/non-covered records with honest counts, and reports actionable errors. Its machine-checkable guarantees and required semantic review are documented separately. Validator/fixture tests and new passing regressions run through existing builds.
