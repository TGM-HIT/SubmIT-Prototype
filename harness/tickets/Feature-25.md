# Feature-25. Allow teacher and administrator roles on one account

## Intent

Each account currently has exactly one role. A user who needs both teacher responsibilities and administrator capabilities must use separate accounts, and role-specific permissions and UI treat `TEACHER` and `ADMIN` as mutually exclusive. Allow one account to hold both roles while preserving the separation between student accounts and staff accounts.

Product-owner decisions (2026-10-22): a user with both `TEACHER` and `ADMIN` receives the combined permissions of both roles, including grading; `STUDENT` remains mutually exclusive with either staff role. Represent account roles as a list. When roles change, the new permissions take effect at the user's next sign-in; already-issued JWTs retain their role claims until expiry.

## Scope and contract

- Support exactly these account role sets: `{STUDENT}`, `{TEACHER}`, `{ADMIN}`, and `{TEACHER, ADMIN}`. Every account has at least one role. Reject an empty role list, duplicate role values, and any combination containing `STUDENT` with another role. Preserve registration's existing behavior: every new account is `{STUDENT}`, regardless of any optional submitted roles.
- Persist all roles for an account. Convert every existing account's current singular role to the corresponding singleton set without losing its identity, credentials, display name, student class, or elective subjects. Apply the same role-set model to registration, bootstrap administrator creation, testing-profile accounts, and administrator role changes.
- Make `roles` the canonical account representation in API request and response models, including login/token user data, user-list results, role-change requests, and the user role filter's result membership. Replace singular account `role` fields in those models; do not maintain competing singular and plural account-role representations. Retain the existing optional scalar `role` query parameter for filtering and define it to match any account whose role set contains that role. Registration remains student-only and continues to ignore supplied roles.
- Keep role-set persistence and last-administrator enforcement transactional. Continue recording role changes in the audit history, with the resulting role set accurately represented by the account response.
- Issue JWTs with a `roles` claim and grant every authority in the claim. Continue accepting unexpired existing JWTs that contain the former singular `role` claim as a singleton role set. A successful role change updates the account and response, but does not alter claims in already-issued tokens; after sign-in, newly issued tokens carry the updated role set.
- Authorize operations by membership in the caller's role set, not by equality with a single role. A `{TEACHER, ADMIN}` account receives the union of teacher and administrator permissions throughout backend endpoints/services and frontend routes/navigation/views. In particular, it can perform teacher grading, teacher idea and formal-application reviews, teacher archive publication review, and administrator account, catalogue, allocation, rubric-publication, and other administrator operations. An `{ADMIN}`-only account remains unable to perform teacher-only grading or decisions; a `{TEACHER}`-only account remains unable to perform administrator-only operations.
- Preserve student-only application and applying-group capabilities. A `{STUDENT}` account retains student access and the other three supported role sets cannot acquire student capabilities. Staff handling of student-owned resources continues to follow existing ownership and resource authorization rules.
- Preserve the last-administrator invariant using set membership: a role change must not remove `ADMIN` from the last account that has it. A dual-role account counts as an administrator, and removing `ADMIN` from it is allowed only if another account retains `ADMIN`.
- In account management, show all assigned roles and allow administrators to select the supported role sets. The student choice is exclusive; teacher and administrator choices may be selected together. Continue to show and manage class/subject details only for student accounts, preserving the existing default-class behavior when an account gains `STUDENT` without an assigned class.
- Preserve the account editor's success and cancel behavior: a successful role save refreshes the visible account list, closes the modal, and restores focus to that account's Edit control; cancel and Escape close without saving and restore focus to the same control.
- Preserve the role-change endpoint's existing `200` success status and `409` last-administrator conflict status. Invalid role-set payloads return the repository's standard validation error response and do not change persisted roles.
- Update `docs/SPEC.md`, `backend/SPEC.md`, and `frontend/SPEC.md` to define the role sets, student/staff exclusivity, combined permissions, representation, and next-sign-in token behavior consistently. Inspect all role, account, authorization, and staff/student references throughout each named specification for contradictions; make no unrelated specification changes. Regenerate and review the generated OpenAPI contract and frontend API types as required; do not hand-edit generated artifacts.

## Acceptance criteria (the Evaluator judges)

- Accounts persist one of the four allowed role sets, and all existing singleton accounts and their non-role data remain intact across initialization.
- Account role API data uses `roles` consistently; registration remains student-only, legacy unexpired singular-role JWTs remain accepted as singleton roles, newly issued tokens grant the stored set, and role changes remain audited.
- The user role filter matches membership, including dual-role accounts. Empty, duplicate, unknown, and student-plus-staff role assignments are rejected without partial changes.
- A dual-role account receives the combined teacher and administrator permissions, including teacher grading and teacher review decisions; an admin-only account does not gain teacher-only permissions, and a teacher-only account does not gain administrator-only permissions.
- Student capabilities remain exclusive to `{STUDENT}`. The existing default-class behavior applies when an account gains `STUDENT`, and class/subject assignment data remains intact through role changes.
- The last account with `ADMIN` cannot lose that role; a dual-role account may lose `ADMIN` only when another account retains it and continues to have teacher permissions.
- Account-management UI supports the allowed role sets and shows combined roles; a successful save refreshes the list and restores focus to the row's Edit control, while cancel and Escape do not save and restore focus. Navigation and role-gated views expose the union to dual-role accounts without granting restricted capabilities to single-role accounts.
- Role changes retain the existing `200` success and `409` last-administrator conflict statuses; invalid role sets use standard validation errors and leave account state unchanged.
- The three named specifications consistently describe the new behavior. API documentation is regenerated and reviewed, and tracked frontend types are regenerated and reviewed when changed.
- Standard (all tickets): existing behavior outside the stated scope is unchanged; no unrelated cleanups; generated artifacts are never hand-edited and are regenerated and reviewed when applicable; commit generated output only when repository tracking conventions require it; no check is claimed that was not performed.
