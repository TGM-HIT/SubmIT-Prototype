# Feature-02 Evaluation 1

**Verdict: revise**

**Reviewed range:** cumulative diff from baseline `16864c1d95d2a03a2af5047d75604030abd76902` through implementation commit `456ec95960832de4bb9efe3bbe479c605560bdec`.

## Summary

The implementation is well aligned with the feature and the checks I reran pass. The backend code uses the same name-normalization function for registration and updates, and the UI wiring appears to update the authenticated state and admin list correctly. However, two API test assertions do not distinguish important required behavior: the PATCH tests never submit a padded valid name, and the user-list test gives the account the same username and display name. The ticket requires durable tests for the changed behavior; these cases could pass even if update trimming were omitted or the list populated displayName from username. This is an actionable test-only gap, so the verdict is revise, not awaiting-human.

## Acceptance criteria and evidence

1. **Registration validation and persistence — established.** `AuthService` trims and validates names by code point before saving. `AccountNameControllerTest` exercises registration through the public API with an outer-whitespace name, checks the trimmed response and subsequent login, accepts 120 characters, and rejects missing, blank-after-trimming, and 121-character values. The registration test also confirms the supplied ADMIN role is still ignored.

2. **Name in registration, login, update, and administrator list responses; unrelated account fields unchanged — implementation established, test evidence incomplete.** `AuthService.toResponse` maps `UserAccount.displayName` to `UserResponse`; registration and login tests use a name distinct from the username, and update tests check the response. `UserRoleControllerTest.administratorUserListIncludesAccountNames` checks a `displayName` property, but its fixture uses `username` as `displayName`, so it does not prove that a distinct saved account name is returned. Update tests also do not submit a padded valid name and assert that both response and persistence contain the trimmed value. See finding F-1 below. The administrator update test checks username, password hash, and role remain unchanged.

3. **Self-update and administrator authorization — established.** The new controller delegates to server-side checks in `UserService`. `AccountNameControllerTest` exercises self-update as STUDENT, TEACHER, and ADMIN, cross-account denial for a teacher, administrator cross-account update, and unauthenticated rejection; it also checks the denied target name remains unchanged. The existing role endpoint remains separate and administrator-only.

4. **Seed accounts and testing-profile boundary — established.** Testing-profile configuration assigns stable student and teacher names, and the bootstrap admin receives `Administrator`. The configuration test checks the seeded names, login responses, and idempotence; the inactive-profile test checks that workflow fixture accounts are absent while the bootstrap admin name is correct.

5. **Authenticated shell, profile editor, admin editing, save/cancel/error state and focus — established by implementation and reported manual evidence.** `AppShell.vue` displays the current name and mounts the shared editor without role gating; the editor sends updates, emits the updated account, retains the draft on errors, and restores focus after save/cancel. Admin rows render names and replace the row state after save. Frontend tests cover registration submission, editing for each role, successful-save event/focus, cancel without save/focus, error input retention, and administrator edits to another account without changing username or role. The handoff reports student and teacher profile interactions, navigation away/back, focus checks, and admin changes; see manual-verification note below.

6. **No public archive exposure and preserve existing role behavior — established by diff and regression checks.** The change adds a dedicated account response field and update endpoint; it does not alter public archive DTOs or publication/redaction code. The role endpoint and its access logic are unchanged, and the backend test suite passes.

7. **All three SPEC files — changed and accepted.** The handoff declares all three changes as `SPEC CHANGE:`. `docs/SPEC.md` minimally documents the shared account-name rule, validation, permissions, and visible names. `backend/SPEC.md` adds the user API and response/validation/fixture details. `frontend/SPEC.md` documents registration, per-role self-editing, admin user-management editing, immediate visible updates, focus, and error retention. They are necessary for this ticket, consistent with code and acceptance criteria, and do not weaken existing requirements.

8. **OpenAPI and generated frontend types — established; ignored artifact caveat is compliant.** I reran `./gradlew generateOpenApi`, inspected the generated PATCH operation, 200/400/401/403/404 responses, request schema, and required `UserResponse.displayName`. `contracts/openapi.yaml` is ignored by the repository, so it is not in the commit diff; the ticket asks that it be generated and reviewed, not that an ignored file be forced into version control. I then reran `npm run api:types`; it completed and produced no tracked change to `frontend/src/api/schema.d.ts`, whose generated types include the new name/API fields. The generated artifact was not manually edited.

9. **Automated and standard checks — pass.** I forced backend execution with `./gradlew test checkstyleMain --rerun-tasks` (success). Frontend `npm run api:types`, `npm run typecheck`, `npm test` (10 files, 35 tests), `npm run build`, and `npm run preview:test` (15 tests) all passed. `git diff --check` on the cumulative baseline-to-implementation range passed. The earlier ordinary Gradle test invocation was up-to-date; the forced rerun above is the result relied on here.

## Required revision

**F-1 — Add discriminating API regression assertions.** In `AccountNameControllerTest`, PATCH a valid name with leading/trailing whitespace and assert the returned and persisted name is trimmed. In `UserRoleControllerTest.administratorUserListIncludesAccountNames`, give the target a display name different from its username and assert the returned `displayName` is the saved display name while `username` remains the login name. Current tests use only unpadded successful PATCH values, and the list fixture uses identical username/name values, so neither assertion proves the specified distinction. Keep the change focused on these tests; the implementation path itself appears to call the shared normalizer and response mapper correctly.
