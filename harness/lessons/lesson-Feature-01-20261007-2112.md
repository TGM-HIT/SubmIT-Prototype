## Proposal 1: The agent shims contradict the role contracts

What prompted it: the run's closing report said `Outcome: stopped` and `Ledger: unchanged` were "the nearest values the format allows" for a paused run. The block in `.github/agents/orchestrator.agent.md` lists only `done|failed|stopped` and `done|failed|unchanged`, and it has no `Follow-ups` line. The contract in `harness/roles/orchestrator.md` requires `awaiting-human` for both fields and a `Follow-ups` line. The Orchestrator followed the shim. The Implementor shim has the same drift: it lacks the rule that `harness/plan.md` and `harness/runs/` are expected to be dirty, the no-op/resolved-finding reporting rule, and the `OUT OF SCOPE:` convention. Handoff-1 then listed "`harness/plan.md` shows a modification that is not mine" under "What's uncertain", which `harness/roles/implementor.md` forbids.

Recommended edit: replace the duplicated procedure in `.github/agents/orchestrator.agent.md` and `.github/agents/implementor.agent.md` with a short identity paragraph plus an instruction to read and follow `harness/roles/<role>.md` as the sole source of the procedure and the return format. Apply the same change to `evaluator.agent.md` and `learner.agent.md` if they also duplicate their contract. If the shims must stay self-contained, copy the machine-readable block and the dirty-harness-paths rule verbatim from the role files and add a sync note to the shim.

Owning document: `.github/agents/orchestrator.agent.md` and `.github/agents/implementor.agent.md`, with `harness/roles/*.md` as the single source of truth. A real run showed that a gap in a shim is not covered by a correct role file.

## Proposal 2: Human-acceptance handling of an incomplete record is undefined

What prompted it: the returned `human-acceptance.md` had the explicit-accept box checked. Every checklist row had Status `verified` but empty "What I observed" and evidence cells. The disposition name, date and rationale were blank. `harness/roles/orchestrator.md` says to require "an unambiguous acceptance instruction" and to record "each check that remains unverified". It does not say how to treat rows that claim `verified` without observations, or what the minimum valid record is. The Orchestrator had to invent a rule: it treated the status as not an attestation and took the identity and time from the header fields. The run log also records the status as "prefilled", although `harness/templates/human-acceptance.md` leaves that cell empty. I could not tell from the run whether the Orchestrator or the human wrote `verified`. That ambiguity is itself the problem.

Recommended edit:
1. In `harness/roles/orchestrator.md`, in the explicit-acceptance paragraph, state the minimum record: the checked acceptance box plus the verifier name and date/time in the header.
2. In the same paragraph, state that a row counts as human-verified only when both the observation and evidence cells are non-empty. Any other row is recorded as unverified-and-accepted, whatever its Status cell says.
3. In `harness/templates/human-acceptance.md`, make the Status cell default to `not checked`, so an untouched row is never read as verified, and state that the Orchestrator must not prefill any other value.

Owning documents: `harness/roles/orchestrator.md` and `harness/templates/human-acceptance.md`.

## Proposal 3: The ticket's manual verification cannot be done by the Implementor, so a human pause was unavoidable

What prompted it: Feature-01's "One-time manual verification" asked for three ideas created through the UI as a student, three different decisions as a teacher, a student-view history check, mobile screenshots, and console checks at every state. The Implementor did one desktop `REQUEST_REVISION` and said so in its handoff. Evaluation 1 kept the manual check pending. Evaluation 2 returned `awaiting-human` with no code defect left. The human then accepted the commit without performing any of the five checks. The pause cost a full round trip and produced no verification.

Recommended edit: in `harness/templates/ticket.md`, in the "One-time manual verification" section, add a requirement that each manual item be labelled either **Implementor-performed** (reachable with the preview tooling and the testing profile, with a stated way to create the needed data through the UI) or **human-only** (needs a real device, a second browser, or a judgement a script cannot make). Add a sentence that a **human-only** item should be listed as such so it can go straight to the awaiting-human checklist without an extra Implementor/Evaluator cycle. Add a second sentence telling ticket authors that if a multi-actor, multi-viewport walkthrough is expected from the Implementor, the ticket must name the fixtures or preview extension that makes it feasible.

Owning document: `harness/templates/ticket.md`. As a follow-on, `harness/roles/evaluator.md` could state that an item the ticket labels human-only is reported as a human-pending item and does not count against the Implementor's pass.

## Proposal 4: Run-log timestamps do not come from a clock

What prompted it: the log has the human return at "21:40" and closeout at "21:45", with the run "paused 2026-10-07T21:30". The human record is dated 21:38, and this Learner was invoked at about 21:41, before the logged closeout time. These values were estimated, not read. Metrics and heartbeat times are the harness's only audit trail of duration.

Recommended edit: in `harness/roles/orchestrator.md`, in the run-log and heartbeat paragraph, require that every timestamp, including the `## Metrics` start, pause, resume and end times, be taken from the system clock (for example `date +%Y-%m-%dT%H:%M%z`) at the moment of the step, and never estimated or rounded forward. The existing "Do not fabricate" sentence does not name timestamps, and the token figure is the only value currently labelled "estimate".

Owning document: `harness/roles/orchestrator.md`.
