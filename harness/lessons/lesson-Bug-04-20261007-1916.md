# Lessons for Bug-04 (run Bug-04-20261007-1916)

The run finished as `done` after two Implementor passes and one revise cycle. Sources read: the run's `run.log`, `handoff-1.md`, `handoff-2.md`, `evaluation-1.md` and `evaluation-2.md`, `changed-paths*.txt`, plus the role contracts and `harness/tickets/Bug-04.md`. These proposals concern the harness only. They do not change the Bug-04 result.

## 1. Define the run-log metrics footer

**What prompted it.** [orchestrator.md](../roles/orchestrator.md) says to "end the run log with the metrics footer", but no document says what the footer contains. `run.log` for this run ends with an Outcome section and no footer. An undefined required element is easy to skip, and the Orchestrator would have had to invent the format.

**Edit.** Replace the "metrics footer" paragraph with a literal template. For example: a `## Metrics` section listing implementor passes, revise cycles, evaluator passes, start and end timestamps, and an estimated token figure labelled "estimate". Say that the footer is mandatory for every outcome, including failed and paused runs.

**Owner.** `harness/roles/orchestrator.md`.

## 2. Say that the ledger and run folder are Orchestrator-owned dirty paths

**What prompted it.** The Orchestrator, by contract, sets the `harness/plan.md` row to `in progress` and creates `harness/runs/<run-id>/` before dispatching the Implementor. Both Implementor handoffs then reported, under "What's uncertain", a "pre-existing `harness/plan.md` modification" and run-folder files that they "left untouched and uncommitted". The Implementor was unsure whether this dirt was a problem, and spent handoff text on it twice. Nothing in the Implementor contract says these paths are expected.

**Edit.** Add one sentence to the Implementor contract: "`harness/plan.md` and `harness/runs/` are written by the Orchestrator during the run. Expect them to be modified or untracked, never commit or edit them, and do not report them as uncertainty."

**Owner.** `harness/roles/implementor.md`.

## 3. Give out-of-scope findings a defined channel

**What prompted it.** The Implementor's contract says to "stop and report" anything outside scope. In this run it found that the backend rejects review requests with unrated optional fields. It reported this only as one bullet under "What's uncertain" in `handoff-1.md`. Neither evaluation mentions it. No step in the Orchestrator contract carries it forward, so it reached the user only because the coordinator happened to repeat it in the closing prose. A real finding could easily have been lost.

**Edit.**
- In `implementor.md`, require such findings to be written as a line starting `OUT OF SCOPE:` under "What's uncertain". This mirrors the existing `SPEC CHANGE:` convention.
- In `orchestrator.md`, require copying every `OUT OF SCOPE:` line into a `## Follow-ups` section of the run log. Also mention them in the closing prose. Optionally add a `Follow-ups: <none|summary>` line to the machine-readable return block.

**Owner.** `harness/roles/implementor.md` for the marker, `harness/roles/orchestrator.md` for carrying it forward.

## 4. Fix the Learner's output path and tell the caller to pass the full folder name

**What prompted it.**
- [learner.md](../roles/learner.md) tells the Learner to write to a path that reads literally `/lesson-.md`. The placeholders have been lost.
- The task statement's `lesson-<ticket-id>-<run-id>.md` is ambiguous, because the run ID already begins with the ticket ID. Taken literally it gives `lesson-Bug-04-Bug-04-20261007-1916.md`. The existing files, such as `lesson-Bug-03b-20261007-1333.md`, use ticket ID plus timestamp only.
- This run's caller passed only `Bug-04 20261007-1916`, although the contract requires the exact folder name.

**Edit.**
- In `learner.md`, restore the path as `harness/lessons/lesson-<ticket-id>-<timestamp>.md`, where `<timestamp>` is the part of the run folder name after the ticket ID. Give one worked example.
- State that the Learner may accept ticket ID plus timestamp from the caller and must resolve it to the folder `harness/runs/<ticket-id>-<timestamp>/`, or ask for the exact name if it does not exist.

**Owner.** `harness/roles/learner.md`.

## 5. Tell ticket authors to specify the success-path end state of interactive UI

**What prompted it.** The only revise cycle came from a gap in the ticket, not from implementation carelessness. Bug-04 required "focus moved into the modal on open and restored to the triggering button on close". It did not say where focus goes when a successful review removes the triggering button, because the idea is no longer reviewable. The Evaluator found this in manual preview, and it cost a full second implement-and-evaluate cycle. The ticket template's UI prompts cover viewports and roles but not what the user sees or where focus is after a successful action.

**Edit.** In the "Scope and contract" UI bullet and the "Acceptance criteria" list of the template, add a prompt such as: "For interactive UI (modals, forms, state changes), state the end state after a successful action as well as after cancel: what is visible, what refreshes, and where keyboard focus lands, especially when the triggering control disappears."

**Owner.** `harness/templates/ticket.md`. Bug-04 itself needs no change, because it is closed.

## 6. Stale tool names in the Orchestrator contract

**What prompted it.** [orchestrator.md](../roles/orchestrator.md) says to run gates with `jbang ...` and says preflight fails when "mvn is missing". The project forbids Maven and uses Gradle, and the preflight output for this run says "backend and frontend toolchains available". The gates ran as `java harness/gates/<gate>.java`. The contract's literal commands therefore did not match how the run was actually executed, so the Orchestrator had to infer the working command. I only inferred this from the run log's "preflight passed" line and the contract text, not from a recorded failure.

**Edit.** Replace `jbang harness/gates/<gate>.java` with `java harness/gates/<gate>.java` throughout, and replace "mvn is missing" with "the backend or frontend toolchain is unavailable". If jbang is intended, document that it is a prerequisite instead.

**Owner.** `harness/roles/orchestrator.md`.

## 7. Name the per-pass artifacts and the gate scope for revise cycles

**What prompted it.** The first pass wrote `changed-paths.txt`. For the revise pass the Orchestrator improvised `changed-paths-2.txt`. `handoff-N.md` and `evaluation-N.md` are numbered, but nothing numbers the changed-paths file. For the revise commit the contract says to "run both gates again on the new handoff and commit". The Orchestrator ran the scope gate on the revision commit's paths only. A later paragraph of the contract, about corrected gates, refers to "the complete deliverable changed-path list". It is unclear which one applies to a revise cycle.

**Edit.** In the Orchestrator contract, name the artifacts per pass as `handoff-N.md`, `changed-paths-N.txt`, and `evaluation-N.md`, with N starting at 1. State that the scope gate runs on each pass's own commit paths, and that the Evaluator receives the cumulative diff from the baseline.

**Owner.** `harness/roles/orchestrator.md`.
