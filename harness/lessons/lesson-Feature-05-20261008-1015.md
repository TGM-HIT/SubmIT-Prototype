# Lessons: Feature-05-20261008-1015

The run needed one revise cycle plus a verification-only pass. Pass 1 skipped the manual verification, the Evaluator found a blank-name validation gap in revise cycle 1, and the fix was not re-checked in a browser. Three of the four proposals below follow from those events. The fourth is about an ambiguity in the ticket and its handling.

## 1. Tell the Implementor where the preview password comes from

**What prompted it.** Handoff-1 says the authenticated browser checks were not performed "because `PREVIEW_PASSWORD` was unavailable". The testing password is documented in `backend/DEV-GUIDELINES.md`, and the ticket said "password via `PREVIEW_PASSWORD`", which an Implementor can read as "supplied by someone else". The Orchestrator then spent a whole extra Implementor pass (handoff-2) only to run the checks. Feature-04's Implementor read the same wording and did the check, so the instruction is read loosely.

**Proposed edit.** In the Ticket Author's procedure, add: when a manual check uses the preview tool, state that the password is the testing-only value documented in `backend/DEV-GUIDELINES.md`, to be set in the command environment, and not a secret the Implementor must be given. Add one sentence to the Implementor contract: a missing environment variable for a documented testing credential is not a reason to skip a manual check; read the documented value and set it.

**Owning documents.** `harness/roles/ticket-author.md` and `harness/roles/implementor.md`.

## 2. Make the Orchestrator catch skipped manual verification before the Evaluator

**What prompted it.** The Orchestrator caught the skip itself, by reading the handoff, and dispatched a verification pass. Nothing in `harness/roles/orchestrator.md` says to do that. The role only runs the handoff-completeness and commit-scope gates. The run could have gone straight to the Evaluator, which would likely have returned `awaiting-human` or `revise` and cost a full evaluation.

**Proposed edit.** In the Orchestrator's gate section, add: if the handoff states that an Implementor-performed manual check was not performed, and no environment limit outside the documented setup prevents it, send it back to a fresh Implementor for a verification-only pass at the next `handoff-N.md` before dispatching the Evaluator. Count it as an Implementor pass, not a revise cycle.

**Owning document.** `harness/roles/orchestrator.md`.

## 3. Require a browser re-check after a revise that changes browser-only behavior

**What prompted it.** The Evaluator's finding, that native `required` blocks the `submit` event, was only visible in a real browser, and handoff-2 had flagged this very gap as uncertain. The revise pass fixed it, tested it in jsdom, and said "I did not re-run a real-browser check". Evaluation 2 accepted the jsdom evidence by reasoning about the form change. That worked here, but the Implementor-performed manual items in the ticket cover the error state, and the fix changed exactly that state.

**Proposed edit.** In the Implementor contract's revise-pass section, add: when the finding concerns behavior that depends on the browser (native form validation, focus, scrolling), repeat the relevant ticket manual-verification item in the preview and report the result, or state the specific reason it could not be run.

**Owning document.** `harness/roles/implementor.md`.

## 4. Ask the ticket to settle native versus custom form validation

**What prompted it.** The ticket required name errors to appear "inside the modal" and gave the rules (trimmed, 1–120 characters) but not how blank input is reported. The Implementor used a native `required` attribute alongside custom validation, and the conflict between the two caused the revise cycle. Also, the new test's comment describes native constraint validation, although the form now has `novalidate`.

**Proposed edit.** In the Ticket Author's procedure, add: when a ticket specifies validation messages shown in the UI, say whether the application's own validator is the single source of the messages, so that browser-native validation is not relied on. Add the matching sentence to the ticket template's mechanical-checks hint: tests for form validation must submit through the real control, not a synthetic event.

**Owning documents.** `harness/roles/ticket-author.md` and `harness/templates/ticket.md`.
