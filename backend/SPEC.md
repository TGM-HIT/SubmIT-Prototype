# SubmIT - Backend Specification

This document defines SubmIT backend behavior and the API contract. Its Spring Boot runtime entry point is `ac.at.tgm.submit.SubmITlication`. Shared business rules live in `docs/SPEC.md`; frontend behavior lives in `frontend/SPEC.md`.

## 1. API Boundary

All endpoints use the `/api/` prefix and JSON request/response bodies unless otherwise specified. Project artefact upload and retrieval may use multipart and binary responses. The canonical API contract is generated from backend annotations into `contracts/openapi.yaml` by the Gradle task `generateOpenApi`. Do not edit the generated file manually.

Every collection endpoint is paginated. Responses contain `content`, `page`, `size`, `totalElements`, and `totalPages`. `page` is zero-based, the default size is 20, and the maximum size is 100.

Use standard statuses: `200` for successful reads or body-returning mutations, `201` for creation, `204` for bodyless mutations, `400` for invalid input, `401` for missing or invalid credentials, `403` for insufficient authorization, `404` for missing resources, and `409` for state or uniqueness conflicts.

## 2. API Resources

### Authentication and users

- `POST /api/auth/register` creates an immediately usable `{STUDENT}` account with language `en`; optional supplied roles are ignored. The default `No class / unassigned` catalogue class is assigned to each new student.
- `POST /api/auth/login` returns a JWT, the account name, persisted language, and complete `roles` list. New JWTs carry a `roles` claim and grant every authority in it.
- `GET /api/users` returns a paginated user list for callers whose roles include `ADMIN`; optional scalar `role` (`STUDENT`, `TEACHER`, or `ADMIN`) and `q` parameters filter by role-set membership and case-insensitive username/display-name substring, respectively. Blank `q` is ignored, and `%` and `_` are literal search characters. Filters combine with AND and apply before pagination.
- `PATCH /api/users/{id}` changes the account name for the account owner or `ADMIN`.
- `PATCH /api/users/{id}/language` accepts `{"language":"en"|"de"}` and changes only the language of the authenticated caller's own account. It returns the updated `UserResponse`; language is required on every user response. Existing account records default to `en` when the language column is added. Missing, malformed, or unsupported values return `400`; missing/invalid authentication returns `401`; a caller changing another account (including an administrator) receives `403`; a missing account receives `404`. This operation does not invalidate tokens or change other account data.
- `PATCH /api/users/{id}/role` accepts a `roles` array for callers whose roles include `ADMIN`. Supported sets are `{STUDENT}`, `{TEACHER}`, `{ADMIN}`, and `{TEACHER, ADMIN}`; empty, duplicate, unknown, and student-plus-staff sets return the standard `400` validation error without changing the account. It returns `409 Conflict` without changing roles if removing `ADMIN` from the only account whose set includes it would leave no administrator. Removing `ADMIN` from a dual-role account is permitted when another administrator remains, and preserves its `TEACHER` role. Changing an account to `{STUDENT}` assigns the default `No class / unassigned` class if the account has no class. Existing class and subject assignments are otherwise preserved. Administrators can change the class through `PUT /api/users/{id}/student-details`.

Every account has a required display name separate from its unique username. Registration and name updates trim leading and trailing whitespace, then reject blank names and names longer than 120 characters. Registration, login, name-update, and administrator user-list responses include the display name. A name update changes no other account field; role changes remain restricted to the existing administrator-only role endpoint. Testing-profile student, teacher, and administrator accounts have stable, distinct, human-readable display names while retaining their existing usernames; the `testing` profile seeds the `Testing Class` and `Testing Class 2` classes and distributes student accounts between them (student01 remains in `Testing Class`); a configured bootstrap administrator is named `Administrator`.

Account language uses only the stable codes `en` and `de`, defaults to `en` for existing and newly registered accounts, and is exposed in authentication and account responses. Registration does not accept a language choice. Only the authenticated account owner may change language; administrator role and name editing remain separate and unchanged.

Account roles are stored as a nonempty role set and exposed only through the canonical `roles` account property (including login/token user data, user lists, and role-change responses/requests); account models do not expose a competing singular `role` property. `STUDENT` is mutually exclusive with staff roles. A `{TEACHER, ADMIN}` account gets the union of both authorities across role-gated services and endpoints. An `{ADMIN}`-only account cannot perform teacher-only grading or review decisions, and a `{TEACHER}`-only account cannot perform administrator-only operations. Student-only operations remain exclusive to `{STUDENT}`. A role change updates persisted roles and audit history transactionally; already-issued JWT claims remain unchanged until expiry, while the next sign-in receives the updated role set. No role-row migration/backfill or legacy singular-`role` JWT support is required because no deployed accounts exist. Bootstrap-administrator and `testing` profile account provisioning continue with their respective singleton roles.

### School years and application periods

- `GET /api/school-years` returns available school years.
- `POST /api/application-periods` creates an application period for `ADMIN`; `PUT /api/application-periods/{id}` updates it for `ADMIN`, provided the period has not been finalized. Both operations require an administrator-provided label.
- `GET /api/application-periods` and `GET /api/application-periods/{id}` return periods and their status, dates, and accepted project catalogue.

An application-period label is required on create and update. The server trims surrounding whitespace and accepts only a nonblank label of 1 to 100 characters after trimming. Period responses expose the label and school year separately; for a legacy period without a stored label, the response label is the school year and the stored record is not rewritten. An application period also records its school year, opening and closing timestamps, eligible accepted projects from that same school year, and lifecycle status (`DRAFT`, `OPEN`, `CLOSED`, `ALLOCATED`, or `FINALIZED`). Dates must be ordered; an application period cannot open unless at least three accepted projects are available. Configured timestamps govern its effective opening state independently of a stale stored status: before `opensAt` it is not open, and at or after `opensAt` but strictly before `closesAt` its returned status and open-period operations are `OPEN`. At or after `closesAt`, application and applying-group writes and early runs are closed. While effectively open, an administrator may start any number of early preliminary runs. They snapshot the applications at start, do not close the period on success or failure, and do not count as the initial run. At the deadline, the system automatically closes applications and processes exactly one initial run synchronously for every due period not already finalized, regardless of persisted `DRAFT`, `CLOSED`, or `ALLOCATED` status or earlier runs. A post-deadline period edit or replacement run cannot defer or suppress that required initial run. The exactly-once check and creation serialize with scheduler, administrator replacement, update, and finalization paths; a period cannot be finalized without its initial run. Already-finalized historical periods are not backfilled. The period becomes `ALLOCATED` after a successful run and remains or becomes `CLOSED` after a failed run; it does not expose an intermediate `ALLOCATING` state. For authenticated student callers only, period reads include a narrow `projectTitles` catalogue of each project ID and its current title when the current time is at or after `opensAt` and at or before `closesAt`, regardless of the stored period status. Titles are resolved at read time only for ideas still accepted for applications; unresolved titles use `Unknown project`. The field is absent for staff, before opening, and after closing. It exposes no other idea data and does not change student access to idea endpoints or public archive responses. Separately, authenticated `STUDENT` callers may use `GET /api/application-periods/{periodId}/catalogue/{projectId}` to request the current accepted idea and specification for a project in that period's catalogue. The current time must be at or after `opensAt` and at or before `closesAt`; this read remains available at the exact deadline even if deadline processing changed the stored status. The project must be in the period's catalogue, remain accepted for applications, and belong to the period's school year. The response includes the title, description, intended outcome, scope points, learning topics, school year, and the current accepted specification, with no owner, review, feedback, supervisor, or other student data; other roles are forbidden.

Period requests optionally accept `eligibilityMode` (`ALL_STUDENTS` or `SELECTED`, default `ALL_STUDENTS`), `eligibleStudentIds` (unique UUIDs referencing current `STUDENT` accounts), and `eligibleClassIds` (unique UUIDs referencing existing classes); omitted arrays default to empty. `ALL_STUDENTS` requires both arrays empty. `SELECTED` is the deduplicated union of selected students and students currently assigned to selected classes; empty arrays admit nobody. Malformed UUIDs, duplicates, unknown references, and selected non-student accounts return `400`; there is no array-size limit. Legacy periods without configuration remain `ALL_STUDENTS` without rewriting stored records. Only `ADMIN` responses include the mode and arrays; other roles omit all three properties. Eligibility may be edited until finalization and is evaluated against current class assignment at each run snapshot.

### Ideas and project specifications

- `POST /api/ideas` creates an idea draft for an authenticated student or teacher. A student may include up to four student `collaboratorIds` (IDs from the narrow student lookup); a teacher idea has only its teacher author as owner.
- `GET /api/ideas` returns a paginated list filtered by supported status, school year, and owner criteria; visibility follows role permissions. Each visible idea includes the creator and all owners with their current display names and IDs; the legacy `ownerId` and `ownerDisplayName` continue to identify the creator.
- `GET /api/ideas/{id}` returns an idea and its current specification, review history, ratings, and supervision preferences as visible to the caller. The creator and every owner, each review author, and each preference teacher include their current account display name alongside their existing IDs; these names are included only in the same authorized idea responses as their corresponding user references.
- `PUT /api/ideas/{id}` updates the authenticated author's draft, an idea returned for revision, or their withdrawn idea.
- `POST /api/ideas/{id}/submit` submits an owned draft, returned idea, or withdrawn idea for teacher review.
- `PUT /api/ideas/{id}/specification` creates or updates the full specification after idea approval.
- `POST /api/ideas/{id}/specification/submit` submits the full specification for acceptance review.
- `POST /api/ideas/{id}/withdraw` withdraws an eligible author-owned submission.
- `POST /api/ideas/{id}/owners` adds a student collaborator for the creator.
- `DELETE /api/ideas/{id}/owners/{studentId}` removes a collaborator for the creator.
- `DELETE /api/ideas/{id}/owners/me` lets a collaborator leave.
- `GET /api/users/students` returns a paginated display-name-only student lookup to authenticated students and administrators (optional display-name substring `q`); other roles are forbidden. Administrators use the same lookup for allocation pins.

Idea requests require a title, description, intended outcome, initial scope points, and school year; learning topics are optional. Full specifications validate the objectives, users, requirements or features, deliverables, scope, and known dependencies or resource needs. Student owners may read the idea and its specification, history, ratings and feedback, and may edit, submit, resubmit, and withdraw under the existing lifecycle. A teacher author has the same lifecycle rights for their own idea and specification. Both student and teacher authoring endpoints enforce ownership; administrators cannot author. The creator is the legacy idea `ownerId`; `owners` identifies the creator and collaborators. Teacher ideas always have one owner and owner-management operations do not permit collaborators on them; teachers are never valid collaborators. Student-created ideas retain the existing collaborator rules: only the creator may add or remove collaborators; only a collaborator may leave; additions accept student accounts only and are limited to five owners total. Owner changes record `IDEA_OWNER_ADDED`, `IDEA_OWNER_REMOVED`, or `IDEA_OWNER_LEFT` audit events and do not affect public archive responses. Authors may edit only their own drafts, withdrawn ideas, or submissions returned for revision; editing a withdrawn idea returns it to draft. Submitted content is immutable until a teacher returns it for revision. Idea responses include `teacherIdea` for teacher and administrator callers only; it is derived from the author's current account role, not stored, and changes if that role changes. Student responses omit this property.

### Reviews, ratings, and supervision preferences

- `POST /api/ideas/{id}/reviews` records a teacher's idea decision: `APPROVE_FOR_SPECIFICATION`, `REQUEST_REVISION`, or `DECLINE`.
- `POST /api/ideas/{id}/specification/reviews` records a teacher's full-specification decision: `ACCEPT_FOR_APPLICATIONS`, `REQUEST_REVISION`, or `DECLINE`.
- `PUT /api/ideas/{id}/supervision-preference` creates or updates the authenticated teacher's preference: `WANTS_TO_SUPERVISE`, `WILLING_TO_SUPERVISE`, `NOT_WILLING_TO_SUPERVISE`, or `NOT_AVAILABLE`, with an optional note.
- `PUT /api/ideas/{id}/supervisor` assigns or replaces the confirmed supervisor for `ADMIN`; assigning a teacher with an explicit refusal (`NOT_WILLING_TO_SUPERVISE` or `NOT_AVAILABLE`) requires `acknowledgeRefusal: true`, or returns `409 Conflict`.

Reviews include written feedback and may include an overall recommendation. Each review may rate work size, curriculum relevance, technical complexity, feasibility, learning value, resource needs, and risk/dependencies. Each rating is an integer from 1 through 5. Ratings and recommendations are advisory and do not replace the explicit decision.

For idea reviews of submitted ideas, `REQUEST_REVISION` and `DECLINE` require non-empty written feedback, but ratings are optional; any supplied rating remains an integer from 1 through 5. A rating key supplied as an explicit JSON `null` (or any other non-integer or out-of-range value) is rejected without changing the idea or adding a history entry, while an omitted rating is accepted. Review responses identify whether an entry is an idea or full-specification review. The authorized idea response history returns the ratings actually recorded with each idea decision and does not synthesize omitted values. Full-specification review validation and rating display remain unchanged.

Only teachers may review or record supervision preferences. A teacher author is forbidden (`403`) from reviewing their own idea or specification; the request leaves the idea and review history unchanged. A decision must be valid for the current lifecycle stage. Reviews and decisions are append-only; corrections are recorded as new review entries rather than overwriting history. Acceptance is rejected unless a full specification has been submitted. Administrators may assign any teacher as the confirmed supervisor, including teachers without a recorded preference; an explicit refusal can be overridden only with `acknowledgeRefusal: true`. Projects may be included in an application period without a confirmed supervisor; administrators may assign or replace a supervisor at any time, including after allocation or finalization. Supervisor changes do not alter allocation results, group membership, applications, reviews, or grades.

### Applications

- `POST /api/application-periods/{periodId}/applications` creates the authenticated student's ranked project choices.
- `GET /api/application-periods/{periodId}/applications/me` returns the student's own application.
- `PUT /api/applications/{id}` replaces the ranked choices for the owning student before the deadline.
- `DELETE /api/applications/{id}` withdraws the owning student's application before the deadline.
- `GET /api/application-periods/{periodId}/applications` returns paginated applications for `TEACHER` and `ADMIN`.

An application contains at least three distinct project IDs, ordered by preference rank. Every project must be accepted and included in the period catalogue. The service rejects create, update, or withdrawal requests before `opensAt` or at/after `closesAt`, independent of a stale stored status. A student has at most one effective submitted application per period, individual or shared. An administrator may independently pin any STUDENT account to a project in the period catalogue; a pin does not edit the application and unranked or no-application targets require explicit acknowledgement. The authorized staff list also returns each student's current display name and each preference's current project title alongside the unchanged IDs; the student's own response may include those same values for only their own application.

An ineligible student receives `403` when creating or updating preferences; saved applications remain stored/readable, can be used if eligibility is restored before a later run, and are not implicitly withdrawn or restored. Existing withdrawal behavior is unchanged.

Authenticated student reads of `GET /api/application-periods` and `GET /api/application-periods/{id}` add `studentApplicationStatus`, containing only the caller's application status or `NOT_SUBMITTED`, and a `studentAssignment` for the caller's submitted application, a caller with a pin, or a caller included in the latest run's immutable eligible-student snapshot. The latter includes eligible callers without an application or pin. These properties are omitted from staff responses; students receive no pin metadata.

### Applying groups (before allocation)

- `POST /api/application-periods/{periodId}/applying-groups` creates a creator-only draft for a student without accepted membership in that period (`201`).
- `GET` on that collection lists the caller's accepted groups and pending invitations; teachers/admins receive read-only staff summaries. All collection routes use the standard pagination metadata/default/maximum.
- `GET /api/application-periods/{periodId}/applying-groups/{id}` exposes only the accepted roster, display names, current ranking, revision, approvals and caller action flags to accepted members, invitees and authorized staff. Unrelated students are forbidden. No private class/subject data is included.
- `GET /api/application-periods/{periodId}/applying-groups/{id}/invitations` paginates pending invitations for the creator or authorized staff, not other members/invitees.
- `POST /api/application-periods/{periodId}/applying-groups/{id}/actions/{action}` accepts `INVITE`, `REVOKE`, `ACCEPT`, `DECLINE`, `APPROVE`, `RANK`, `SUBMIT`, `WITHDRAW`, `LEAVE`, `TRANSFER`, `DISSOLVE`. Required positive `revision` binds every write to current state. `studentId` is required for invitation/revocation/transfer, `projectIds` for ranking, and `confirm: true` for submission/dissolution. IDs are UUIDs. Creator-only management, self-only consent/departure, invited-student-only acceptance/decline and current student roles are enforced by the service.

Submission requires 2–5 accepted students including the creator, at least three distinct accepted catalogue projects, and explicit unanimous approval of the same roster/ranking revision. Invitation acceptance is not revision approval; pending invitations neither reserve membership nor replace solos. Shared submission atomically replaces members' eligible solo submissions, after explicit confirmation. Solo create/update/withdraw endpoints reject independent writes while shared submission represents the caller. Own-application reads and period projections report coherent `SHARED_SUBMITTED` status; replaced solos are absent eligibility, never silently restored.

Actual ranking/roster changes invalidate every approval and reopen shared submission as a noneligible draft; pending invitation changes alone do not. Non-creators may leave, a creator transfers before leaving or dissolves with confirmation, and fewer than two cannot submit. Transfer changes only management, preserving roster/ranking approvals. Dissolution releases everyone; withdrawal/reopening/departure never restore prior solos. All group writes serialize on the owning period, recheck the revision and configured time interval, and reject before `opensAt` or at/after `closesAt`, independent of stale stored status. Concurrent final-seat/competing-group acceptance and submission cannot partially replace solos or duplicate eligibility. Role changes and registration never automatically enroll students.

Changing a shared ranking or submitting it requires every accepted member to be eligible at that time, otherwise return `409`. A submitted group that becomes mixed-eligibility is excluded whole from a run without modifying its saved roster or ranking. It may participate again once every member is eligible.

### Allocation pins

- `PUT /api/application-periods/{periodId}/allocation-pins/{studentId}` creates or replaces the student pin; request fields are required `projectId` and optional `acknowledgeUnranked` (default `false`). `DELETE` on the same route removes it and returns `204`, or `404` when absent. `GET /api/application-periods/{periodId}/allocation-pins` is paginated for `TEACHER` and `ADMIN`; students are forbidden.
- Only administrators may write pins. Unknown periods or students return `404`; non-STUDENT targets and projects outside the catalogue return `400`; finalized periods, more than five effectively pinned students for one project or conflicting targets within a submitted unit, and unranked projects without acknowledgement return `409`.
- Pin responses include student ID and current display name, project ID and current title, ranked-choice status, and saved time. Create, replace, and remove are audited. A catalogue update that would remove a pinned project returns `409` without changing the period.
- Pins are hidden from students. Student period projections expose only their ordinary assignment state; ranking and application endpoints do not reveal pin data.

### Allocation

- `POST /api/application-periods/{periodId}/allocation-runs` starts an early run for `ADMIN` while the period is effectively `OPEN` and before its deadline, or a replacement run after the deadline and before finalization. Runs execute synchronously: an allocation-run record is stored internally as `RUNNING` during processing, then becomes `COMPLETED` or `FAILED` before the request returns, so clients cannot observe the transient `RUNNING` status through the API. A run response includes `early: true` for early runs and `false` for all other runs, including stored runs without that field. Early runs leave the period `OPEN` on success or failure and cannot be finalized. The automatic initial run is processed exactly once at the deadline for every due period not already finalized, regardless of its stored status or early/replacement runs. A period edit after the deadline and a post-deadline replacement run cannot defer or suppress it. The scheduler, replacement, update, and finalization paths serialize the check and creation; finalization cannot proceed without the initial run. Already-finalized history is not backfilled. This initial run is not an early run. A successful initial run sets the period to `ALLOCATED`; a failed initial run leaves or sets it to `CLOSED`.
- `GET /api/application-periods/{periodId}/allocation-runs` returns paginated run history for `TEACHER` and `ADMIN`.
- `GET /api/allocation-runs/{id}` returns run status, summary, and result for `TEACHER` and `ADMIN`. The authorized run response resolves current student display names and project titles alongside the unchanged result IDs at read time; these labels are not stored in or used to mutate the immutable run snapshot.
- `POST /api/allocation-runs/{id}/finalize` finalizes an allocation for `ADMIN`.

Each run snapshots effective eligible student IDs using the selected students and current class memberships. Only eligible candidates participate; submitted groups require every member to be eligible, pins cannot add an ineligible candidate, and a previously stored eligible pin can apply in a later run after eligibility is restored. Every eligible student without a submitted solo or shared preference is also a candidate with an empty ranking and zero preference-satisfaction contribution; such a student may be assigned to any feasible catalogue project. The objective remains assigned count first, then preference satisfaction for submitted rankings, with existing deterministic tie-breaking. Each new assignment snapshot stores `hadPreferences`; authorized staff assignment results expose its non-null Boolean value. The caller's own student period assignment exposes optional `assignedWithoutPreferences`; both flags are omitted for legacy results lacking immutable state, never reconstructed from live applications. A new run's eligible IDs, applications, pins, applying units, and outcomes are immutable and unaffected by later eligibility or class changes. Mixed submitted groups are listed whole in `excludedApplyingUnits` for authorized staff with the `MEMBER_INELIGIBLE` reason.

The student-only period projection distinguishes `NO_RESULT`, `PRELIMINARY`, `FINAL`, `NOT_ASSIGNED_PRELIMINARY`, and `NOT_ASSIGNED_FINAL`. Before the deadline, early runs are excluded; after the deadline preliminary state is based on the most recent completed run created at or after the deadline, never on an early run. Final state is based on the finalized run's stored project group. Assigned responses resolve the current project title and current display names only for members of that student's assigned group, marking the caller; optional rank is the caller's own preference. An eligible caller without a submitted application may receive their own assignment projection from the immutable eligible-ID snapshot, without a pin; ineligible callers receive no candidate data from that run. The projection never includes member IDs, optimizer reasons, pin data, or other students' preferences or application data. Student access to staff allocation and application-list endpoints remains forbidden.

An allocation run uses an immutable snapshot of eligible applications, submitted applying units (exact accepted roster, ordered ranking and unanimously approved revision), projects, and the pins used. A submitted unit is indivisible and contributes its size to assigned count and per-student preference satisfaction. Its members share a project or are all unassigned; units may combine with solos or other units only within final size 3–5. Current members must remain students at snapshotting; invalid units fail explicitly rather than being split. Original-unit snapshots plus explicit pins preserve effective unit-wide constraints without depending on live membership. Same-project member pins deduplicate capacity, conflicting targets are rejected, and each explicit pin remains separately removable. Draft membership does not manufacture an effective shared unit.

Finalization persists complete membership and immutable origin cohorts. Student assignment members expose display names, display-only `originLabel` and `ownCohort`, not member UUIDs, pin/admin data or private assignments. Distinct original units retain separate cohort labels; individual additions are labelled individually, and legacy rows without provenance show `Origin unavailable`. The full final group, including additions, supplies Formal proposal membership. Anonymous archives exclude invitations, consent, applying-group membership and provenance as well as other private application data.

An allocation run retains its existing solo and pin behavior. It assigns each student at most once. Pinned students are assigned to their pinned project and are never moved by a run; only pins whose target remains an eligible STUDENT are used. The optimizer first maximizes assigned count, then ranked preference satisfaction, with eligible no-preference candidates available to every catalogue project at zero satisfaction. Groups remain three to five inclusive, with pins counting toward capacity. A pinned project that cannot reach three members reports pinned students unassigned with an explanation naming the pin; no smaller group is created. The result includes each project's assigned students, preference outcomes, unassigned students, and explanations for unassigned projects or students. Failed or incomplete runs expose their status and error details; they must not appear successful. An administrator may start a replacement run before finalization. A finalized run cannot be overwritten. Pin changes apply only to subsequent runs; stored run snapshots and results are unchanged.

### Formal group project applications

- `GET /api/formal-applications/eligible-projects` returns a paginated safe list for the authenticated `STUDENT`. It has no student-ID parameter and includes only persisted finalized `project_group` memberships containing the caller, across all finalized periods. A group is eligible only when its owning period and allocation run are finalized and the group's project is in that period's catalogue; preliminary runs, unassigned students, and other students' groups are excluded. Pagination uses the standard zero-based `page` default 0 and `size` default 20, normalized to 1–100. Students with no eligible groups receive an empty page; missing or invalid authentication returns `401`, and non-student roles receive `403`.
- Each eligible-project entry contains exactly `projectId`, `projectTitle`, `periodId`, `periodLabel`, `schoolYear`, `formalProposalId`, and `formalProposalStatus`. Project and period UUIDs are API values only. Resolve current project and period display labels at read time; use `Unknown project` when a finalized project no longer resolves and use the school year as the period-label fallback when a legacy period has no label. The nullable proposal ID/status pair reflects the current Formal proposal, with status limited to `DRAFT`, `NEEDS_REVISION`, `SUBMITTED`, `APPROVED`, or `DECLINED`. Do not expose group member IDs, student/application data, rankings, pins, or private allocation information.
- `GET /api/projects/{projectId}/formal-application-roster` returns `{ members: [{ studentId, displayName }] }` in finalized group roster order. Each member contains exactly the account UUID and current display name; use `Unknown student` when the account no longer resolves. This is a separate authenticated roster exception: only a `STUDENT` who is a member of that project's finalized group may access it. Do not accept a caller-supplied student ID or include cohort provenance, applications, rankings, pins, allocation data, or other account details. The eligible-project response and student assignment response remain free of group-member IDs.
- `POST /api/projects/{projectId}/formal-applications` creates a draft formal application for the allocated group.
- `GET /api/projects/{projectId}/formal-applications` returns the application's current version and paginated review history to authorized group members and teachers.
- `PUT /api/formal-applications/{id}` updates the group's draft or returned-for-revision application.
- `POST /api/formal-applications/{id}/submit` submits the application for teacher review.
- `POST /api/formal-applications/{id}/reviews` records a teacher decision: `APPROVE`, `REQUEST_REVISION`, or `DECLINE`, with feedback.

A formal application is separate from student preference applications. Its request and response fields implement the official form:

- `topic`: project topic, maximum 200 characters.
- `individualTopics`: one `{ studentId, topic }` entry per allocated group member; each `topic` is maximum 200 characters.
- `initialSituation`: the initial situation the project aims to change, maximum 400 characters.
- `investigationConcerns`: one `{ studentId, text }` entry per allocated group member; the combined text length across all entries is maximum 2,400 characters.
- `objective`: project objective or goal, maximum 400 characters.
- `plannedResults`: one `{ studentId, text }` entry per allocated group member; the combined text length across all entries is maximum 2,400 characters.
- `milestones`: an ordered list of `{ text, date }` entries.
- `cooperationPartner`: optional cooperation partner information.

Each allocated group member must have exactly one individual topic, investigation-concern entry, and planned-result entry. Validate that entries identify group members only, text limits are enforced server-side, and milestones have non-empty text and valid dates. Use a consistent character-counting rule in validation and document it in the API schema. Only members of the allocated group may author or submit the form. Submitted content is immutable until returned for revision. Project realization cannot be marked started until a teacher approves the formal application. Reviews and application versions are retained.

### Rosters, continuous grades, and project metrics

- `GET /api/grading-rubrics` returns available rubric versions and effective periods to authorized users.
- `GET /api/grading-rubrics/active` returns the active rubric version, including categories, criteria, assessment subject (individual, group, or both), rating scale and labels, evidence requirements, metric definitions, and configured aggregation rules.
- `GET /api/grading-rubrics/{id}` returns a specific immutable rubric version.
- `POST /api/grading-rubrics` publishes a new rubric version for `ADMIN`, with its effective date or school-year applicability.
- `GET /api/projects/{projectId}/student-grades` returns paginated individual grade history to teachers and administrators, who may optionally filter the project's history by `studentId`; without the filter, staff receive the project's history. Students may retrieve only their own grades whether the filter is omitted or matches their ID; requesting another student's ID is forbidden.
- `POST /api/projects/{projectId}/student-grades` records an individual student's rubric assessment for `TEACHER` only, including rubric version, grade, assessment date, and evidence/comments. `{ADMIN}`-only accounts are forbidden; a dual-role account is authorized by its `TEACHER` role.
- `POST /api/projects/{projectId}/student-grades/{gradeId}/revisions` allows `TEACHER` only to record a correction or reassessment without deleting the prior entry; `{ADMIN}`-only accounts are forbidden.
- `GET /api/projects/{projectId}/group-grades` returns paginated group-level assessment history to teachers, administrators, and authorized group members.
- `POST /api/projects/{projectId}/group-grades` records a group-level rubric assessment for `TEACHER` only; `{ADMIN}`-only accounts are forbidden.
- `GET /api/projects/{projectId}/metrics` returns paginated metric observations for authorized users.
- `POST /api/projects/{projectId}/metrics` records a project metric observation for `TEACHER` only; `{ADMIN}`-only accounts are forbidden.
- `GET /api/projects/{projectId}/final-grade` returns the final project grade and its basis when recorded to authorized teachers, administrators, and project members.
- `GET /api/projects/{projectId}/students/{studentId}/final-grade` returns an individual final grade and its basis to that student and authorized teachers or administrators.
- `PUT /api/projects/{projectId}/final-grade` allows `TEACHER` only to record or confirm the project and individual final grades after project completion; `{ADMIN}`-only accounts are forbidden.

The initial rubric version is based on the draft `docs/Entwurf Rubrikenbewertung.docx` and includes technical realization, project management, written work and technical documentation, presentation/discussion/defense, self-competence, and professional-field competence. The draft uses a 5-to-1 scale, evidence/notes, and category-level overall assessments. Since the rubric can change, expose rubric structure and versions as data; do not hard-code criteria or treat the draft as final. Only an administrator may publish a new immutable, school-approved version with an effective date or school-year applicability. Each version defines category and criterion identifiers, descriptions, scale and labels, assessment subject (student, group, or both), applicable project stage, metric definitions, and any aggregation rules. Existing project assessments remain bound to the version used when they were recorded. Applying a new version to an in-progress project requires an explicit recorded version transition and cannot rewrite past assessments.

Only teachers may record or revise individual and group grade entries. Grade entries identify the assessed student or group, rubric version and criterion, teacher, grade, assessment date, evidence/comments, and any superseded entry. Validate the submitted grade against the criterion's rubric scale. Only teachers may record project metric observations; they retain the metric-definition version, value, measurement time, and recording user where applicable, and validate against the configured definition. Administrators may read authorized grading data but may not record or revise grades, metrics, or final grades.

Final-grade inputs and calculation rules must be explicit and versioned. The final project grade and individual final grades must consider the applicable rubric assessments and project metric observations. When configured rules exist, responses include the resulting grade, applicable rule version, and inputs. Without configured calculation rules, only a teacher may record or confirm each final grade with a rationale identifying how relevant grades and metrics were considered; the service must not invent weights or derive an undocumented result. Administrators may read authorized final-grade data but cannot record or revise it. Final grades and their basis are retained as history. Students can read only their own individual grades; teachers and administrators with access to the project can read the full grade roster.

### Project completion and artefact archive

- `GET /api/projects/{projectId}/artifacts` returns a paginated artefact catalogue for authorized users.
- `POST /api/projects/{projectId}/artifacts` uploads an artefact using multipart form data, with type, title, description, file, and optional publication-submission metadata.
- `GET /api/artifacts/{id}` returns artefact metadata to authorized users.
- `GET /api/artifacts/{id}/content` retrieves an artefact's bytes for authorized users.
- `DELETE /api/artifacts/{id}` removes an artefact only when permitted by lifecycle and role; removal is auditable.
- `POST /api/artifacts/{id}/publication-review` submits an artefact for publication review or records an authorized teacher's approve/reject decision. Approval and unpublication decisions are auditable.
- `GET /api/public/projects/{projectId}/archive` returns the public archive catalogue for a completed project without authentication.
- `GET /api/public/projects/{projectId}/archive/{artifactId}` retrieves the content of an approved public artefact without authentication.
- `POST /api/projects/{projectId}/complete` records completion for an authorized teacher once required final grading and archive artefacts are present.

Artefact types include `WEBSITE_ARCHIVE`, `POSTER`, and `SOURCE_DATA`. After completion, the public archive is read-only and anonymously accessible, without platform registration, through the public routes above. An artefact is never public merely because it was uploaded: each item requires explicit publication approval by an authorized teacher, and only approved artefacts of a completed project appear in public catalogues or are retrievable anonymously. Private artefacts remain available only through the authenticated routes.

Before publication, the website snapshot and every proposed public artefact must be reviewed for student-identifying or other personal/sensitive data, credentials, private communications, grades, teacher feedback, and restricted material. Source data must be anonymized or redacted as needed. The public archive must exclude student names/identities and group membership; accounts; preference and formal applications; reviews; student or group grades; rubric assessments; teacher comments; private metric observations; uploader identities; and audit data. Public metadata, filenames, embedded assets, and links must not reveal this information or expose authenticated-only resources. Publication review and any redaction are recorded. The website snapshot is downloadable/browsable only through a safe viewer that does not execute untrusted active content in the application's origin. Project members and teachers may access non-public project artefacts according to role and school privacy/retention policy.

The project archive records internal metadata, uploader, timestamps, publication status, and changes. Only authorized users may upload, replace, remove, approve publication, or unpublish artefacts. Completion validation confirms presence of the required archive artefact types and final grading; it does not imply a particular file format unless defined by school policy.

### Audit

- Paginated read-only audit resources expose idea submission changes, reviews and decisions, supervision preference changes, application changes, allocation runs, formal project application versions and decisions, rubric version changes, grade and metric changes, final grades, project completion, and artefact changes to authorized users.
- `GET /api/audit` returns the paginated audit list, and `GET /api/audit/{entityType}/{entityId}` returns paginated entries for one entity. Both require authentication and are available to `TEACHER` and `ADMIN`; `STUDENT` callers are forbidden.
- Audit entries cannot be created, edited, or deleted by clients.

## 3. Backend Contract Rules

- Controllers validate HTTP input and delegate business operations to exactly one service method.
- Services enforce roles, ownership, review-stage rules, deadlines, group membership, grading-roster constraints, and allocation invariants.
- Repositories perform data access only and use paginated `Page<T>` queries for collections.
- State transitions, review writes, application snapshots, and allocation result persistence are transactional where needed to prevent partial updates.
- Allocation runs retain their input snapshot and outcome so the result can be reviewed and reproduced.
- Formal project applications, immutable rubric versions, grade histories, metric observations, final-grade bases, and project artefact changes are retained and auditable.
- Request, response, validation, and security annotations fully describe the generated OpenAPI contract.
- API errors use one consistent response shape and include useful validation or conflict details without exposing secrets.

### Student class and elective-subject catalogue

- `GET /api/student-classes` and `GET /api/elective-subjects` return paginated shared catalogues to authenticated teachers and administrators. The class catalogue includes the default `No class / unassigned` entry.
- Class lookup pages use immutable class-ID ordering; administrators may traverse every page for period cohort configuration. Current student-to-class assignment, not a stored class expansion, determines selected-class eligibility at each allocation snapshot.
- Administrators create entries with `POST` and rename entries with `PATCH` on these catalogue resources; deletion is not supported. Names are trimmed, 1 to 100 characters, and unique without regard to case.
- `GET /api/users/{id}/student-details` returns current student class and elective-subject IDs and names to authenticated teachers and administrators. `PUT` on that route lets administrators assign one required class and a required list of zero to four unique subject IDs.
- Catalogues and assignment mutations are administrator-only. Assignments can target only students; unknown IDs, repeated subjects, and more than four subjects are rejected before mutation.
- Staff-only identity responses may include current class and elective-subject names. Generic account, student lookup, student-owned application/group, and public archive responses do not expose another students assignment details. The administrator account list may include the details.
- Allocation, idea-owner, staff application-summary, and staff grade responses resolve current names; allocation snapshots remain unchanged.
