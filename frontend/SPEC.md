# SubmIT - Frontend Specification

This document defines the SubmIT Vue application behavior. Shared product behavior lives in `docs/SPEC.md`; API details and the generated contract live in `backend/SPEC.md` and `contracts/openapi.yaml`.

## 1. Application

The frontend is a Vue 3 application using Vite, TypeScript, and Tailwind CSS. It communicates with the backend through `/api` and must not treat client-side permission checks as authorization.

## 2. Navigation and Screens

Provide authenticated views for:

- A dashboard showing the current school year, application period dates and status, and the user's relevant next actions.
- Paginated project ideas with filters for school year and lifecycle status.
- Student and teacher-author views for creating and editing idea drafts, tracking review feedback, developing full specifications after approval, submitting revisions, and viewing decision history. Teacher-authored ideas are single-owner.
- Teacher review queues for ideas and full specifications, with submission details, review history, decision actions, written feedback, and structured ratings.
- Teacher supervision-preference controls for each project, including wants to supervise, willing to supervise, not willing, and not available states with an optional note.
- Accepted project catalogue views with project details, supervisor-confirmation status, and project review information visible to authorized users.
- Student application views for browsing accepted projects and choosing **Apply individually** or **Apply together**, with at least three distinct ranked choices. The Applications workspace shows shared drafts/submissions, accepted roster and creator, pending invitations, current revision and each member's approval, effective individual/shared/absent eligibility, locked state and deadline.
- Student views for editing or withdrawing an application before the deadline, and for viewing their own application status and allocation result. Applications shows each period's submission status, preliminary/final or unassigned state, current project title and only the assigned group's current display names (marking the caller); Overview shows a concise per-period assignment or application summary linking to Applications. Early preliminary runs are never shown to students; before the deadline no early result appears, and after the deadline preliminary assignments use only the most recent completed run created at or after the deadline. Preliminary assignments are explicitly subject to finalization or a replacement run. Students never see UUID labels, usernames, optimizer reasons, or unrelated students' individual application/preference data; invitees and accepted members may inspect their authorized shared roster and ranking.
- Student Formal proposal views for selecting an eligible allocated project from the authenticated student's finalized memberships across all periods. Load every page of eligible projects, and label each option with its current project title, period label and school year, and any existing Formal proposal status; do not display or request project or period UUIDs. Selecting an existing proposal opens its current form and review history without creating a duplicate. Selecting a project with no proposal offers the existing **Start a formal proposal** action. Preserve the form and lifecycle: `DRAFT` and `NEEDS_REVISION` are editable; submitted, approved, and declined proposals remain read-only.
- Group views for drafting, submitting, and revising the official formal project application after allocation, using every final member including allocation additions; this Formal proposal is separate from an applying group. Teacher and administrator author/review views retain their existing project-ID lookup and review controls.
- Teacher views for reviewing formal project applications and approving, requesting revisions, or declining them with feedback.
- Project progress views for teachers to record and review ongoing individual and group grades against the active rubric, and to record project metric observations.
- Rubric views showing the active and applicable rubric version, category structure, criteria, rating scale, and evidence/comments.
- Administrator controls for publishing a new approved rubric version with its effective date or school-year applicability.
- Project completion views for individual final grades, the overall project grade where configured, and their underlying rubric assessments and metric inputs.
- A public, unauthenticated archive view for completed projects, plus authenticated project archive management and private-artefact views.
- Teacher and administrator views for application-period configuration and application summaries.
- Administrator views for users, roles, confirmed supervisor assignments, automatically started allocation runs, early preliminary runs while a period is open, run results, post-deadline replacement runs before finalization, and finalizing eligible allocation results. The early-run control explains that applications remain open and students do not see those results; early and deadline/replacement runs have distinct text labels.
- Audit-history views for visible submissions, reviews, applications, and allocation runs.

Authentication provides registration, login, JWT handling, logout, and session-expiry behavior.

Registration collects a required account name distinct from the username and creates a student account using the existing registration and login flow. Newly registered students receive the default `No class / unassigned` class and can use the account immediately. In Users & roles, administrators can change a student's class and assign up to four subjects; changing another role to Student defaults its class to `No class / unassigned` unless the administrator chooses a different class. Signed-in students, teachers, and administrators can manage their own account name on the authenticated User Settings page at `/settings`; the shell provides a User Settings navigation link and continues to show the current display name, username, and role. Save trims outer whitespace, requires a nonblank value of at most 120 characters after trimming, updates the authenticated account and shell immediately without logout or reload, and shows a success status while remaining on the page. Cancel restores the saved name without changing it. Save and cancel return focus to the Account name field; validation or server errors preserve the entered value for correction. Username and role are not editable there. Administrators can still edit any account name from user management. On Users & roles, administrators can filter the paginated account list by role and search usernames and display names; each account has one Edit action that opens a modal for changing the account name and role. Student assignment controls always save exactly one class and enforce the four-subject limit. Registration and login authorization behavior remain unchanged apart from assigning the default class to new students.

## 3. Permissions in the UI

- `ADMIN` sees user and role management, application-period configuration, allocation-run and finalization controls, and a Fixed assignments section to list, add, change, and remove pins. The section uses student lookup/display names and project titles, shows unranked warnings, requires explicit confirmation before sending acknowledgement, and is unavailable for writing after finalization.
- `TEACHER` sees review queues, rating and decision controls, supervision preferences, authorized application and allocation results, formal-application review, student-grading, project-metric, and final-grading controls.
- `TEACHER` can create and manage their own ideas and specifications under the student author lifecycle, but cannot review or decide their own submissions; explain the unavailable self-review action. Teacher-authored ideas are labelled "Teacher idea" for teachers and administrators.
- `STUDENT` sees controls to manage ideas they own (including ideas created by a collaborator), full specifications, preference applications, and (after allocation) their group's formal application and project artefacts. Student identity, group membership, and grades are never exposed through the public archive.
- Only students use the finalized eligible-project dropdown for Formal proposals. Teachers and administrators retain the existing project-ID lookup and teacher review workflow; role-specific controls do not change the backend authorization boundary.
- Hide or disable actions that the current user's role or resource state does not permit. The backend remains authoritative and may reject stale or unauthorized actions.

## 4. Interaction Requirements

Every list supports pagination and clearly exposes loading, empty, error, and retry states. Forms show field-level validation and server errors without losing valid user input. Display lifecycle status and deadlines in plain language.

The student Formal proposal project dropdown loads all pages of the self-only eligible-project endpoint. Its loading, empty, failed-load, retry, and selected-project-fetch-error states are explicit and accessible; a failed request is never presented as an empty list, and a failed proposal fetch keeps the selected option available. Options show only current human-readable project/period labels and, when present, the human-readable existing proposal status. Project and period UUIDs remain internal API values and are not rendered in the student controls, status text, links, or accessible names.

The UI must make the following behavior clear:

- Applying groups contain 2–5 accepted students at submission (creator-only formation drafts are allowed), stay together in allocation and may receive additions to reach final size 3–5. Only the creator manages invitations and ranking, submits/withdraws/transfers/dissolves; invitees inspect roster/ranking and accept/decline for themselves, and accepted members explicitly approve the current revision or leave. Acceptance is not approval. Ranking/roster changes reopen submission and invalidate all approvals; pending/declined invitations alone do not. Transfer preserves approval and removes the old creator's management controls. Deadlines lock every group action.
- Confirm atomic replacement of all members' solo submissions before shared submission. Confirm withdrawal, leaving and dissolution with an explicit no-restoration warning. Cancel sends no mutation and returns focus to its trigger; success refreshes shared/effective/dependent state and focuses the changed group, invitation lookup after invite changes, or the Applications primary group action after departure/dissolution. Errors remain visible, preserve valid ranking/search input and never present successful consent. Invitation, student lookup and staff shared-summary lists expose usable pagination, including entries after the default first 20; unavailable data is not rendered as empty.
- Staff shared summaries identify units and accepted members separately from replaced solo records. Student preliminary/final assignments and staff results distinguish each original applying cohort from individual allocation additions, identify the student's own cohort and use an honest unavailable-origin label for historical results. Display names/project titles replace UUID labels. Pins to any submitted-group member constrain the whole unit; same-project member pins deduplicate, conflicting targets fail, unranked targets require acknowledgement, and removing one explicit pin leaves other member pins effective. These constraints are explained in staff controls without exposing pin metadata to students.
- Invitations, consent and applying-group membership/provenance are private and absent from public archive responses, DOM, links and downloads. No role, registration, idea ownership or equal ranking automatically implies applying-group membership.

- A student or teacher author starts with a concise idea submission containing a title, description, intended outcome, initial scope points, learning topics, and school year.
- Submitting an idea sends it to teacher review and locks author editing until the teacher requests revision or approves it for full specification.
- Approval allows the author to submit full specifications but does not mean the project is accepted into the application catalogue.
- A full specification includes objectives, intended users, features or requirements, deliverables, proposed scope, and known resources or dependencies.
- Teacher decisions and comments remain visible as review history. Clearly distinguish approval for full specification, acceptance for applications, revision requests, and declines.
- In Ideas & reviews, show every idea owner by current display name and identify the creator; students may search the display-name-only student lookup, choose collaborators at idea creation, and creators may add/remove collaborators in details while collaborators may leave. Confirm destructive owner changes, refresh owner/student lists, return focus to the lookup after add/remove and to the Ideas primary action after leaving, and close a departed collaborator’s detail view. Keep the UI readable on mobile with long owner names wrapping. Identify review authors, and teachers with recorded supervision preferences by their current account display names rather than IDs; administrators also see eligible teachers by display name in Confirm supervisor. Keep IDs for internal matching and preference status, review context, and notes visible.
- Teachers can start a review directly from an idea-list row when an idea or specification is awaiting review. Idea details and review forms open in accessible modal dialogs; a review may also be opened from the details modal, and a successful decision refreshes the list and visible history.
- Teacher ratings use a consistent 1-to-5 scale for work size, curriculum relevance, technical complexity, feasibility, learning value, resource needs, and risk/dependencies. Explain each category and show that the ratings inform but do not automatically determine the decision.
- For submitted idea reviews, declines and revision requests require non-empty written feedback but do not require ratings. Show only ratings recorded with each idea-review history entry, never defaults or an empty ratings section; keep full-specification review display unchanged. After a successful decision, refresh the idea and history, close the review flow, and focus the affected idea's Details & history control.
- Supervision preference is separate from a confirmed supervisor. In Ideas & reviews, show each teacher their own recorded preference alongside its idea, with no summary when none is recorded; retain recorded preferences in Details & history and keep editing there. Let administrators assign any teacher, grouping the options by preference and requiring explicit acknowledgment before assigning a teacher who recorded an explicit refusal.
- Students must choose at least three distinct accepted projects and rank them before an application can be submitted. Show the deadline, prevent duplicate choices, and allow reordering with accessible controls. The effective open state begins at `opensAt` regardless of stale stored status; application changes and withdrawal are available strictly before `closesAt`, and the locked state and deadline are clear. On the Applications page, a student sees current project titles from the open period catalogue in the catalogue, saved ranking, add selector, and move-button accessible labels; do not use the student's own idea list as a title source or render project UUIDs. Use `Unknown project` when a catalogue title is unresolved and do not show a project-reference ID. Period reads and catalogue details remain available through the exact `closesAt` instant even if deadline processing has changed the stored status; the detail view is unavailable after that instant. Expand each catalogue entry to read the current idea details and accepted specification for that project through the closing instant, with a clear per-project retry when the details request fails.
- In the staff application summary, identify each application and its status line by the student's current display name, and show ranked preference project titles; do not show application, student, or project IDs in those labels.
- Make clear that the system closes applications and starts exactly one initial allocation automatically when the deadline is reached for every due, unfinalized period, regardless of stored status, early or replacement runs, or later period edits. Administrators can review the run, request a replacement run before finalization, and finalize its result; finalization cannot bypass the initial run. Administrator pins fix students to projects for future runs without changing their rankings; unpinned students are optimized around feasible pins and valid groups remain three to five members. After a successful add, change, or removal, refresh the list and move focus to the changed entry or, after removing the last pin, to the add-form student control; cancelled actions return focus to the control that opened them.
- After allocation, show each assigned project or an explicit unassigned outcome. Label pinned assignments in text as fixed by the administrator and show the pin explanation for an unassigned pinned student. Project results show group members only to authorized users and never imply an invalid group size.
- Allocation results distinguish a completed run from an incomplete or failed one and explain unassigned students or projects when the system provides a reason. In authorized allocation result views, show current project titles and student display names for assignments and unassigned outcomes, retaining the supplied pin explanation and other reason text and avoiding IDs in those labels. Pin data and its administrator origin never appear in student responses.
- Once a group is formed, provide a distinct formal project application form with the official fields: project topic (maximum 200 characters); individual topic per student (maximum 200 characters each); initial situation the project aims to change (maximum 400 characters); scientific investigation concerns linked to each student (maximum 2,400 characters total across the group); project objective or goal (maximum 400 characters); planned result of each student's individual part (maximum 2,400 characters total across the group); milestones, each with text and date; and an optional cooperation partner.
- Display remaining character counts for each limited field, including the shared group totals for investigation concerns and planned results. Make it clear to students how shared limits apply as group members edit their contributions.
- Show teacher approval or revision feedback before presenting project work as approved to begin.
- The initial rubric is based on the draft `docs/Entwurf Rubrikenbewertung.docx`, which may change. Present criteria from the applicable rubric version rather than hard-coding the draft as permanent. Its current categories are technical realization, project management, written work and technical documentation, presentation/discussion/defense, self-competence, and professional-field competence.
- Publishing a new rubric version is an administrator action. Clearly display version applicability; changes must not silently alter earlier assessments or grade calculations. When a new version is explicitly applied to an in-progress project, show the transition and preserve which version applies to each assessment.
- Teacher grade-entry controls select the active rubric version, assessment category/criterion, assessment subject (student or group as configured), and date; they record the grade and evidence/comments and show the assessment history. The draft uses a 5-to-1 scale with evidence/notes and category-level overall assessments; use the scale and labels provided by the active rubric. Clearly identify later corrections or reassessments without hiding earlier entries. Students can view only their own individual grades.
- Project metric entry and display must be driven by metric definitions in the applicable rubric or school configuration. Do not hard-code an assumed metric list, units, or scale in the UI.
- Show individual final grades and the overall project grade where configured, with their bases. The bases must demonstrate consideration of applicable rubric assessments and project metrics. If calculation rules have not been configured, present teacher-recorded or confirmed grading with the teacher's rationale and without implying an automatic formula; when rules are configured, show the rule version and applicable inputs.
- The completed project's approved public archive is accessible without registration and is read-only. Provide an accessible browser for the website snapshot and clear ways to retrieve approved poster and source-data artefacts. Clearly label the archive as a completed-project snapshot, distinct from the live website.
- Keep publication review separate from upload: only explicitly approved artefacts for completed projects appear in the public archive. Authenticated archive management identifies private artefacts and provides authorized teacher publication-review and unpublish controls.
- Public archive pages and files must not expose student names or identities, group membership, account information, applications, formal-application or review history, individual or group grades, rubric assessments, teacher feedback, private project metrics, uploader identities, or audit history. Do not show uploader metadata publicly.
- Before publication, require review of website snapshots and artefacts for personal/sensitive data, credentials, private communications, grading information, and unsafe active content. Source data must be anonymized or redacted as needed. Public filenames, metadata, embedded assets, and links must not leak private information or lead to authenticated-only data.
- Do not expose non-public project archive files through public routes or cache private responses in the public archive. Public browsing remains permission-free only for approved contents; private artefacts remain behind authentication and role checks.
- Clearly show which required archive artefacts are present and any outstanding completion requirements. Confirm consequential archive changes and project completion.
- Confirm consequential actions such as submitting or withdrawing an application and finalizing allocation results.

Use the generated OpenAPI contract for API types and endpoint details. Do not hard-code duplicated request or response models when generated types are available.

## 5. UX Quality

Use responsive layouts for desktop and mobile, keyboard-accessible controls, visible focus states, semantic labels, and non-color-only status indicators. Preserve list filters, page position, and review/application context when navigating to a detail view and back. Dates and times must be displayed consistently with the user's locale while retaining the authoritative deadline from the API.

## Student class and elective-subject presentation

The administrator interface provides shared class and elective-subject catalogue editing and lets administrators assign one class and up to four subjects to each student. It provides validation feedback, allows clearing subject assignments, and displays resolved catalogue names rather than identifiers.

Authenticated teacher and administrator identity views show current class and elective-subject names beside student names in ideas/reviews, application summaries, allocation results, administrator account lists, and grading. Catalogues and student assignments are not presented to students or in student-facing groups, and do not appear in public archive views. The existing registration and login flow remains unchanged; new student accounts are assigned the default class.
