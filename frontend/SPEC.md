# SubmIT - Frontend Specification

This document defines the SubmIT Vue application behavior. Shared product behavior lives in `docs/SPEC.md`; API details and the generated contract live in `backend/SPEC.md` and `contracts/openapi.yaml`.

## 1. Application

The frontend is a Vue 3 application using Vite, TypeScript, and Tailwind CSS. It communicates with the backend through `/api` and must not treat client-side permission checks as authorization.

## 2. Navigation and Screens

Provide authenticated views for:

- A dashboard showing the current school year, application period dates and status, and the user's relevant next actions.
- Paginated project ideas with filters for school year and lifecycle status.
- Student and teacher-author views for creating and editing idea drafts, tracking review feedback, developing full specifications after approval, submitting revisions, and viewing decision history. Teacher-authored ideas are single-owner.
- Idea and full-specification narrative forms offer mutually exclusive form, Markdown import, and PDF upload modes. Markdown imports accepted English/German level-two headings into the editable existing fields, preserving title, school year, collaborators, and current values on parse failure. PDF replaces narrative fields only; idea metadata remains manual and is never extracted from a file. Server-side PDF validation requires a non-empty signed PDF of at most 10 MiB and retains existing lifecycle and field limits.
- An authenticated Templates/Vorlagen route provides four downloadable Markdown templates for the supported idea and specification headings.
- Teacher review queues for ideas and full specifications, with submission details, review history, decision actions, written feedback, and structured ratings.
- Teacher supervision-preference controls for each project, including wants to supervise, willing to supervise, not willing, and not available states with an optional note.
- Accepted project catalogue views with project details, supervisor-confirmation status, and project review information visible to authorized users.
- Student application views for browsing accepted projects and choosing **Apply individually** or **Apply together**, with at least three distinct ranked choices. The Applications workspace shows shared drafts/submissions, accepted roster and creator, pending invitations, current revision and each member's approval, effective individual/shared/absent eligibility, locked state and deadline.
- Student views for editing or withdrawing an application before the deadline, and for viewing their own application status and allocation result. Applications shows each period's submission status, preliminary/final or unassigned state, current project title and only the assigned group's current display names (marking the caller); Overview shows a concise per-period assignment or application summary linking to Applications. Early preliminary runs are never shown to students; before the deadline no early result appears, and after the deadline preliminary assignments use only the most recent completed run created at or after the deadline. Preliminary assignments are explicitly subject to finalization or a replacement run. Students never see UUID labels, usernames, optimizer reasons, or unrelated students' individual application/preference data; invitees and accepted members may inspect their authorized shared roster and ranking.
- Student Formal proposal views select an eligible allocated project from the authenticated student's finalized memberships across all periods. Load every page of eligible projects, and label each option with its current project title, period label and school year, and any existing Formal proposal status; do not display or request project or period UUIDs. Once selected, retrieve its private roster from the roster endpoint and do not offer start/edit actions until the roster succeeds. Roster and existing-proposal failures remain explicit and retryable; retain selection and ignore stale responses after selection changes. Present every finalized group member in roster order as an accessible keyboard-navigable tab labelled by current display name, using a visible ordinal to distinguish duplicate names. Each tab contains exactly that member's topic, investigation concern, and planned result fields. IDs are used only to preserve the existing contribution payload mapping and are never displayed or included in student-facing accessible names. Proposal-level fields and milestones remain shared; students cannot add or remove group members. Preserve shared character limits and existing lifecycle: `DRAFT` and `NEEDS_REVISION` are editable; submitted, approved, and declined proposals remain read-only. Successful create, update, and submit refresh the selected project's status; closing without saving makes no request and restores focus. Teachers use the searchable Formal proposal list, while administrators retain project-ID lookup and the existing review workflow.
- Teacher Formal proposal views start with a paginated list of proposals whose projects have a current confirmed supervisor assignment to the caller. A labeled text search matches current project title, allocated member display names, associated period label, and school year; clearing the supervised-only filter makes all proposals searchable. Results show current project title, every allocated member's current display name, period label and school year, and current status without rendering proposal or project UUIDs. Search and supervisor filtering happen before pagination. Selecting a result loads its existing proposal and review history through the existing detail route, then presents its human-readable project/period context and teacher review controls. Keep search/filter/page state while reviewing and after successful decisions; ignore stale list/detail responses, expose retryable loading failures, prevent conflicting selection while details load, and restore keyboard focus to the selected row when returning to the list (or the list heading if that row is no longer present). Teachers retain existing all-proposal read/review authorization; supervision affects only the initial list, not detail or review access.
- On `/grading`, teachers select from the same existing-proposal summaries and browse semantics as the teacher Formal proposal list: default to currently confirmed supervision of the caller; allow clearing that discovery filter; search current title, every allocated member display name, period label and school year with trimmed case-insensitive substring matching; filter before pagination; and show every member name, period/year and localized proposal status. Keep the query while changing the supervision filter and provide accessible pagination. Selecting a result opens only that project's grading record, not proposal detail/review or roster workflows. The supervisor filter limits discovery only and does not change grading authorization.
- On `/grading`, students choose from all pages of the authenticated self-only finalized-membership eligible-project endpoint, including memberships with no proposal or grades. Label each option and the selected-project heading with current project title, period label and school year; distinct periods remain distinguishable when titles repeat. Project/proposal/period UUIDs are internal option or request values only. Students see no project-ID box, other students' individual/final grades, or grading mutation controls. `{ADMIN}`-only accounts retain the authorized project-ID lookup and read-only grading record; rubric browsing, version downloads and publication are on `/rubrics`. `{ADMIN, TEACHER}` accounts use the teacher selector and retain teacher grading controls.
- Group views for drafting, submitting, and revising the official formal project application after allocation, using every final member including allocation additions; this Formal proposal is separate from an applying group.
- Teacher views for reviewing formal project applications and approving, requesting revisions, or declining them with feedback.
- Project progress views let teachers independently choose the project's routine and final criterion rubrics and select an actual allocated student by current display name and class/elective context. Routine mode renders all `STUDENT`/`BOTH` criteria in configured order with blank grade inputs on every new assessment, prevalidates populated rows, and appends only explicitly graded observations. Final mode renders the selected final rubric and hydrates only that student's current final values for that exact version; changed values require a reason and create revisions, while unassessed rows stay blank. Group grades and metrics remain routine-phase inputs. Loading, empty, retry, partial-save, ambiguous-outcome and conflict states remain explicit. Administrators retain authorized read-only access but cannot record or revise grades or metrics.
- Authenticated `/rubrics` views for `STUDENT`, `TEACHER`, `ADMIN`, and combined-role readers, with an active-version context, paginated immutable version history, and exact-version configured definitions, including categories, criteria, rating scales, evidence requirements, metrics, and aggregation rules.
- Administrator controls for publishing a new approved rubric version with its effective date or school-year applicability.
- Project completion views for individual final grades, the overall project grade where configured, and their underlying rubric assessments and metric inputs. Only teachers may record or revise project and individual final grades; administrators have read-only grading access.
- A public, unauthenticated archive view for completed projects, plus authenticated project archive management and private-artefact views.
- Teacher and administrator views for application-period configuration and application summaries.
- Visible student and staff period views identify each period by its label and retain the school year as context; the administrator period selector does the same. If a legacy period has no usable stored label, use its school year as the displayed label.
- Administrator views for users, roles, confirmed supervisor assignments, automatically started allocation runs, early preliminary runs while a period is open, run results, post-deadline replacement runs before finalization, and finalizing eligible allocation results. The early-run control explains that applications remain open and students do not see those results; early and deadline/replacement runs have distinct text labels.
- Audit-history views for visible submissions, reviews, applications, and allocation runs.

Authentication provides registration, login, JWT handling, logout, and session-expiry behavior. Account roles are the canonical `roles` list; the current session uses exactly the roles in its issued JWT and does not adopt later account changes until a fresh sign-in. Each authenticated account's persisted `en` or `de` language controls the frontend UI across routes and is restored from account data at login/session hydration. User Settings for every role provides explicit save and cancel actions for the caller's own language preference. Cancel does not call the API; a failed save retains the saved value and draft. On success the whole authenticated UI switches immediately without a reload.

Unauthenticated login, registration, and public archive pages use the primary `navigator.language`: German for `de` and regional variants, English for `en` and regional variants, and English for unsupported or missing values. No anonymous choice is persisted or sent to the server. Logging out restores the browser-derived language. Frontend-owned UI messages, including accessible names, client validation, and frontend-generated statuses/errors, are localized in complete English and German catalogs without silent missing-key fallback. Frontend-generated dates and numbers use the selected locale where formatted. Do not translate user-authored content, account names/usernames, backend-authored text/error messages, archive content, or lifecycle data beyond known frontend labels.

Registration collects a required account name distinct from the username and creates a `{STUDENT}` account using the existing registration and login flow, ignoring any submitted roles. Newly registered students receive the default `No class / unassigned` class and can use the account immediately. In Users & roles, administrators can change an account's roles, class, and up to four subjects; the supported sets are `{STUDENT}`, `{TEACHER}`, `{ADMIN}`, and `{TEACHER, ADMIN}`. Student selection is exclusive; Teacher and Administrator can be selected together. Existing class and subject assignments are retained when roles change, and `No class / unassigned` is assigned only if an account gains `{STUDENT}` without an existing class. Signed-in students, teachers, and administrators can manage their own account name on the authenticated User Settings page at `/settings`; the shell provides a User Settings navigation link and continues to show the current display name, username, and all assigned roles. Save trims outer whitespace, requires a nonblank value of at most 120 characters after trimming, updates the authenticated account and shell immediately without logout or reload, and shows a success status while remaining on the page. Cancel restores the saved name without changing it. Save and cancel return focus to the Account name field; validation or server errors preserve the entered value for correction. Username and roles are not editable there. Administrators can still edit any account name from user management. On Users & roles, administrators can filter the paginated account list by role membership and search usernames and display names; each account has one Edit action that opens a modal for changing the account name and supported role set. Student assignment controls always save exactly one class and enforce the four-subject limit.

## 3. Permissions in the UI

- `ADMIN` sees user and role management, application-period configuration, allocation-run and finalization controls, a Fixed assignments section to list, add, change, and remove pins, and period-specific priority-project controls. The pin section uses student lookup/display names and project titles, shows unranked warnings, requires explicit confirmation before sending acknowledgement, and is unavailable for writing after finalization. Priority controls list the selected period's accepted projects with current state and allow reversible mark/unmark selection without a confirmation dialog until finalization, including after the deadline while replacement runs remain permitted. Show loading, empty, error, retry, and save states; failed saves retain the draft selection, while successful saves show the persisted set and return focus to the save control. Keep the priority explanation and controls localized in English and German.
- An account with both `TEACHER` and `ADMIN` sees the union of these administrator controls and teacher controls, including teacher grading and review decisions. An `{ADMIN}`-only account does not see teacher-only grading or review-decision controls; a `{TEACHER}`-only account does not see administrator-only controls.
- In the administrator period editor, explicitly choose **All students** (the default) or **Selected students and classes**. Selected mode uses current display names/class names, complete paginated lookup data, loading/empty/error/retry feedback, and never UUID labels. Show the saved configuration while editing; changes are available until finalization. Save refreshes the period and moves focus to its row; cancel sends no mutation and returns focus to its trigger with saved state intact. Non-admin period views never show cohort controls or membership.
- `TEACHER` sees review queues, rating and decision controls, supervision preferences, authorized application and allocation results, formal-application review, and controls to record or revise individual/group grades, project metrics, and project/individual final grades.
- `{ADMIN}`-only accounts retain authorized read-only grading views but see no individual-grade, group-grade, metric, or final-grade mutation controls. Rubric publication is available only on `/rubrics`. A dual-role account receives the teacher grading controls and administrator rubric authoring controls.
- Every authenticated rubric-reader role can use the separate `/rubrics` page to browse and download any rubric version, including inactive versions. Entries show human-readable name, version and applicability; selecting a version loads its exact complete definition. JSON downloads are reusable publication-request definitions without database/publication metadata; Markdown presents the same configured definition readably. Browsing and downloading do not publish, switch the active rubric, mutate project/grade drafts or expose assessment records.
- On `/rubrics`, only administrators can start a local draft, copy a selected immutable version, load reusable UTF-8 JSON, edit the publication-request JSON, and explicitly publish a new immutable version. A malformed or incompatible file leaves the current draft unchanged; replacing an edited draft requires confirmation. Drafts are client-local, never alter the source version, and are discarded on cancellation or loss of administrator access. Server validation/conflict errors retain the draft for correction; publication refreshes version and active context without assuming a future-effective version is active.
- `TEACHER` can create and manage their own ideas and specifications under the student author lifecycle, but cannot review or decide their own submissions; explain the unavailable self-review action. Teacher-authored ideas are labelled "Teacher idea" for teachers and administrators.
- `STUDENT` sees controls to manage ideas they own (including ideas created by a collaborator), full specifications, preference applications, and (after allocation) their group's formal application and project artefacts. Student identity, group membership, and grades are never exposed through the public archive.
- For Formal proposals, students use the finalized eligible-project dropdown, teachers use the searchable proposal list, and administrators retain the existing lookup/review workflow. On `/grading`, students use the finalized eligible-project dropdown, teachers use the searchable teacher proposal-summary list, and `{ADMIN}`-only accounts retain the existing project-ID lookup. A dual-role `{ADMIN, TEACHER}` account uses the teacher selector plus teacher grading controls; rubric authoring remains on `/rubrics`. Role-specific controls do not change the backend authorization boundary.
- Hide or disable actions based on membership in the current user's role set or resource state. `{STUDENT}` is the only student role set; staff roles cannot gain student-only application or applying-group capabilities. The backend remains authoritative and may reject stale or unauthorized actions.

## 4. Interaction Requirements

Every list supports pagination and clearly exposes loading, empty, error, and retry states. Forms show field-level validation and server errors without losing valid user input. Display lifecycle status and deadlines in plain language.

The student Formal proposal project dropdown loads all pages of the self-only eligible-project endpoint. Its loading, empty, failed-load, retry, and selected-project-fetch-error states are explicit and accessible; a failed request is never presented as an empty list, and roster or proposal failures keep the selected option available without offering start/edit actions. Options show only current human-readable project/period labels and, when present, the human-readable existing proposal status. Project and period UUIDs remain internal API values and are not rendered in the student controls, status text, links, or accessible names. Roster member IDs are used only to associate contribution values with the existing request payload and are never rendered in student-visible text or accessible names. Teacher proposal result labels similarly show only human-readable project, member, period, and status values; internal UUIDs are used only for the existing detail request and are absent from teacher-facing text and accessible names. Teacher list loading, empty, retryable error, filter, and paginated states are explicit and localized in English and German.

The `/grading` teacher selector uses the existing typed `formal-applications` summary service, not a student roster/catalogue or proposal-detail request. Its initial supervision filter is enabled; text search is trimmed and case-insensitive across current project title, every group member display name, period label and school year, and remains unchanged when the supervision filter is toggled. Filtering precedes pagination. Search, filter and page changes are disabled during project-record loading or mutation. Results have accessible selection controls, page/count status, and localized current proposal status. Student grading choices use the self-only eligible-project service and load every page before marking the collection complete; failure on any page clears incomplete choices and offers retry. No `studentId` query or staff roster request is made to build student choices.

Initially, `/grading` shows no project histories or project-specific mutations. A selection loads individual grades, group grades, metrics and the role-appropriate final-grade record for exactly that internal project ID. The selected-project heading displays human-readable project/period context and receives focus after a successful load. Teacher return and student clear/change actions make no mutation, discard unsaved drafts and clear previous histories, final grade, and success messages. Teacher browsing query/filter/page state is retained and focus returns to the selected result or list heading if that result is no longer present; student clearing restores focus to the dropdown. Reselecting always reloads persisted data rather than restoring stale histories or form drafts. List and project-record loading, empty, failure, and retry states remain independently accessible and localized; a failed project load retains the selected option but never shows partial records or enables writes. Only a final-grade `404` is the explicit no-final-grade state. Ignore late responses after return, clear, unmount or superseding loads. Successful grading mutations stay on the selected project and refresh that record; failed mutations retain inputs. Students still see only their own individual and final grades, and administrators without `TEACHER` remain read-only. Keep selection, search/filter/pagination, project context, error states and action controls operable without page-level horizontal overflow or clipped actions at desktop 1440 × 900 and mobile 390 × 844.

The `/grading` page is for project assessment and histories; it does not contain the full rubric definition, rubric-version browser/downloads, or publication editor. It shows each project's separate routine and final rubric selections, initially unselected without silently defaulting to the active version, and may link to `/rubrics`. The teacher selection controls provide a human-readable all-version lookup or accessible pagination. Student entry uses the authorized grading-member surface, not the student-only Formal roster. Assessment rows use the exact selected rubric definition; browsing or downloading on `/rubrics` must not alter project/grade drafts or historical rubric-version associations.

The UI must make the following behavior clear:

- Applying groups contain 2–5 accepted students at submission (creator-only formation drafts are allowed), stay together in allocation and may receive additions to reach final size 3–5. Only the creator manages invitations and ranking, submits/withdraws/transfers/dissolves; invitees inspect roster/ranking and accept/decline for themselves, and accepted members explicitly approve the current revision or leave. Acceptance is not approval. Ranking/roster changes reopen submission and invalidate all approvals; pending/declined invitations alone do not. Transfer preserves approval and removes the old creator's management controls. Deadlines lock every group action.
- Confirm atomic replacement of all members' solo submissions before shared submission. Confirm withdrawal, leaving and dissolution with an explicit no-restoration warning. Cancel sends no mutation and returns focus to its trigger; success refreshes shared/effective/dependent state and focuses the changed group, invitation lookup after invite changes, or the Applications primary group action after departure/dissolution. Errors remain visible, preserve valid ranking/search input and never present successful consent. Invitation, student lookup and staff shared-summary lists expose usable pagination, including entries after the default first 20; unavailable data is not rendered as empty.
- Staff shared summaries identify units and accepted members separately from replaced solo records. Student preliminary/final assignments and staff results distinguish each original applying cohort from individual allocation additions, identify the student's own cohort and use an honest unavailable-origin label for historical results. Display names/project titles replace UUID labels. Pins to any submitted-group member constrain the whole unit; same-project member pins deduplicate, conflicting targets fail, unranked targets require acknowledgement, and removing one explicit pin leaves other member pins effective. These constraints are explained in staff controls without exposing pin metadata to students.
- Invitations, consent and applying-group membership/provenance are private and absent from public archive responses, DOM, links and downloads. No role, registration, idea ownership or equal ranking automatically implies applying-group membership.

- A student or teacher author starts with an idea whose title and school year remain required manual fields and whose collaborators remain manual selections. The narrative may be entered in existing fields, imported from Markdown, or provided as a PDF; form and Markdown narratives retain the existing required fields, while PDF remains an unparsed narrative document.
- Submitting an idea sends it to teacher review and locks author editing until the teacher requests revision or approves it for full specification.
- Approval allows the author to submit full specifications but does not mean the project is accepted into the application catalogue.
- A full specification includes objectives, intended users, features or requirements, deliverables, proposed scope, and known resources or dependencies.
- Markdown idea headings map to `Description`/`Beschreibung`, `Intended outcome`/`Beabsichtigtes Ergebnis`, `Initial scope points`/`Erste Umfangspunkte`, and optional `Learning topics`/`Lernthemen`. Specification headings map to `Objectives:`/`Ziele:`, `Intended users`/`Vorgesehene Nutzende`, `Requirements`/`Anforderungen`, `Deliverables`/`Ergebnisse`, `Proposed scope`/`Umfang`, and `Dependencies or resources`/`Abhängigkeiten oder Ressourcen`; list sections use one bullet per value and scalar sections retain paragraph text. Unknown, missing, duplicate, or malformed sections do not partially change fields.
- Teachers can open a private PDF preview modal with loading, error/retry, and close behavior. PDF access follows existing idea-read rules, including student access through an open accepted-project catalogue only; responses are private and non-cacheable. Public archive pages and unrelated responses never expose PDF content or private metadata. PDF bytes associated with submitted specification reviews remain unchanged across later revision edits.
- Teacher decisions and comments remain visible as review history. Clearly distinguish approval for full specification, acceptance for applications, revision requests, and declines.
- In Ideas & reviews, show every idea owner by current display name and identify the creator; students may search the display-name-only student lookup, choose collaborators at idea creation, and creators may add/remove collaborators in details while collaborators may leave. Confirm destructive owner changes, refresh owner/student lists, return focus to the lookup after add/remove and to the Ideas primary action after leaving, and close a departed collaborator’s detail view. Keep the UI readable on mobile with long owner names wrapping. Identify review authors, and teachers with recorded supervision preferences by their current account display names rather than IDs; administrators also see eligible teachers by display name in Confirm supervisor. Keep IDs for internal matching and preference status, review context, and notes visible.
- Teachers can start a review directly from an idea-list row when an idea or specification is awaiting review. Idea details and review forms open in accessible modal dialogs; a review may also be opened from the details modal, and a successful decision refreshes the list and visible history.
- Teacher ratings use a consistent 1-to-5 scale for work size, curriculum relevance, technical complexity, feasibility, learning value, resource needs, and risk/dependencies. Explain each category and show that the ratings inform but do not automatically determine the decision.
- For submitted idea reviews, declines and revision requests require non-empty written feedback but do not require ratings. Show only ratings recorded with each idea-review history entry, never defaults or an empty ratings section; keep full-specification review display unchanged. After a successful decision, refresh the idea and history, close the review flow, and focus the affected idea's Details & history control.
- Supervision preference is separate from a confirmed supervisor. In Ideas & reviews, show each teacher their own recorded preference alongside its idea, with no summary when none is recorded; retain recorded preferences in Details & history and keep editing there. Let administrators assign any teacher, grouping the options by preference and requiring explicit acknowledgment before assigning a teacher who recorded an explicit refusal.
- Students must choose at least three distinct accepted projects and rank them before an application can be submitted. Show the deadline, prevent duplicate choices, and allow reordering with accessible controls. The effective open state begins at `opensAt` regardless of stale stored status; application changes and withdrawal are available strictly before `closesAt`, and the locked state and deadline are clear. On the Applications page, a student sees current project titles from the open period catalogue in the catalogue, saved ranking, add selector, and move-button accessible labels; do not use the student's own idea list as a title source or render project UUIDs. Use `Unknown project` when a catalogue title is unresolved and do not show a project-reference ID. Period reads and catalogue details remain available through the exact `closesAt` instant even if deadline processing has changed the stored status; the detail view is unavailable after that instant. Expand each catalogue entry to read the current idea details and accepted specification for that project through the closing instant, with a clear per-project retry when the details request fails.
- An ineligible student sees a clear period-specific explanation and cannot create/update preferences, but can still read and withdraw a saved application under the existing deadline rules. Do not erase, implicitly submit, or restore saved preferences when eligibility changes. A submitted group ranking change or submission is blocked with `409` unless every accepted member is eligible; a mixed submitted group is identified as excluded whole in staff results without splitting or rewriting it.
- In the staff application summary, identify each application and its status line by the student's current display name, and show ranked preference project titles; do not show application, student, or project IDs in those labels.
- Make clear that the system closes applications and starts exactly one initial allocation automatically when the deadline is reached for every due, unfinalized period, regardless of stored status, early or replacement runs, or later period edits. Administrators can review the run, request a replacement run before finalization, and finalize its result; finalization cannot bypass the initial run. Administrator pins fix students to projects for future runs without changing their rankings; unpinned students are optimized around feasible pins and valid groups remain three to five members. After a successful add, change, or removal, refresh the list and move focus to the changed entry or, after removing the last pin, to the add-form student control; cancelled actions return focus to the control that opened them.
- The exact allocation objective order is: maximize assigned pinned students; then total assigned students; then students assigned to priority projects in that period's run snapshot; then ranked preference satisfaction using the existing scoring and deterministic tie-breaking. Priority projects are equal within their tier; priorities never reduce total assignments, override a feasible pin, split a submitted applying unit, or relax the three-to-five group-size limit. With no designated priorities, the existing objective and deterministic results remain unchanged.
- After allocation, show each assigned project or an explicit unassigned outcome. Label pinned assignments in text as fixed by the administrator and show the pin explanation for an unassigned pinned student. Project results show group members only to authorized users and never imply an invalid group size.
- Allocation results distinguish a completed run from an incomplete or failed one and explain unassigned students or projects when the system provides a reason. In authorized allocation result views, show current project titles and student display names for assignments and unassigned outcomes, retaining the supplied pin explanation and other reason text and avoiding IDs in those labels. Pin data and its administrator origin never appear in student responses.
- Staff run detail identifies the priority projects saved in that run's snapshot, not the period's later configuration. Priority settings and early-run results remain unavailable to students; do not expose priority metadata in student period/application responses or public archive surfaces.
- Every eligible student is a candidate even without a saved ranking. Staff assignment rows identify preference-backed and no-preference assignments and show an explicit unavailable label when a legacy result lacks immutable preference-state evidence; explain whole mixed-eligibility group exclusions. The student period projection shows only the caller's own no-preference indicator; historical results without snapshot evidence show an unavailable label. Never expose another group member's preference status, rankings, eligibility IDs, class membership, pins, or optimizer details in student views. Eligibility changes affect only later snapshots; pins do not override ineligibility and saved pins can apply again after restored eligibility.
- Once a group is formed, provide a distinct formal project application form with the official fields: project topic (maximum 200 characters); individual topic per student (maximum 200 characters each); initial situation the project aims to change (maximum 400 characters); scientific investigation concerns linked to each student (maximum 2,400 characters total across the group); project objective or goal (maximum 400 characters); planned result of each student's individual part (maximum 2,400 characters total across the group); milestones, each with text and date; and an optional cooperation partner.
- Display remaining character counts for each limited field, including the shared group totals for investigation concerns and planned results. Make it clear to students how shared limits apply as group members edit their contributions.
- Show teacher approval or revision feedback before presenting project work as approved to begin.
- The initial rubric is based on the draft `docs/Entwurf Rubrikenbewertung.docx`, which may change. Present criteria from the applicable rubric version rather than hard-coding the draft as permanent. Its current categories are technical realization, project management, written work and technical documentation, presentation/discussion/defense, self-competence, and professional-field competence.
- Publishing a new rubric version is an administrator action on `/rubrics`, using a local JSON draft copied from a selected version or loaded from reusable JSON. Clearly display version applicability; changes must not silently alter earlier assessments or grade calculations. When a new version is explicitly applied to an in-progress project, show the transition and preserve which version applies to each assessment. Published versions remain immutable.
- Only teachers can configure separate routine/final rubric versions and use grade-entry controls. Show every configured `STUDENT`/`BOTH` criterion for the selected student and exact phase rubric, in category order, including configured description, scale/labels, evidence requirement, date, evidence, and comments; exclude `GROUP`-only criteria. Routine rows are blank every time and saving appends only valid rows with an explicitly chosen grade. Final rows show only current exact-version final values, keep unassessed criteria blank, and require a revision reason for changes. Preserve visible history for superseded entries. Validate all populated rows before requests and report confirmed successes, unresolved rows, ambiguous outcomes and revision conflicts accurately; never call a per-row sequence atomic or blindly retry an ambiguous routine write. A stale final-revision conflict blocks retry until history is refreshed; preserve the draft, surface the current value and require an explicit resubmission. Administrators may read authorized grading history but cannot mutate grades. Students can view only their own individual grades.
- Only teachers can enter project metrics. Metric entry and display must be driven by metric definitions in the applicable rubric or school configuration. Do not hard-code an assumed metric list, units, or scale in the UI. Administrators may retain authorized read access.
- Show individual final grades and the overall project grade where configured, with their bases. Only teachers can record or revise these grades. The bases must demonstrate consideration of applicable rubric assessments and project metrics. If calculation rules have not been configured, present teacher-recorded or confirmed grading with the teacher's rationale and without implying an automatic formula; when rules are configured, show the rule version and applicable inputs. Administrators may retain authorized read access.
- The completed project's approved public archive is accessible without registration and is read-only. Provide an accessible browser for the website snapshot and clear ways to retrieve approved poster and source-data artefacts. Clearly label the archive as a completed-project snapshot, distinct from the live website.
- Keep publication review separate from upload: only explicitly approved artefacts for completed projects appear in the public archive. Authenticated archive management identifies private artefacts and provides authorized teacher publication-review and unpublish controls.
- Public archive pages and files must not expose student names or identities, group membership, account information, applications, formal-application or review history, individual or group grades, rubric assessments, teacher feedback, private project metrics, uploader identities, or audit history. Do not show uploader metadata publicly.
- Before publication, require review of website snapshots and artefacts for personal/sensitive data, credentials, private communications, grading information, and unsafe active content. ## Student class and elective-subject presentation

The administrator interface provides shared class and elective-subject catalogue editing and lets administrators assign one class and up to four subjects to each student. It provides validation feedback, allows clearing subject assignments, and displays resolved catalogue names rather than identifiers.

Authenticated teacher and administrator identity views show current class and elective-subject names beside student names in ideas/reviews, application summaries, allocation results, administrator account lists, and grading. Catalogues and student assignments are not presented to students or in student-facing groups, and do not appear in public archive views. The existing registration and login flow remains unchanged; new student accounts are assigned the default class.
