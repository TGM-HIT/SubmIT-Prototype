# Frontend Development Guidelines

The SubmIT frontend is a Vue 3 application using Vite, TypeScript, and Tailwind CSS. Functional behavior is defined in `frontend/SPEC.md`; shared product behavior is defined in `docs/SPEC.md`.

## Structure

Organize code by user-facing feature below `frontend/src/features`. Relevant features include authentication, dashboard, ideas and specifications, teacher reviews and supervision, school years and application periods, student applications and allocation, formal proposals, grading rubrics and assessments, project metrics, project archive/artefacts, and audit history.

Keep reusable primitives in `components`, layouts in `layouts`, routes in `router`, application state in `stores`, reusable behavior in `composables`, and HTTP access in `services`. Components must not construct raw endpoint URLs or implement authorization rules. Follow existing project structure when extending it rather than adding duplicate layers.

## API and State

- Use generated OpenAPI types from `contracts/openapi.yaml` for endpoint and request/response details. Regenerate frontend API types with the existing `api:types` script after the OpenAPI contract changes.
- Centralize authentication, request errors, pagination, and retry behavior in shared services. Keep server state separate from local form state and preserve pagination/filter state during navigation.
- The backend is authoritative for role and resource permissions. The frontend may hide or disable controls based on role and lifecycle state, but must handle backend `401`, `403`, validation, and conflict responses without losing valid form input.
- Keep lifecycle states visible and distinct: teacher approval to develop full specifications is not acceptance for student applications; student preference applications are different from an allocated group's formal proposal; teacher approval of the formal proposal is required before project work is presented as approved to begin.
- For formal proposals, bind per-student topic, investigation concern, and planned result fields to the correct group member. Show individual character limits and live shared totals for investigation concerns and planned results. Client validation improves usability, but the backend enforces the limits.
- Render rubric criteria, scales, metrics, and calculation information from the applicable rubric version. Do not hard-code the draft rubric as permanent. Preserve clear context for individual versus group assessments, rubric version, assessment date, teacher evidence/comments, and grade history.
- Show students only their own individual grades. Do not expose student identity, group membership, applications, reviews, grades, rubric assessments, teacher feedback, private metrics, uploader identity, or audit data in public archive pages or files.
- Treat public archive browsing as a separate unauthenticated, read-only experience. Only approved artefacts for completed projects are public. Private artefacts and archive-management controls require authentication and authorization. Never render untrusted archived website code in the application's origin.
- Display public artefact metadata only after excluding private uploader and student information. Avoid leaking restricted data through URLs, filenames, embedded assets, links, browser caches, or error messages.

## UI and Tailwind

Use semantic HTML, responsive layouts, keyboard-accessible controls, visible focus states, labels, and status indicators that do not rely on color alone. Keep domain feature styles close to their feature and use shared Tailwind tokens/components for repeated patterns.

Every async view must define loading, empty, error, retry, and success states. Forms must display field-level validation and preserve user input after server errors. Use clear confirmations for submitting/withdrawing applications, publishing or removing public artefacts, and finalizing allocation or grading actions. Public archive browsing should make it clear that the content is a reviewed, read-only snapshot and not the live project website.

## Interface localization

All frontend-owned interface strings belong in the parallel `en` and `de` catalogs under `src/locales/`; keys must match exactly. Use the installed Vue I18n composer (`$t` in templates or `i18n.global.t` in TypeScript) rather than embedded locale conditionals. Missing translations are warnings and English fallback is disabled. Keep user- and backend-authored content, including API error messages, unchanged. Resolve anonymous language from `navigator.language`; authenticated language comes from the account response. Use the selected locale for frontend-generated date and number formatting.

For browser-locale verification, use the supported preview tool's `--locale <BCP-47-tag>` option, for example `npm run preview -- --path /login --locale de-DE`. The preview sets Chromium's locale and verifies/reports its actual `navigator.language`; do not assign that browser property in application code. Keep parser and CLI regressions in `scripts/preview.smoke.mjs` and run `npm run preview:test` after changing preview behavior.

## Verification

Run the scripts defined in `frontend/package.json` after frontend code changes:

- `npm run check:deprecated` resolves `@deprecated` declarations in owned TypeScript/Vue source (including tests, generated API declarations, and Vite configuration) and JavaScript/Node `.mjs` preview and documentation tooling. Vue script blocks are parsed and analyzed. It fails on findings or source-analysis errors; do not suppress findings or exclude owned files.
- `npm run typecheck`
- `npm run test`
- `npm run preview:test` (includes preview/documentation-tooling and deprecation-checker fixtures)
- `npm run build`

`npm run typecheck` and `npm run build` run the deprecation check before Vue/TypeScript checking; the root `make check` reaches it through the frontend build. Run the deprecation check and relevant tests before integrating frontend changes. Documentation-only changes do not require these commands unless their Node tooling changes.

For repeated JUnit report summaries or structural JSON comparisons, the optional helpers in the [shared verification guide](../scripts/README.md) may be useful when their documented behavior matches the check. JUnit summaries validate supplied counts but do not establish report provenance; JSON comparison ignores object-key order, preserves array order, and does not print values. These helpers do not replace required checks or direct test execution.

## Full-lifecycle local documentation

The public entry point is the **repository-root** `make doc LANGUAGE=en` or `make doc LANGUAGE=de`, not a frontend-local npm command. No credential setup is required: the runner defaults to the existing public testing-profile fixture password described in `backend/DEV-GUIDELINES.md` for its isolated local backend. `PREVIEW_PASSWORD` is an optional environment override; an empty value uses the default. Never supply production credentials or put passwords in templates or generated guides. Requires Make, the existing Java/Gradle setup, installed frontend dependencies (`make install`), the preview tool's supported Node version and Chrome/Chromium (`CHROME_BIN` may select an executable).

The command starts and owns a fresh backend JVM in the `testing` profile and Vite, refuses an existing preview session or occupied ports 8080/5173, runs the shared Chrome/CDP lifecycle, validates all Markdown links and PNGs, then replaces the selected local guide set. No application needs to be prestarted. It never reuses or stops an unrelated preview session. Missing, unsupported or incomplete `LANGUAGE` fails before startup or output replacement; no language fallback is used.

Only this command's child environment selects existing minimal testing fixtures and disables optional allocation-pin preview and bootstrap-admin credentials. It preserves the 32 testing accounts and ten minimal idea fixtures. Ordinary full/minimal fixture implementations are unchanged. The explicit documentation setup uses authorized existing HTTP services to prepare two supporting accepted projects and an initial valid rubric; later it prepares each applicant's initial ranking record and minimal initial final-grade records before dependent page reads. The run report discloses these records rather than presenting them as UI actions. The main project is created through UI controls, including a real revision round, specification acceptance, period setup, ranking saves, scheduler deadline allocation, finalization, formal approval, assessments/metrics, final-grade confirmation with rationale, private upload, publication review, completion and an anonymous archive with download/privacy checks. The existing 30-second allocation scheduler is unchanged; a bounded poll waits for its initial non-early run rather than starting a replacement.

Generated Markdown and desktop screenshots (1440 × 1000) live only in ignored `docs/user-guide/`. Tracked locale content, templates/rendering, validation and shared scenario tooling live under `frontend/scripts/documentation/`; generation must not change those sources. Reports and failure screenshots live outside the guides in ignored `frontend/.preview/documentation-report.json` and `frontend/.preview/documentation-failure-desktop.png`. They record stage, actor, route, dynamically resolved identifiers, exact selectors/control labels, prepared prerequisites and checkpoint dimensions, but not credentials.

On failure/interruption, the command exits nonzero, preserves the previous guide set, and removes its services, browser profiles, staging directory and owned lock. Fix the reported stage/prerequisite and rerun the same root command. Do not clear an unrelated shared session. If a host crash or SIGKILL prevents normal cleanup, first inspect the PID in `frontend/.preview/documentation.lock` and confirm it no longer owns processes or ports before removing that stale lock; never delete a live run's lock.

`npm run preview:test` includes Node-runner documentation tests for locale/input validation, guide/reference/PNG integrity, atomic output replacement, injected failures and repeatable inventory, alongside ordinary preview/session smoke tests. The durable real-browser lifecycles are the root `make doc LANGUAGE=en` and `make doc LANGUAGE=de` commands; run each for its own language and compare the checkpoint and guide-reference inventories in its report. Inspect generated English and German guides and images for language clarity and accurate, legible UI state; structural tests do not replace presentation judgement.

To add a language, follow [`scripts/documentation/README.md`](scripts/documentation/README.md).

## Local browser preview

Add `--network-report` to a preview invocation to print API request URLs/methods, initiators, statuses and observed completion/failure flags for local evidence. Authentication requests, headers and payloads are excluded; response bodies are not captured. A cancellation field is unavailable unless a failure event occurs. Retain diagnostic reports only in the run's ignored evidence directory.

Applying-group walkthrough (opt-in, testing accounts only): from `frontend/`, run `DADB_TESTING_APPLYING_GROUP_PREVIEW=true npm run preview -- --session-start`. Use the existing `--session --auth --username student01|student02|admin01 --path /applications|/allocation --viewport desktop|mobile` commands with `PREVIEW_PASSWORD` from the documented testing-account convention and an ignored run evidence `--output-dir`. Each invocation authenticates its own actor against the same disposable session. In **Apply together walkthrough**, create the group as student01, invite student02 by display-name lookup, accept as student02, save three preferences as creator, approve the current revision as both, then confirm shared submission as creator. Use the separate **Apply together departure** period for cancellation/leave/withdraw/dissolution evidence; do not withdraw the main pair. The fixture provides initial own applications for student01/02/03 in both periods. As admin01 inspect pins and start an early run, then wait for the main period's real future deadline (420 seconds from session startup) and automatic initial run before finalizing through the UI. Capture member final-group provenance and the separate Formal proposal action on both viewports. Stop with `npm run preview -- --session-stop`. Prerequisites and ordinary fixture preservation are defined by `TestingApplyingGroupPreviewConfiguration` and tested by `TestingApplyingGroupPreviewTest`; do not patch database state or skip failed setup requests to advance the story.

From `frontend/`, run `npm run preview:help` for the reusable Chrome/CDP preview command and options. `npm run preview -- --viewport mobile --output-dir /tmp/previews --screenshot ideas-mobile.png` starts the frontend and backend, waits for readiness, captures the real page, and shuts down its child processes. Chrome/Chromium and Node.js `^20.19.0 || ^22.12.0 || >=24.0.0` are required, matching the supported dependency engines. Node 23 is excluded because the patched test dependencies (Vitest 4.1.12+ and jsdom 28) do not support it. `CHROME_BIN` or `--chrome` selects a nonstandard browser path. Default screenshots go to the ignored `frontend/.preview/` directory.

For browser-generated file downloads, first prepare the full definition through the localized download button; it exposes and focuses an accessible `a download` link once the request completes. Activate that focused link using an ordered `--step 'download:SELECTOR'` with an ignored `--output-dir`. The step requires the link to already be focused, sends a real browser Enter key, waits for the Chrome download-completion event, and retains the payload under the browser-suggested filename (adding a numeric suffix only to avoid overwriting prior evidence). `--network-report` records the related local request URL, method, initiator, response status and completion state without credentials or response bodies. Use `--step 'tab-to:SELECTOR'` to reach a control with actual browser Tab input during an ordered flow; it reports the observed focused element. Other `key` steps likewise report resulting focus, and `read:SELECTOR` records visible page state. Do not treat a dispatched event alone as observed focus.

For rubric pagination walkthroughs only, `--seed-rubric-pagination-preview` requires a fresh started preview, `--auth --username admin01`, and `--path /rubrics`. It creates 21 synthetic, future-effective rubric versions through the existing authenticated publication API before opening the page; the default seeded draft remains active and can be reached on the next page. This disposable setup is not production data. The reusable setup and download capture are implemented in `scripts/preview.mjs` and covered by `scripts/preview.smoke.mjs`. `--evidence-report FILE` writes the sanitized request/interaction/fixture report under `--output-dir`, alongside captured browser downloads and screenshots.

For anonymous public-archive browsing checks, start a fresh testing-profile preview with `--seed-archive-preview`, for example `npm run preview -- --seed-archive-preview --path '/archive/{archiveProjectId}'`. The preview substitutes the generated completed-project ID into that route and reports it. The fixture uses the existing testing accounts and archive lifecycle services; it contains an approved WACZ website snapshot with an active-content isolation probe, relative page link, and bundled image, plus the required completion artefacts. It is absent from ordinary and production data, does not alter default fixture/account counts, and cannot be combined with a shared preview session. After opening the snapshot with the supported ordered steps, `--step assert-archive-isolation` verifies the iframe sandbox, application-origin storage/cookie probe, restrictive CSP, and bundled data URL and includes the result in `--evidence-report`.

Ordinary `make run-testing` startup already provides the immutable, testing-only snapshot `dev55-draft-testing-v1` of the changeable `docs/Entwurf Rubrikenbewertung.docx`; it is explicitly an unapproved draft and is not school policy. The version is available to `/grading` rubric-selection controls but is not bound to a project by default; teachers must explicitly select routine and final versions. The opt-in `DADB_TESTING_GRADING_SELECTION_PREVIEW` fixture adds a distinct synthetic final rubric for phase-specific grading walkthroughs (details in `backend/DEV-GUIDELINES.md`). The full-lifecycle documentation workflow is separate: its preparation still publishes its own valid initial rubric through the API, verifies that rubric is active, and later publishes a second immutable version through the administrator UI on `/rubrics`. Do not remove or replace those publication steps with the ordinary testing fixture; that workflow deliberately covers rubric publication.

For authenticated previews, use a testing-profile account already documented in `backend/DEV-GUIDELINES.md`; the preview tool can seed an idea with `--seed-idea-owner USER` or an idea with a review and supervision-preference history using `--seed-idea-history USER`. For allocation pin pagination and infeasible-pin result verification, opt in to the reusable testing-only fixture with `--seed-allocation-pin-preview` when starting an authenticated preview as `admin01`; this enables the testing-profile fixture described in the backend guide and cannot be combined with minimal-fixture mode. The latter creates only synthetic data in the temporary testing profile using the documented testing accounts; both options require a started local testing-profile preview and a testing student account. See `npm run preview:help` for details. For example, set `PREVIEW_PASSWORD` to that documented testing password and run `npm run preview -- --auth --username student01 --path /ideas`. Reusable form interactions may be requested with repeatable `--fill SELECTOR=VALUE`, `--click SELECTOR`, and `--wait-for SELECTOR`; `--expand-select SELECTOR` temporarily displays all options of a native selector inline for screenshot inspection. For conditional flows that need actions interleaved, repeat `--step` with `fill:SELECTOR=VALUE`, `set-json-field:SELECTOR=FIELD=VALUE`, `set-file:SELECTOR=REPOSITORY_RELATIVE_PATH`, `click:SELECTOR`, `wait:SELECTOR`, `read:SELECTOR`, `focus:SELECTOR`, `tab-to:SELECTOR`, `key:Tab|Shift+Tab|Escape`, `download:SELECTOR`, `screenshot:FILE`, or `offline` / `online`; `accept-confirms` and `reject-confirms` configure confirmation dialogs only in the local preview. `set-file` resolves a named file inside this repository and selects it only on a matching browser file-input element; it does not accept arbitrary host paths. For example, `--step 'set-file:#rubric-draft-json=backend/src/main/resources/testing/grading-rubric-draft.json'` selects the checked-in reusable rubric fixture. `set-json-field` changes one top-level string field in an existing object-shaped JSON textarea and dispatches input/change events; it is local editing only and never publishes. The network steps disconnect or restore the browser after page load for reusable request-failure and offline-state checks; intentional offline API failures appear in the request report without failing the preview when their localized fallback is shown. `--step measure-overflow` reports document, body and viewport widths and fails if the document has horizontal overflow. This supports reusable multi-step workflows and screenshots between states.

For same-browser navigation checks, `--step navigate:/path` performs a same-origin document navigation, `--step assert-url:/path?query#hash` verifies the current path, query and hash, and `--step reload` reloads the current document while retaining that browser's storage. `navigate` accepts only same-origin absolute paths.

They run in that order after authentication, and each wait allows up to 10 seconds. Known behavior: the preview run fails when the page triggers any HTTP 4xx response, including an expected one such as a student's `GET .../applications/me` returning 404 before an application exists, so create the needed record first or report the expected 4xx with its URL; `--fill` and `--click` options run in that fixed order, so open a form with `--click` and `--wait-for` it before filling it, or use `--step` for flows that interleave actions. To inspect the testing-profile submitted formal proposal fixture as a teacher, use the project ID documented in `backend/DEV-GUIDELINES.md`:

```sh
PREVIEW_PASSWORD=testing-password npm run preview -- --auth --username teacher01 --path /formal-application --fill '#project-id=03a00000-0000-4000-8000-000000000001' --click 'form.toolbar button' --wait-for '#formal-decision' --expand-select '#formal-decision' --viewport desktop --output-dir /tmp/bug03-preview --screenshot formal-applications.png
```

Interactions run after authentication in the order fill, click, wait, then expand, Tab navigation, and keyboard selection. Expanding changes only the preview page's rendered select size, not application data or production code.

### Real-browser keyboard regression suite

The grading/rubric browser regression is available through the same browser test target. It navigates to `/rubrics` for rubric version browsing and downloads, while grading workflows remain on `/grading`:

```sh
PREVIEW_PASSWORD=testing-password npm run test:keyboard -- --grading-only --output-dir ../harness/runs/<run-id>/evidence/<revision>
```

It uses four disposable ordinary full `testing` previews (`admin01`), one for each English/German × desktop 1440 × 900/mobile 390 × 844 combination, on four successive frontend/backend ports from the configured bases. It opts into the existing 21-version rubric-pagination fixture, saves the account language through Settings, and follows **Rubrics & progress** with actual Tab/Enter input. It exercises first/next/previous/next pagination, both definition preparation controls and both real browser saves. `assert-action-visible:SELECTOR` verifies the focused action is enabled and wholly within the viewport; `measure-overflow` checks page width. The runner compares the saved filenames, entire parsed JSON and entire ordered Markdown with a test-owned expectation from the independently preserved Dev-55 resource, not the application exporter. It checks the blank project ID, unchanged active version and selected page after saving. The per-case directories contain saved payloads, page-one and post-save screenshots, focus/input/request/download/console/Chrome diagnostic traces, and the parent `grading-keyboard-results.json` records pass/fail without skipping missing prerequisites. Use a new ignored revision directory to preserve earlier evidence. Mocked smoke tests do not replace this real-browser command.

Preview evidence reports are persisted on interaction/download failure as well as success. They redact authentication secrets and retain available download begin/progress, request URL/method/initiator/status/completion, page console and Chrome process diagnostics. Blob-download fields absent from CDP are explicitly unavailable, not inferred from a successful detail API read. Browser download directories are resolved to absolute paths before configuring Chrome (relative paths are not a portable CDP save destination). A canceled progress event remains a failed check; it is not a successful save. Chrome/macOS diagnostics may only be classified as host noise when completed saves and page-console/request checks establish that the observed run was unaffected.

The repeatable initial keyboard regression suite runs actual Chrome/Chromium key input through the existing CDP preview and testing-session lifecycle. From `frontend/`, run:

```sh
PREVIEW_PASSWORD=testing-password npm run test:keyboard -- --output-dir ../harness/runs/<run-id>/evidence
```

The caller-provided evidence directory must be ignored by Git. The command requires the documented testing password, supported Node.js, installed frontend dependencies and backend toolchain, Chrome/Chromium (`CHROME_BIN` may select a nonstandard executable), and six successive frontend/backend preview ports from the configured bases (5173–5178 and 8080–8085 by default). It starts six disposable testing-profile sessions across two repetitions, waits for the existing seeders, and stops only sessions it owns. K1/K2 share one session per repetition; K3 desktop and mobile each start from isolated fixture state. A pre-existing session or occupied port is a failure, not something the suite stops or reuses. Each K3 session opts into the existing `DADB_TESTING_ELIGIBLE_FORMAL_PROJECT_PREVIEW` fixture for the private finalized roster and the 2027/2028 **New proposal** project; ordinary testing seed data and account counts are unchanged. See `backend/DEV-GUIDELINES.md` for the existing accounts and fixture details.

The positive matrix contains only K1–K3 (12 cases). K2 selects TEACHER with Space, requires the draft-derived Save button to become enabled, then cancels and reopens to verify the original roles and disabled Save without a role update. K3 compares reopened labels and all three contribution fields with the same roster identity and persisted API values in memory; actual roster IDs must be absent from every tab label.

Run the separate deliberate incorrect-focus command to verify failure reporting:

```sh
PREVIEW_PASSWORD=testing-password npm run test:keyboard -- --negative-focus --output-dir ../harness/runs/<run-id>/evidence/negative-focus
```

This invocation starts one disposable session and **must exit 1**, not pass as an expected rejection. It leaves username focused while asserting password focus through the reusable bounded browser assertion. Its `keyboard-results.json` must contain one `failed` case with the named step, expected `password`, observed `username`, and a failure-diagnostic screenshot. Do not combine this output directory with the positive matrix.

`keyboard-results.json` contains the named scenario, viewport, key sequence, observed focus or state assertions, and precise failure step; assertion errors include expected/observed state. Scenario screenshots are named by run, K1-K3, viewport and final UI state; failed-case captures use a failure-diagnostic suffix. Rendered screenshot text is masked. Results exclude credentials, authentication payloads, tokens, private roster names and IDs, and proposal field contents. A passing browser run is evidence of the listed page-level interactions only: it is not an exhaustive accessibility certification. `npm run test` covers component tests, and `npm run preview:test` covers Node-runner and mocked preview regressions; neither is real-browser evidence. OS-native select popup permission checks, assistive-technology behavior, and personal visual or usability judgments still require their separate genuinely human checks.

For an actual collapsed native popup on macOS, use headed Google Chrome with `--tab-to SELECTOR --native-select-by-key SELECTOR=VALUE`. This uses macOS System Events input; it is restricted to headed macOS Chrome, does not fall back to CDP key events, and verifies the selected DOM value before saving a screenshot. If macOS reports that `osascript` is not permitted to send keystrokes:

1. Open **System Settings → Privacy & Security → Accessibility**.
2. Enable the app that launched the preview command. Use **Terminal** if you ran `npm` in Terminal; use **Visual Studio Code** if you ran it in VS Code's integrated terminal. Grant permission to that host app, not Google Chrome. If the app is not listed, add it with **+** (Terminal is in `/Applications/Utilities/Terminal.app`; VS Code is normally in `/Applications/Visual Studio Code.app`), then enable it.
3. Quit and reopen that host app so it starts with the updated permission. Return to `frontend/` and rerun the preview command. For example, with the local testing profile and an enabled Ideas status option different from the current selection:

   ```sh
   PREVIEW_PASSWORD=testing-password npm run preview -- --headed --auth --username student01 --path /ideas --tab-to '#status-filter' --native-select-by-key '#status-filter=IDEA_SUBMITTED' --viewport desktop --output-dir /tmp/bug03b-native --screenshot ideas-native-selected.png
   ```

   If `IDEA_SUBMITTED` is already selected or unavailable, use another enabled `#status-filter` value that is different from its current value.

4. Count this as successful evidence only when the real command reports that the macOS native-popup keyboard selected the requested value, completes the screenshot, and the saved screenshot at `/tmp/bug03b-native/ideas-native-selected.png` shows the selector displaying the changed value. The preview also checks the live DOM value before taking the screenshot. Record that screenshot path and the reported value. A permission error, mock/smoke-test result, or screenshot without a confirmed changed value is not proof that the native popup interaction succeeded; do not substitute `--select-by-key` or `--expand-select` for this check.

### Persistent shared preview session

By default every `npm run preview` invocation starts a fresh temporary testing profile and discards it afterwards. To verify a multi-actor flow across several independent invocations (for example a student edits an idea and a teacher then reviews that same idea), opt in to one shared session. Its data lives only until you stop it; browser login state is never shared, because every invocation launches its own temporary browser profile.

```sh
npm run preview -- --session-start     # starts backend + frontend detached, waits for readiness, prints the frontend URL
npm run preview -- --session-url       # prints the URL again; fails if no session is running
PREVIEW_PASSWORD=testing-password npm run preview -- --session --auth --username student01 --seed-idea-history student01 --seed-idea-title 'Distinct title' --path /ideas --screenshot step1.png
PREVIEW_PASSWORD=testing-password npm run preview -- --session --auth --username student01 --path /ideas --step 'click-record-action:Distinct title|text:Edit' --step 'wait:#idea-title' --step 'accept-confirms' --step 'fill:#idea-description=Edited by the student' --step 'click:form.panel button.button:not([type=button])' --step 'wait:article.data-row' --step 'click-record-action:Distinct title|text:Submit'
PREVIEW_PASSWORD=testing-password npm run preview -- --session --auth --username teacher01 --path /ideas --step 'read-record:Distinct title' --screenshot teacher.png
npm run preview -- --session-stop      # stops both process groups and discards the data
```

A submitted idea is not editable by its student, so the example seeds with `--seed-idea-history` (submitted, then a teacher requests revision); the student can then edit and resubmit it through the UI. Switch roles by authenticating again with another `--username`. `--seed-idea-owner` and `--seed-idea-history` work with `--session` and seed into the session's backend; `--seed-idea-title` gives the seeded idea a distinctive title. To reopen a record that an earlier invocation created or changed, use `--step click-record-action:TITLE_OR_ID|SELECTOR` (click a control inside that Ideas-list row, given as a CSS selector or `text:BUTTON_TEXT` such as `text:Edit`) or `--step read-record:TITLE_OR_ID` (log the row's text, including its status). The key is the exact idea title or the idea ID (the ID is the suffix of the row's `details-button-ID`); the step fails if no row or more than one row matches, so it never falls back to a different record. The record must be on the listed page.

Limitations: one session at a time, on ports 5173 and 8080 unless `--frontend-port`/`--backend-port` are given to `--session-start`. `--session-start` fails with a clear message if a port is in use or a session is already running; `--session` fails if no session is running or a service died (run `--session-stop` to clear it); a default (non-session) preview fails while a session is running rather than clashing on its ports. Session state and service logs are in the ignored `frontend/.preview/` directory. Always run `--session-stop` when finished.

Use `npm run preview:test` for the no-dependency preview-tool smoke tests.
